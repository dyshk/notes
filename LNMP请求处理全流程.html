LNMP 请求处理全流程 · Docker 与裸机双模式

用户访问网址时，后台每一步在做什么、读的是哪个配置文件的哪一行、以及这一步最容易踩的坑
GET http://localhost/index.php
当前模式：Docker 容器化。 Nginx、PHP-FPM、MySQL 各跑在一个独立容器里，各自有独立的文件系统与网络命名空间。 容器之间通过 Docker 内建 DNS + 服务名（php、mysql）通信，不能用 127.0.0.1，也不能用 unix socket。 宿主机在这条链路里只干两件事：转发端口（80:80）、提供代码目录（把 ./html 同时挂给 nginx 和 php）。
当前模式：裸机直接安装。 Nginx、PHP-FPM、MySQL 都是同一台机器上的系统服务，共享同一个网络命名空间， 因此彼此可以用 127.0.0.1 / localhost，甚至用 unix socket 通信（比 TCP 更快）。 核心认知：Nginx 不会执行 PHP，它只是个"转发员" —— 漏配 location ~ \.php$ 会导致 .php 源码被直接下载。
请求链路架构 · Docker 容器化

结构篇

服务是怎么连起来的 · 又是怎么跑起来的

上面讲的是「一个请求进来之后怎么走完」；这一节讲的是「这套东西平时靠什么连着、各自内部在跑什么」。 整套架构其实只有 三条通信线 和 三个进程组，把这两件事看明白，剩下都是细节。

① 连接全景：三条通信线 + 两张网

三条通信线：① 浏览器 → nginx（靠 80 端口映射）；② nginx → php（backend 网内，php:9000）；③ php → mysql（backend 网内，mysql:3306）。 另外还有一条「旁路」：宿主机数据库工具 → mysql（3306 端口映射），只给你调试用，网站本身不走它。
nginx 画了两次，是因为它同时接了 frontend 和 backend 两张网（compose 第 22 行 networks: [frontend, backend]），物理上是一块网卡 eth0 + 一块 eth1。 php 只在 backend（第 48 行）、mysql 只在 backend（第 74 行）—— 所以 mysql 在 frontend 网上根本不存在，外部只能靠 3306 端口映射进来。

③ 为什么三个地方填的地址都不一样

谁在说话该填什么为什么
浏览器（宿主机上）localhost 或服务器 IP它跟 nginx 之间隔了一层 Docker 端口转发，用的是宿主机的地址。
Nginx（容器里）php:9000它和 php 同在 backend 网，可以直接用服务名；写 IP 也行但容器重启 IP 会变。
PHP（容器里）mysql（端口 3306）同上。这是你之前自检失败的根因 —— 填 127.0.0.1 等于让 php 连它自己。
DBeaver（宿主机上）localhost:3306它走的是端口映射，所以反而可以用 localhost。
一句话记住：localhost / 127.0.0.1 永远指「正在说话的那台机器自己」。 在宿主机上说话 → 指宿主机；在容器里说话 → 指那个容器。所以同一个词在四个位置含义完全不同， 判断的唯一标准是：这段代码跑在哪台机器（哪个容器）里。

④ 端口映射：哪些口对外开放了

服务映射实际监听谁能访问说明 / 建议
nginx"80:80"0.0.0.0:80（所有网卡）局域网 / 公网这是网站的入口，必须开放，保持即可。
mysql"3306:3306"0.0.0.0:3306同网段任何机器 只为本机 DBeaver 调试方便。生产环境改成 "127.0.0.1:3306:3306"，数据库就只有宿主机能连，局域网扫不到。
php无（未配置 ports）仅容器内网 9000只有 backend 网内的 nginx故意不暴露，这是对的。 php-fpm 直接对外是安全隐患，它只该被 nginx 访问。
坑点："80:80" 是 "0.0.0.0:80:80" 的简写，意思是「宿主机所有网卡的 80 都转到容器 80」。 写成 "127.0.0.1:80:80" 就只有本机浏览器能访问，局域网其他机器访问不了 —— 排查"别人打不开我网站"时先看这里。

⑤ 每个服务内部到底在跑什么（进程模型）

lnmp-nginx
  • 1 个 master 进程 + N 个 worker 进程。 master 只负责读配置、管 worker，真正处理请求的是 worker（数量默认等于 CPU 核数）。
  • 官方镜像用 nginx -g 'daemon off;' 前台运行 —— 容器里 PID 1 必须占住前台，一旦后台化容器就会立刻退出。
  • 健康检查是 nginx -t（compose 第 27 行），只验配置语法，不验端口。
  • 改了 default.conf 之后执行 docker exec lnmp-nginx nginx -s reload 即可，不用重启容器。
lnmp-php
  • master 进程 + worker 池（默认池名 www）。 master 只做调度和拉起 worker，PHP 代码是 worker 执行的。
  • worker 监听 9000 端口等 nginx 送活过来（FastCGI）。
  • 为什么镜像必须是 -fpm 变体：cli 变体根本没有 php-fpm 这个二进制，9000 没人监听 → nginx 一律 502。
  • pdo_mysql / mysqli 是在 Dockerfile-php 第 4 行编译进镜像的 —— 没有它俩，PHP 连不上任何数据库。
  • 健康检查 php-fpm -t（compose 第 51 行）。
lnmp-mysql
  • mysqld 是单进程多线程：一个进程，内部用线程池处理并发连接。
  • 初始化只在 /var/lib/mysql 为空时发生一次。 之后改 compose 里的 MYSQL_ROOT_PASSWORD（第 67 行）对已有数据完全无效 —— 必须 ALTER USER 改，或 down -v 删卷重建。
  • 健康检查每 10 秒 mysqladmin ping（第 77 行），且 start_period: 40s（第 81 行）专门给首次初始化留时间，别把它调小。
  • 字符集由 command 里的 --character-set-server=utf8mb4（第 72-73 行）指定，同样是初始化时定死的。

→
4. nginx 最后起第 19-21 行

depends_on 的两种条件差别很大：
  • service_started：只要容器进程起来了就算数，不管里面服务能不能用。nginx 等 php 用的是这个（第 21 行）。
  • service_healthy：要等 healthcheck 真的通过才开始。php 等 mysql 用的是这个（第 47 行）—— 因为 MySQL 首次初始化很慢，光"容器起来了"远不等于"能连了"。
  • 注意 depends_on 只保证"数据库能应答"，不保证"你的库表已经建好"。建表、导数据这类事仍要在应用里做重试或单独执行。

⑦ 为什么两个容器能看到同一个 .php 文件

环节发生了什么
挂载 ./html 被同时挂进 nginx（第 14 行）和 php（第 41 行），而且容器内路径一模一样，都是 /usr/share/nginx/html。
Nginx 侧 匹配到 .php 后，按 default.conf 第 30 行算出脚本绝对路径：
SCRIPT_FILENAME = /usr/share/nginx/html/index.php，随 FastCGI 请求一起发给 php。
PHP 侧 php 拿到这个路径，在自己容器的文件系统里按原样去找。因为挂载点相同，它找到的就是宿主机 ./html/index.php 那同一个文件。
不一致会怎样 若两边容器内路径不同（比如 php 挂到 /var/www/html），php 找不到脚本 → 错误日志 Primary script unknown，浏览器只显示一行 File not found.，非常难排。
顺带说清另外两个挂载为什么带 :ro： ./nginx/default.conf（第 15 行）和 ./php/php.ini（第 42 行）都标了只读， 意思是只允许容器读，不允许容器改宿主机上的文件 —— 防止容器里的进程反过来篡改你的配置。代码目录 ./html 不能加 :ro，因为网站可能要写缓存、传附件。

⑧ 连不上时，按报错反查

报错出在哪条连接怎么查
SQLSTATE[HY000] [2002] Connection refused php → mysql 连库主机是不是写了 127.0.0.1 / localhost？改成 mysql。再确认 php 跟 mysql 同在 backend 网。
Public Key Retrieval is not allowed DBeaver → mysql JDBC URL 末尾加 ?allowPublicKeyRetrieval=true&useSSL=false。这是 MySQL 8 默认认证插件 caching_sha2_password 的要求，不是密码错。
ERROR 1045 Access denied 任意 → mysql MySQL 账号 = 用户名 + 来源主机。多条都能匹配时优先级：具体 IP > 主机名 > 通配符 %。你改的那条可能根本不是被命中的那条。
ERROR 1130 Host ... is not allowed 任意 → mysql 压根不存在匹配的账号。进 mysql 建一个 'web_user'@'%' 再授权。
502 Bad Gateway nginx → php 三查：① php 容器在跑吗（docker ps）；② 镜像是 fpm 变体吗；③ 9000 端口监听了吗。再用 docker logs lnmp-nginx 看具体是 connect failed 还是 timeout。
浏览器只显示 File not found. 挂载 / 路径 两边挂载路径是否一致（见 ⑦）；./html 里到底有没有那个文件；宿主机上被挂载的是不是被误建成了目录。
413 Request Entity Too Large 浏览器 → nginx 请求体超过 client_max_body_size 25m（default.conf 第 13 行），但别只改这一处，四道关要一起对（见下方知识库）。
容器特有的三条规则（Docker 模式必读）
  • 容器之间只能走 TCP。 不能像裸机那样共用 unix socket —— 两个容器没有共享文件系统。
  • "挂载"不等于"复制"。 改挂载进来的文件内容，容器立刻读到；改 docker-compose.yml 本身（端口 / 环境变量 / 挂载路径 / command），必须 up -d 重建才生效。
  • 容器的文件系统是临时的。 只有卷和 bind 挂载目录里的东西会留下 —— 所以扩展要写进 Dockerfile，数据要放命名卷。
上传大小要过四道关（数值必须递增）
门槛在哪改作用没改的症状
① Nginxclient_max_body_size 25m;限制整个 HTTP 请求体413 Request Entity Too Large
② PHP 表单post_max_size = 25M限制整个 POST 数据提交后空白页、无任何报错（PHP 静默丢弃整个 POST）
③ PHP 文件upload_max_filesize = 20M单个上传文件大小$_FILES 报"文件太大"
④ PHP 时间max_execution_time = 120单个脚本最长执行秒数大文件 / 导入跑到一半 502
为什么不能都填同一个数：POST 体积 = 文件本体 + 表单其他字段 + multipart 边界与头部，所以 post_max_size 必须大于 upload_max_filesize。 两者相等时，一个"看着没超限"的文件会先撞上 post_max_size，PHP 会丢弃整个 POST 且不报错 —— 表现为提交后页面空白、$_POST 与 $_FILES 全空。 这是"文件明明不大却传不上去"最常见的成因。Nginx 侧的 client_max_body_size 必须 ≥ post_max_size，memory_limit 必须 ≥ post_max_size。
两种挂载怎么选：命名卷 vs Bind Mount
对比项Named Volume 命名卷Bind Mount 绑定挂载
写法mysql_data:/var/lib/mysql./html:/usr/share/nginx/html
数据在哪Docker 管理区 /var/lib/docker/volumes/<卷名>/_data你指定的宿主机目录
宿主机直接改路径深、要 root，一般不直接改Vim / IDE 直接改，容器立刻读到
名字规则自动加项目名前缀：lnmp-web_mysql_data相对路径按 compose 文件所在目录解析
compose 里必须在末尾 volumes: 声明，否则报错不需要声明
down 之后容器删了卷还在；加 -v 才连卷一起删完全不受影响
怎么选：代码和配置用 bind（要随时改、看得见）；数据库这类由容器自己维护的数据用命名卷（别让宿主机权限去管它，bind 最容易踩 UID 坑）。 本项目的分法就是：./html、./nginx/default.conf、./php/php.ini 用 bind；mysql_data:/var/lib/mysql 用命名卷。

一个隐蔽的坑：bind 挂载时如果宿主机上被挂载的那个文件不存在，Docker 会自动创建一个同名目录，不报错。 结果 nginx 拿到一个目录当配置文件，行为诡异且报错不直观。上传完先 ls -l 看一眼，权限位以 d 开头就说明搞错了。
裸机必知：三种身份 + fastcgi_pass 三种写法
三种"身份"，别搞混：
身份是谁用在哪
SSH 登录用户root 或普通用户敲命令、传文件
Web 运行用户Debian 系 www-data；EL 系默认 apachePHP 读写文件时的身份
MySQL 账号你创建的数据库用户网站连数据库时用
最常见的坑：用 root 把文件拷进站点目录，属主还是 root，而 PHP 以 www-data 身份运行 → 写不了文件 → 表单一提交就失败。 正确做法：sudo chown -R www-data:www-data /var/www/<站点目录>（EL 系换成 apache:apache）。 不要用 chmod -R 777 —— 那等于让同机任何进程都能改你的网站代码，是提权跳板。

fastcgi_pass 三种写法（socket 名写错就是 502）：
场景典型路径
Ubuntu / Debianunix:/run/php/php<版本>-fpm.sock
EL 系unix:/run/php-fpm/www.sock
走 TCP 端口127.0.0.1:9000
确认真实文件名用 ls /run/php/（Debian）或 ls /run/php-fpm/（EL）。 另外，MySQL 账号 = 用户名 + 来源主机：'app'@'%' 覆盖 socket / TCP / 远程；多条都能匹配时优先级是 具体 IP > 主机名 > 通配符 %。 这就是"改了密码还是 1045"的真正原因 —— 改的那条根本不是被命中的那条。
